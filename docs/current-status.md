# Current status (as of 2026-07-31)

Scaffold complete and verified: `pnpm typecheck` and `pnpm build` pass, `pnpm dev` opens the app. The UI is built with Chakra UI v3. Three things are real: (1) repository management — add local git repos via the native folder dialog, the GitHub slug is read from the `origin` remote, list persists to `~/.pr-reviewer/repositories.json`; (2) API-key settings — a gear on the welcome screen opens a dialog to enter a Claude API key and a GitHub token. Keys are validated with a live API call before saving, encrypted with Electron `safeStorage` (macOS Keychain), and stored in `~/.pr-reviewer/secrets.json`. Raw keys never cross IPC to the renderer; only status (set/not-set) does. A stored key that fails to decrypt (keychain locked, or access denied to that launch of the app) reports as not set but is NEVER deleted — decrypt failures are often transient, and deleting on one destroys the key permanently. (3) live open PRs and diffs — `github/client.ts` uses the stored token to fetch a repo's open pull requests via the GitHub REST API (plain `fetch`, no Octokit), including per-PR line/file counts, and each PR's changed files with their patches (`/pulls/{n}/files`). The Review screen is split into three tabs: **Overview** (`components/PullRequestOverview.tsx`) shows the PR's description and live GitHub metadata — a close/reopen button sits at the bottom next to the dates (`components/ClosePullRequestButton.tsx`, `setPullRequestState` PATCHes the pull's state; inline confirm step to close, Reopen on closed PRs, hidden on merged, success invalidates every open-PR view including `["openPrCounts"]`; only rendered in the full review screen via the `showActions` prop, not the home-screen preview panel) — the panel is a **hero over two columns** (`components/PullRequestHero.tsx` + `components/PullRequestSidebar.tsx`, laid out by a **container query** in `PullRequestOverview` rather than viewport breakpoints, since this panel is a column beside the queue on the home screen and the whole window on the review screen — the only question worth asking is whether there is room *here* for two columns): the hero leads with the **title** (that's what a reviewer is looking for when the panel paints; badges above it made the eye start on a chip), then the state/draft and review-status badges, then one mono line carrying `#number · author · n commits · n files · +adds −dels` — split across two rows it made the first screen mostly metadata — then head → base branch chips, in the direction the code travels (the base is editable in place on open PRs — `components/BaseBranchSelect.tsx`, a searchable Chakra `Combobox` over `getBranchInfo`'s branches (kept in newest-commit-first order; head branch excluded; lazy-loaded when opened) that calls `setPullRequestBase` → PATCH `/pulls/{n}` with `{base}`, then invalidates the detail/files/commits/reviewDecision/list queries since the base drives the whole comparison; closed/merged PRs show a plain badge), the description and conversation fill the reading column, and the right-hand rail (`PullRequestSidebar`, sticky while it is a column, stacked under the column below 900px of panel width) holds the PR's standing facts: **Review status**, **Reviewers** (`ReviewerList` — each reviewer's latest verdict plus those still owed), **Assignees** (`UserList`, shared with the issue rail), **Labels** (each GitHub label's hex colour is mapped by hue to the nearest Chakra palette in `lib/labelColor.ts` and rendered as a themed `Badge` — low-saturation or extreme-lightness colours fall back to gray) and the opened/updated dates. **Every rail section answers its own heading rather than disappearing when empty** ("No reviewers yet", "Nobody assigned", "No labels"): a section that vanishes reads as a panel that failed to load. The rail is sticky, and capped at roughly the scrollport's height with its own overflow — a stuck element taller than the scrollport can never scroll further, so an uncapped long rail (a dozen reviewers and as many labels) would put its own bottom out of reach. Review status (`components/ReviewProgress.tsx`; the pure `buildReviewSteps` is unit-tested) is three steps down a connected line, every one read from state the app already keeps rather than invented: *Read summary* from the cache-only `getAnalysis` (done only while the cached analysis names the current head SHA — one run against an older head is stale progress, not progress), *Inspect n files* from GitHub's viewed-file checkboxes (`["viewedFiles"]`), and *Submit review* from the local draft comments plus whether the signed-in viewer has left a verdict (a bare comment isn't the end of a review, and without a token we don't know who the viewer is, so the step stays honestly pending). It renders only in the full review screen (`showActions`), because each of those reads is a request and the home-screen preview is a quick look. Reviewer assignment and CI checks aren't supported yet, so the rail has no Checks section and no "Add reviewer" button. All of it comes from the `getPullRequest` detail call, plus the PR's conversation timeline, which merges (oldest-first) conversation comments (GitHub issue comments via `listPullRequestComments`, `/issues/{n}/comments`; rendered as `components/CommentCard.tsx` — avatar + author + relative-time header over a markdown body, with an emoji reaction bar at its foot), meaningful reviews, inline review threads, and the PR's commits (`listPullRequestCommits`) — consecutive commits collapse into one grouped block (`components/CommitTimelineGroup.tsx`, each row an avatar + subject + sha linking to the commit on GitHub + relative time), like GitHub's conversation view; the "Conversation (n)" count is discussion items only, not commits; all timestamps app-wide render via `components/RelativeTime.tsx` (relative "3h ago" with the exact date/time on hover, `formatDateTime` in `lib/formatDate.ts`); below the timeline, `components/CommentComposer.tsx` posts new comments (a `MarkdownEditor` with Write/Preview tabs, Cmd/Ctrl+Enter submits, `addPullRequestComment` POSTs and the created comment is appended to the query cache via `setQueryData`); every comment — conversation comments and inline review comments alike — carries an emoji reaction bar (`components/ReactionBar.tsx`): a chip per emoji already used (filled when the signed-in user is one of the reactors) plus a picker for all eight, toggled optimistically through `setReaction` and confirmed by a refetch. Reactions go over GraphQL, not REST: REST's reaction summary can't say whether *you* reacted (finding out would take a request per comment) and its delete endpoint wants the reaction's own id, while the GraphQL `addReaction`/`removeReaction` mutations take the emoji plus the comment's node id — so `PullRequestComment`/`ReviewComment` now carry `nodeId`, and `ReactionContent` is GraphQL's enum (`THUMBS_UP`…`EYES`), mapped to emoji in `lib/reactions.ts` (which also holds the pure `applyReaction` used for the optimistic update, and a fixed display order so a new emoji never shuffles the existing chips). `listReactions` returns one comment-id → reaction-groups map for the whole PR (`["reactions", repo, number]`, shared by every bar so comment count doesn't drive fetch count; paging conversation comments and review threads as two queries; empty rather than an error without a token, since reactions are decoration on a view that must still render). The PR description itself and submitted reviews have no reaction bar yet. Inline diff review comments are a separate endpoint — each inline thread also joins the conversation timeline as `components/ReviewThreadCard.tsx`: a header with the file path and line range (or an "Outdated" badge when `line` is null), the tail of the comment's `diff_hunk` as a mini highlighted diff (trimmed to the commented range, min 4 lines), then the thread itself; resolved threads collapse to just that header with an orange "Resolved" badge and a Show/Hide toggle, like GitHub — resolution isn't in the REST comments, so `listResolvedReviewThreads` (a GraphQL `reviewThreads.isResolved` lookup, joined by the thread's first-comment `databaseId` = REST comment id, paginated past 100) feeds `["resolvedThreads", repo, number]` and a failed lookup just shows threads unresolved; threads can be resolved/unresolved in-app: `DiffCommentThread`'s footer shows a Resolve/Unresolve conversation button whenever the caller knows the current state (the Overview's cards, and the Changes tab's diffs — ChangesView also queries `["resolvedThreads"]` and passes the id set through `DiffCommenting.resolvedRootIds`), calling `setReviewThreadResolved` over IPC — a GraphQL `resolveReviewThread`/`unresolveReviewThread` mutation, with the thread's node id looked up by paginating `reviewThreads` until the first-comment `databaseId` matches the REST root comment id — then invalidating `["resolvedThreads"]`; on-diff rendering is on the Changes tab — see below); **Changes** (`components/ChangesView.tsx`) is the real selectable file list + unified diff (`components/DiffView.tsx`) — the file-list sidebar is drag-resizable via `lib/usePanelWidth.ts` (a shared hook that also powers the Review tab's chat column: pointer-drag from the panel edge, width clamped and persisted per localStorage key; a panel's bounds are declared as a `PanelBounds` beside the panel, so whoever lays it out uses the same numbers) and has a filter input above the list (case-insensitive substring match on path/previousPath, Esc clears, the Files heading shows matched/total while filtering; the value is debounced 150ms via `use-debounce`, and `DiffLines` is `memo`ized — with ChangesView memoizing its `commenting` prop for referential stability — so filter keystrokes re-render only the sidebar, never the diff rows) — with an optional commit-by-commit mode — a collapsible (collapsed by default) compact scrollable commit list (`components/CommitsPanel.tsx` over `components/CommitList.tsx`, shown only when the PR has 2+ commits, fed by `/pulls/{n}/commits` via `listPullRequestCommits`) is anchored to the foot of the file-list column, under the files and above that column's own controls (the "Hide test files" row here, the commit box in the local view) — below the files, not above them, because the changed files are what the column is opened for and history is what you go looking for; picking a commit swaps the file list/diffs to just that commit's changes (`listCommitFiles`, `/commits/{sha}`), and an "All changes" row at the top reverts to the full changelist (the default). Files can be marked as viewed like on GitHub — and it IS GitHub's state (GraphQL `viewerViewedState` + `markFileAsViewed`/`unmarkFileAsViewed` mutations, with the PR node id cached per app run in `client.ts`), so checks sync with github.com and a file changed after viewing auto-unchecks (DISMISSED counts as not viewed): a "Viewed" outline button in the diff header (`DiffView`, left of the +/− counts; green with a check when on), viewed rows dimmed with a green check in the file list (`FileList` — whose rows also carry two count chips: review comments (`CommentCountBadge`, gray) and local AI explanations (`ExplanationCountBadge`, accent-tinted with a sparkle so it doesn't read as GitHub data; counts from `["explanations", repo, number]`), both hidden at zero), and an "n/total viewed" counter beside the Files heading, all fed by `["viewedFiles", repo, number]` (`listViewedFiles` returns `[]` without a token) with optimistic toggles via `setFileViewed`; like inline commenting, all of it is scoped to the all-changes view, not commit-by-commit. The Changes tab also has GitHub-style inline review comments: `listReviewComments` (`/pulls/{n}/comments` — the review-comments API, distinct from the conversation's issue comments) loads existing inline discussions, grouped into per-file threads by `lib/reviewComments.ts` (replies attach via `in_reply_to_id`; a reply orphaned by a deleted root is promoted to root so the thread survives; outdated threads — `line: null` — are dropped from the diff but still shown in the Overview timeline), each rendered by `components/DiffCommentThread.tsx` under its anchor line with a reply box (`replyToReviewComment`, `/pulls/{n}/comments/{id}/replies`) and, on the viewer's own comments (login via `getViewer`, cached under `["viewer"]`), a hover-revealed delete button with an inline confirm step (`deleteReviewComment`, DELETE `/pulls/comments/{id}`; success refetches the list rather than editing the cache, because deleting a thread's root re-roots its replies server-side). Diff lines covered by an existing thread's range get a yellow marker stripe on their left edge (`isCommented` in DiffLines, works in both view modes). Hovering a diff line shows a "+" gutter button — click for one line, or press-and-drag for a range (one side, one hunk; GitHub's rule: deleted lines anchor LEFT, added/context lines RIGHT) — opening `components/DiffCommentComposer.tsx`, which posts via `addReviewComment` (`commit_id` = the detail query's full `headSha`; the summary `PullRequest.headSha` is truncated and must not be used). Inline comments can also be **drafted into a batch review** — GitHub's pending-review flow, but held locally: the composer offers "Add single comment" (posts immediately, as before) and "Start a review" (saves a draft); once any draft exists on the PR only "Add review comment" is offered, like GitHub. Drafts live in the main process (`store/drafts.ts`, `~/.pr-reviewer/drafts.json` keyed repo#number — disk-backed so a half-written review survives restarts; CRUD over IPC as `listDraftComments`/`addDraftComment`/`updateDraftComment`/`deleteDraftComment`, renderer cache `["draftComments", repo, number]`), render under their anchor lines as `components/DraftCommentCard.tsx` (yellow "Pending" badge, edit-in-place, delete with inline confirm) with the same gutter stripe as real threads (`DiffCommenting` carries `drafts` + `reviewStarted`), and count into the Submit review trigger's label ("Submit review (3)"). `SubmitReviewDialog` lists the pending comments, a comment-verdict review with drafts needs no body, and the main process's `submitReview` attaches them as the `comments` array of the single `POST /pulls/{n}/reviews` call — one notification for the author — clearing the drafts only after GitHub accepts. All of this lives in `DiffLines` behind an optional `commenting` prop (`DiffCommenting`), so it works in both inline and split modes — in split view the two-column layout is cut into segments so thread/composer bands span the full pane width between them — and is only wired up in the Changes tab's all-changes view (commit-by-commit diffs number lines differently than the PR diff, and Review-tab `FileDiffCard`s stay read-only); **Review** (`components/ReviewPanel.tsx`) holds the agent summary + Q&A chat. The PR description renders as real GitHub-flavored markdown (`components/Markdown.tsx`, react-markdown + remark-gfm, plus rehype-raw → rehype-sanitize so inline HTML — which GitHub allows and bots like Notion's rely on — renders instead of showing as escaped text, with untrusted tags/attributes stripped); external links open in the system browser (main-process `setWindowOpenHandler`/`will-navigate` guard via `shell.openExternal`). (4) the analysis pipeline is real — the stored Claude key powers a single structured-output call (see `docs/analysis-pipeline.md`), exposed over IPC as `getAnalysis` (cache-only check, returns null if not analysed) and `analyzePullRequest` (runs the model; takes the review personality and an optional `force` that skips the cache read — the summary pane's footer has a small "Re-analyse" button that uses it). The model sometimes leaks the groups JSON into the summary string; `splitLeakedGroups` in pipeline.ts strips it (and uses the leaked copy as groups if the real field came back empty). The Review tab is the guided review: a "Quick review / Deep review" empty state (analysis is never automatic), then a three-panel layout — left, `components/AnalysisNav.tsx` (a Changes-style nav list: Summary, then the **Issues** section, then each reading-guide group and behavior change as a clickable row; claims show their short `title`, groups get risk-colored dots); middle, `components/AnalysisDetail.tsx` renders the selected item — the summary pane (+ "Not in this PR" + analysed-commit footer), an issue pane, the resolved-issues pane, or a claim/group with its full text and the relevant files' diffs embedded as collapsible cards (`components/FileDiffCard.tsx`, mechanical groups start collapsed) plus clickable `file:line` anchor chips that scroll to the diff within the pane (shared pane pieces — anchor chips, diff cards, the "Ask about this" split button — live in `components/AnalysisShared.tsx`); right, `components/ChatPanel.tsx` is the full-height Q&A column. **Issues is the merged home of the analysis's risks and the findings pass** (`lib/issues.ts` builds the unified list): every open issue is its own nav row (severity dot; a green check marks **verified** findings), opening `components/IssuePane.tsx` — a verified finding shows severity + category + Verified badges, the body, the anchored file's diff, the "Suggested comment", a **copy-as-markdown** icon button in its header (`lib/issueMarkdown.ts` — title, severity/category/verdict, backticked `path:line` anchors, body, then the anchored code as a fenced ```diff block per anchor, then the suggestion — evidence before the ask, for pasting into a coding agent or a message; unit-tested, and it always carries the verdict so an unverified risk can't be pasted as though it were confirmed. It also names the commit the anchors were measured against, and when the PR has moved past it the code blocks are **omitted** with the mismatch stated in the document: the snippet is cut from the *current* diff at a line numbered against an older one, so it can hold unrelated code, and wrong evidence is worse than none. The staleness facts (`IssueAnchorCommits` — the analysis SHA, the findings SHA, and the PR's head) are built once in `ReviewPanel` and passed to both copy paths, since risks and findings can come from different commits and two components assembling this separately is what let the copy path drift from the draft path's guard. The code comes from `lib/patchSnippet.ts`, which cuts a window (±10 rows) out of the file's patch around the anchor line and **synthesizes its own `@@` header** from the rows it returns — copying the original would describe lines the window doesn't include; an anchor that isn't in the diff, or a file whose patch hasn't loaded, simply gets no block rather than a misleading one). The Issues section header has the **bulk form** of the same thing beside the findings-run button (`components/CopyIssuesButton.tsx` → `issuesToMarkdown`): every open issue in one document under a counted heading, split by `---`, each issue still self-contained (its own verdict, location, and PR reference) since a long paste usually gets split up again at the other end; it waits for the files query rather than copying a whole review with none of its code quoted, and **Add as draft comment** (creates a draft review comment via `addDraftComment`, then marks it `accepted`; blocked when the findings run is outdated, since the anchor line may have moved) / **Dismiss** / **Ask about this**; an **unverified** risk (the findings pass hasn't confirmed or cleared it) shows an Unverified badge with Ask/Dismiss, plus a "checking" spinner while a findings run is in flight. Confirmed risks disappear from the list (their verified finding represents them); cleared risks move to the **Resolved** row at the section's foot (`components/ResolvedIssuesPane.tsx` — accepted/dismissed issues restorable via `lib/useIssueResolution.ts`, cleared risks badged "Non-issue" with the agent's note — verdict appearance is enum-driven: `issueVerdict` in `lib/issues.ts` maps each issue to verified/non_issue/checking/unverified and `verdictMeta` — beside it, with `categoryMeta` — maps that to badge label/colour, so the model never writes verdict prose, only the one-line note; both tables live in the lib rather than in a component because the copy-as-markdown output has to use the same words as the badges). The findings pass runs when the user picks a deep review (both `ReviewPanel`'s empty state and `ReanalyzeButton` chain it with `force`, sharing the `["findIssues", repo, number]` mutation key so `useIsMutating` drives every loading state); after a quick review, the telescope icon button in the Issues section header runs it on its own (it becomes a re-run icon once findings exist). Selection state (`AnalysisSelection`, exported from AnalysisNav) lives in `ReviewPanel` and falls back to Summary if a selected item no longer exists. Risk badges: `components/RiskBadge.tsx`. The chat is a repo-aware agent (`agent/session.ts` + `agent/tools.ts`): the main process keeps one context per PR (rebuilt if the PR gets new commits) and disk-backed conversation histories in `~/.pr-reviewer/chats.json` (capped at 100 messages per PR; the newest 20 go to the model as context) — exposed as `getChatHistory` over IPC, which `ChatPanel` loads via `useQuery(["chatHistory", …])` with local overlay state for streaming/failed messages, so conversations survive restarts; context = the same capped diff the analysis uses (`buildPullRequestContext`, exported from pipeline.ts) + the cached analysis JSON; model `claude-sonnet-5` (fast for interactive use — Opus stays on the one-shot analysis); the context block is marked `cache_control: ephemeral` so follow-up questions hit Anthropic's prompt cache. Answers stream: the main process parses the SSE stream and pushes `text_delta`s to the renderer via `webContents.send` on the `chatChunk` channel (see `ChatChunk`/`RendererEvents` in `shared/ipc.ts`; preload exposes `onChatChunk` returning an unsubscribe); `askQuestion` still resolves with the full answer, which replaces the streamed text as the authoritative copy. On top of that runs a client-side tool loop (max 8 rounds; the final round is sent without tools to force a text answer): the model can call `read_file`, `list_files`, `grep_repo`, and `git_log` (defined + executed in `agent/tools.ts` against the workspace clone, pinned to the PR's head SHA). `grep_repo` triggers `ensureHeadBlobs` first — a targeted backfill that lists the blobs missing from the reviewed commit's tree (`rev-list --missing=print`, which counts donor/alternate objects as present) and batch-fetches just those by id; it also runs during PR warm-up, so the first grep rarely waits. Within a question's loop, the full tool conversation is kept and a moving `cache_control` breakpoint sits on the newest tool results so each round re-reads the prefix from Anthropic's prompt cache; stored history stays plain text (tool activity is not replayed across questions). Tool failures are returned to the model as `is_error` tool results — it's prompted to fall back to diff-only answers and say what it couldn't verify. Diff rendering is shared: `lib/diffParser.ts` (patch → lines + syntax highlighting via `lib/highlighter.ts` (shiki) — each hunk is highlighted as two whole documents, old side (del+context) and new side (add+context), and shiki hands the tokens back already split by line, so multi-line constructs like `/** */` block comments and template literals keep their state across lines; hunks are never concatenated since the unseen gap between them could invalidate carried-over state; plus `buildSplitRows` which pairs del/add runs into side-by-side rows) feeds `components/DiffLines.tsx`, used by both the full-pane `DiffView` (Changes tab) and `FileDiffCard` (Review tab); file status letters/colors live in `lib/fileStatus.ts`. On the Changes tab, `DiffView` also fetches the file's full contents at the diff's commit from the workspace clone (`getFileAtCommit` over IPC → `readFileAtCommit` in `repo/workspace.ts`, null for binary/unavailable — everything degrades to diff-only; query `["fileAtCommit", repo, sha, path]`, infinite staleTime, excluded from persistence) and hands it to `DiffLines` as `DiffExpansion`, which buys three things: (1) add/context rows swap their html for slices of the whole highlighted file — per-hunk fragment highlighting mis-colors hunks that start mid-construct (e.g. inside a JSX tag); a text-equality guard between the file and the diff drops the upgrade when they disagree; (2) hunk headers grow an expand button (and a tail row after the last hunk) that splices the hidden gap in as `expanded: true` context rows via `computeGaps`/`expandLines` in diffParser — expanded rows can't host comments (GitHub can't anchor outside the diff) and count as hunk separators so comment selections can't cross them; (3) a "View file" toggle in the header renders the entire file (`components/FileView.tsx`, same mono font + syntax palette as diff rows) — it also works for too-large-to-diff files, and deleted files opt out of all three (no file at that commit). Diffs render inline or split (side-by-side): the global layout mode lives in `lib/diffViewMode.ts` (localStorage + `useSyncExternalStore` hook so every mounted diff reacts), picked via `components/DiffViewModeSelect.tsx` at the right end of the Review screen's tab bar (its menu is portalled — non-portalled it stacked under the diff panes' sticky elements) — Inline / Split / Dynamic, where Dynamic goes split per diff when its container is ≥960px (ResizeObserver in DiffLines). Nothing is mock anymore, and the chat can see beyond the diff via its repo tools. (5) attachments are real — images and videos can be pasted, dropped, or picked in any markdown editor and are uploaded to GitHub through a signed-in github.com session (there is no API for it), then render back as inline images and video players (see `docs/attachments.md`).

The repo workspace is real (`repo/workspace.ts` + `repo/git.ts`): opening a PR fires a best-effort background warm-up (from the `getPullRequest` IPC handler) that maintains a **bare, blobless** clone per repo at `~/.pr-reviewer/repos/owner__repo.git` — no checkout; everything is read from the object store pinned to a commit (`showFile`/`listFiles`/`logForPath`), so all PRs of a repo share one clone and blobs download lazily on first read. The PR's head commit comes from `refs/pull/<n>/head` (works for fork PRs). Clones use the user's registered local checkout as an object donor (`--reference-if-able`) when available — the alternates link persists, so donor objects count as present forever. Warm-up finishes by backfilling the head commit's tree (`ensureHeadBlobs`): batch-fetch only the blobs missing after the donor and previously-fetched PRs are counted, so grep never has to lazy-fetch file-by-file and each PR only downloads its own delta. Auth: the GitHub token is injected per-command via `GIT_CONFIG_*` env vars (never written to the clone's config); every git command gets it because lazy blob fetches can happen on any read. Syncs are deduped in-flight and rate-limited (5-min TTL).
