# Architecture details

Full detail behind the short summary in `AGENTS.md`. Read this file when working on the tab bar, the sidebar, the review queue, or the main review screen.

Electron (chosen over Tauri because the Claude Agent SDK, Octokit, and git tooling are all Node/TypeScript — Electron's main process runs them natively; Tauri would need a Node sidecar).

- **Main process (Node)** — all the real work: GitHub API (Octokit), local repo clones under `~/.pr-reviewer/repos` (blobless: `--filter=blob:none`), diff parsing, the analysis pipeline, Claude Agent SDK sessions, SQLite persistence. Secrets never reach the renderer.
- **Tab navigation** — the app holds several things open at once, as a row of tabs across the top (`components/TabBar/`). A reviewer jumping between three PRs and a working tree does not have to close one to look at the next. `lib/tabs/tabs.ts` is the state: a `Tab` is a discriminated union of the pinned **queue** tab, a **pull request** tab, a repository **Issues** tab, and a **local changes** tab (one per worktree; not wired up yet, so Current changes is still a tab inside the queue). Every change is a pure `(state, args) => state` function, tested in the node environment; `lib/tabs/useTabs.ts` is the Zustand store over them, persisted to localStorage so the row survives a restart. Zustand rather than the `useSyncExternalStore` pattern the settings stores use (issue #49), for the selectors: a PR tab records the text in its file filter, and the tab bar must not render again for each key press. Rules worth knowing: a tab's id comes from its content (`pr:owner/repo#7`), so opening a PR that is already open focuses that tab and shows the pane the caller asked for rather than adding a second tab; the **queue tab is pinned first and cannot be closed**, because it is the way back to the lists; closing the active tab activates the tab to its right, then the left at the end of the row; the `PullRequest` in a tab is a copy taken when it opened and is only ever read to draw the tab, so the query cache stays the one source of truth for what the screen shows; and a stored tab the app cannot parse is dropped on its own rather than failing the whole row. **There is one queue tab, not one per repository** — picking a repository points that tab at it and closes nothing, which is the whole win: the PRs you had open stay open. `App.tsx` therefore holds only what the queue needs (the active repository path and the preview PR) plus the settings dialog. The tabs store holds each repository Issues tab, including its selected issue, filters, and page. Shortcuts in `lib/hotkeys.ts`: Cmd/Ctrl+W closes, Control+Tab and Control+Shift+Tab move along the row (Control on macOS too, since Command+Tab belongs to the OS), and Cmd/Ctrl+1–9 select by position with 9 meaning the last tab. `MAX_LIVE_TABS` and `pickLiveTabIds` are in place for keeping more than one tab in the DOM, but **App still mounts only the active tab**: switching repaints from the query cache at once, and scroll position resets. Chromium clears `scrollTop` when an element goes to `display: none`, so keep-alive has to keep the layout box (`visibility: hidden`, or `content-visibility: hidden`) — measure which one holds the scroll in the running app before writing that code.
- **Renderer (React + Chakra UI v3)** — purely presentational. Below the tab row, a full-height split. Left, `components/HomeSidebar.tsx`, which `App.tsx` renders **beside every tab**, so a reviewer can jump straight from one PR to the next. Its PR rows always open the PR itself — no preview step, since picking a PR from a list you deliberately keep in the sidebar means you want to read it; the preview panel is for the **Repositories** flow, where the main column lists a repo's open PRs and you may be skimming. Picking a repository leaves the review screen for the home screen's open-PR list (and drops any preview, which belonged to the old repo). The row for the PR being reviewed is marked (`selected` on `SidebarPullRequestRow`, the same style as the active repo). Because the sidebar now outlives the home screen, the state it needs sits in `App.tsx`: the registry and its three mutations in `lib/useRepositoryActions.ts` (shared with the home screen's empty-state "Add repository"), the recently-viewed list, the preview PR, and the settings dialog. It can be hidden — useful when reading a wide diff: `lib/sidebarCollapsed.ts` (localStorage + `useSyncExternalStore`, so both screens react), hidden with the panel button right of Settings in the sidebar's header, brought back with `components/ShowSidebarButton.tsx` at the left of either screen's top bar, and toggled with **Cmd+B / Ctrl+B** — the app's keyboard shortcuts go through TanStack Hotkeys (`@tanstack/react-hotkeys`, alpha; `HotkeysProvider` in `main.tsx`, `useHotkey` in `App.tsx`), with the binding and its platform-aware tooltip label in `lib/hotkeys.ts`: the library's `Mod` resolves to Command on macOS and Control elsewhere, and `formatForDisplay` writes it as "⌘ B" or "Ctrl+B" for the two buttons' tooltips; that bar also takes over the macOS traffic-light padding while the sidebar is away. The sidebar has five sections, each collapsible (a Chakra `Collapsible` per section — the chevron sits in the heading trigger, section-level actions stay outside it so buttons aren't nested, and the collapsed set persists in localStorage via `lib/sidebarSections.ts`, keyed by section id so a newly added section starts open; headings carry a count so a collapsed section still says how much is in it) — **Repositories** (`components/RepositoryList.tsx` — each row shows the owner org/user's avatar (rounded, `UserAvatar` with the folder icon as fallback — also used when the repo has no slug) and, at its right edge, the repo's open-PR count (query `["openPrCounts"]` → `getOpenPullRequestCounts`, one aliased GraphQL query over all registered slugs; no token or an inaccessible repo just omits that entry) in a fixed slot that swaps to the remove button on hover; rows are drag-sortable via dnd-kit: whole-row drag with a 4px pointer-distance activation so plain clicks still select, the dragged row rendered in a `DragOverlay` — the row left behind dims as the placeholder and the default drop animation glides the overlay into its slot instead of snapping; the new order is set optimistically in the `["repositories"]` cache and persisted through the `reorderRepositories` IPC call, which reorders the registry by path, appends any paths the renderer didn't send, and returns the saved list), **Review requests** (open PRs where the user's review is requested, via `listReviewRequestedPullRequests` over IPC — GitHub issue search `review-requested:@me`, filtered in the main process to the registered repos' slugs before the per-PR detail fetches; query key `["reviewRequests"]`; compact rows with the author's avatar (PR icon fallback) and a comment-count chip), **My pull requests** (same shape for `author:@me` via `listMyPullRequests`, query key `["myPullRequests"]`, comment-count chip, default PR icon; both sections share `searchOpenPullRequests` in `github/client.ts`, and `Welcome.tsx` invalidates both queries when repos are added/removed since the registry drives the filter), **Analysed** (`components/AnalyzedSidebarList.tsx` — PRs the user has run the analysis on, newest first, across every repo (not scoped to the selected one, unlike the old tab) and capped at the 7 newest since the section shares the sidebar with four others; the main process's cache only stores repo/number/sha, so each row fetches live detail through `peekPullRequest` under the shared `["pullRequest", …]` key, showing a skeleton until it lands; the row's meta is the analysis's age, turning orange when the analysis was run against a commit that's no longer the head), and **Recently viewed** (compact rows, not full cards — PRs the user has opened from any repo, stored in renderer localStorage via `lib/recentPrs.ts`, recorded by `App.tsx` on select, capped at 7 — enforced on read too, so older longer lists trim themselves — each row shows the author's avatar (PR-icon fallback), with a clear button in the section header) — and a footer anchored at the bottom with two actions: "Add repository" (folders picked via the native directory dialog) and Settings (opens the settings dialog). The main column is the **review queue**: a header naming it (with a refresh button, a compact New-pull-request trigger, and `components/QueueActionsMenu.tsx` — open the repo on GitHub, add a repository, Settings, since the sidebar that also offers the last two can be hidden), then three navigation triggers carrying counts — **Open (n)**, **Issues (n)**, and **Changes (n)**. Open and Changes select a queue view. Issues opens or focuses one top-level tab for that repository. On the pull request queue and the top-level Issues screen, the list is a narrow, drag-resizable column (`lib/usePanelWidth.ts`, key `reviewQueueWidth`, 380–700px, default 480) with the preview panel filling the rest of the window beside it — a list read top to bottom doesn't need the width, and the thing being read does; on the Changes tab the split is different again: the tab bar caps a narrower file-list column (`localChangesFileListPanel`, 220–600px, default 300) and the diff fills the rest of the window from directly under the top bar, so nothing sits in a strip of empty space above the diff. That is why the queue's chrome is two components — `components/QueueHeader.tsx` is the full-width top bar, `components/QueueTabs.tsx` the tab triggers, placed over whichever column the tab in question uses. Everything in the column shares a `4` gutter, rows included, so the tabs, the filter box and the row text all line up. With nothing picked in a list, the space beside it holds a one-line placeholder rather than letting the column stretch. Current changes is a review of the selected repo's *uncommitted* work with real git actions (for reviewing an agent's slice before it becomes a PR, then committing it): `components/LocalChangesColumn.tsx` (the file list, filter and commit box) beside `components/LocalChangesPane.tsx` (the diff), with `lib/useLocalChanges.ts` holding the state they share — the two are separate components because the tab bar caps the column and not the window, so they can't be one. It is the Changes-tab layout minus every PR-only affordance (no commenting, viewed state, or context expansion). The file list splits into **Staged** and **Unstaged changes** groups the way git sees them — a partially staged file appears in both, which is git's model, not a bug; staged rows' names tint green. Rows reveal hover actions (unstage on staged rows; stage and discard on unstaged ones — `FileList`'s optional `rowActions`, drawn in the diff-counts slot), each group has a bulk button whose label says "shown" instead of "all" while a filter is active (`lib/localChangesSelection.ts`, which also carries a staged rename's old path along so unstaging can't leave the deletion half behind), `components/CommitComposer.tsx` under the list commits exactly the index — never "commit -a", so the Staged group is the record of what's about to be committed (Cmd/Ctrl+Enter; success toast carries the short SHA) — and discard goes through `components/DiscardChangesDialog.tsx`, a real confirmation dialog since it's the app's one irreversible action: tracked paths revert to the index, untracked ones are deleted outright, and the dialog is told which are untracked by the data (`LocalChanges.untracked`), never guessed from status letters. The tab also reads the branch's **committed** history, through the same affordance the PR Changes tab uses: the same `CommitsPanel` at the foot of the column (over `CommitList`, generalized with `allLabel`/`newestFirst` — here the top row says "Uncommitted changes" rather than "All changes", the panel's `hint` names the base while nothing is picked, and git log is already newest first). Picking a commit points the whole tab at it — a flat file list of what it changed, its diffs, and its own message above them (`components/CommitMessageHeader.tsx`) — read-only, with the commit box **disabled rather than removed**: a commit box under a past commit's files reads as an offer to change that commit, and unmounting it made the panels above it jump every time a commit was picked. `listLocalCommits` (`repo/commits.ts`) picks the range rather than taking one: the trunk first (`origin/HEAD`, else the well-known names) so `trunk..HEAD` is exactly the work done on this branch, then `@{upstream}` — which is what answers on the trunk itself, making the list the unpushed commits — and recent history (capped at 200) when the checkout is level with both, with `base` returned so the heading can say "vs origin/main" instead of showing a number with no unit. `getLocalCommitFiles` diffs a merge against its first parent (`-m --first-parent`): git's combined diff is a different format, and the question is what the commit brought in. Both go through the same `parseGitDiff` the uncommitted lists use, so a commit's files render through the existing `FileList`/`DiffView` unchanged. Queries `["localCommits", path]` (staleTime 0, refetch on focus — new commits land while the app runs) and `["localCommitFiles", path, sha]` (infinite staleTime, since a commit is immutable); neither is persisted, and a selected commit the list no longer holds (amended, rebased away) drops back to the uncommitted work rather than leaving an empty pane. Reads come from `getLocalChanges(repoPath)` over IPC → `main/repo/changes.ts`, which diffs the index against HEAD (`diff --cached`; the empty tree only when the repo has no commits yet) and the working tree against the index as separate diffs, diffs each untracked file against `/dev/null` (a small worker pool caps process spawn), and parses the output into the same `PullRequestFile[]` shape the diff UI already renders — binary files and patches over 1MB get `patch: null` (the viewer's existing "too large" state), and header paths handle git's C-quoting plus the trailing tab it appends to unquoted spaced paths. Writes (`stageFiles`/`unstageFiles`/`discardChanges`/`commitChanges`) are wrapped by `main/ipc/localChanges.ts`: every mutation first checks the path is a registered repo or one of its listed worktrees, and writes are serialized per checkout because git holds one index lock. In `changes.ts` itself, every git call runs with `GIT_LITERAL_PATHSPECS=1` so a filename like `pages/[id].tsx` can never glob onto other files; unstage falls back to `rm --cached` in an unborn repo; discard splits paths by `ls-files`, restoring tracked ones and `clean -f` (never `-x`, so ignored files survive) on the rest; and failures surface git's stderr/stdout so hook output and "nothing to commit" reach the user's error toast. No token, no network — it's the one view that works on a repo with no slug. The tab label's count comes from the cheap `getLocalChangeCount` (porcelain status only — no patches are built just for the badge; query `["localChangeCount", repoPath]`, always-on for the selected repo), while the detailed `["localChanges", repoPath]` query (options for both exported from `lib/useLocalChanges.ts`) runs only while the tab is showing; both are `staleTime: 0` + refetch-on-focus since the working tree moves constantly, and never persisted; while the tab is showing, the top bar's right side swaps the New-PR button for a refresh button refetching those queries. The checkout's branch name sits at the **head of the file-list column**, under the tabs and over the files — it belongs with the files it decides, not in the window's top bar (`components/BranchLabel.tsx`). When the repo has linked git worktrees (agents often work in several at once), that branch label becomes a worktree switcher (`components/WorktreeSelect.tsx`, fed by `listWorktrees` over IPC → `git worktree list --porcelain -z` in `repo/local.ts`, skipping bare/prunable entries; query `["worktrees", repoPath]`, never persisted): picking a worktree points the whole tab — file list, diffs, branch label, count — at that checkout's path (`useLocalChanges` takes the whole `WorktreeSelection` — the column draws the picker itself — and every query was already keyed by path), and the selection lives in `Welcome.tsx`, only honoured while it names a listed worktree so a removed worktree or a repo switch falls back to the registered checkout. The Open tab is the selected repo's open PRs — rendered by `components/OpenPullRequestList.tsx` as rows, not cards (`components/QueueRow.tsx` is the shared shell — icon, truncated title, a trailing slot, a meta line and a footer line, hairline-separated, the selected row marked with an accent bar down its left edge; `components/PullRequestQueueRow.tsx` fills it in: the PR icon tinted by **state** since the rows carry no state badge — grey draft, green open, purple merged, red closed, from `prStateMeta` exported by `PrStateBadge.tsx` so the icon and the badge can't disagree about whether a PR is merged or merely closed (the row paints open green where the badge uses blue: GitHub's colour, and a column of blue icons reads as links). The summary type has no `state`/`merged`, which is honest — every list feeding these rows asks GitHub for open PRs only, so a row is a draft or it's open — then `+adds −dels`, `#number author · n commits · n files` with the comment chip, and the repo slug over a relative time. `PullRequest` carries an optional `commits` (optional because lists persisted before it existed don't have it, and a row would rather leave the segment out than claim zero)). Above the rows sits `components/QueueFilterBar.tsx`: an always-there filter box (`filterByText` in `lib/listFilters.ts` — title, author, or the number with or without its "#") over the Author / Assignee / Sort dropdowns, which hide behind a sliders button because the column is too narrow for three selects side by side and the text box is what a reviewer reaches for nine times in ten; a dropdown away from its default puts a dot on that button, so a filter can't hide rows while the control that set it is out of sight. Filtering and sorting stay client-side over the already-loaded list (sorts: newest/oldest/most/least commented/recently/least recently updated; assignee includes "Assigned to nobody"), and the component is keyed by repo slug so filters reset on repo switch. Each row's time follows the sort (`sortTimeField`) — created for the "newest" sorts, updated for the two update sorts — since "updated 5m ago" on a row in a list ordered by opening date reads as a broken sort. One fetch returns the `OPEN_PULL_REQUEST_LIMIT` (50, in `shared/types.ts`, used by the GraphQL query itself) most recently updated open PRs; unlike the issue list, the queue deliberately doesn't say so on screen — a standing notice above the rows a reviewer reads all day earns its space less than the rows do; the top-level **Issues** tab is the same shape for one repository's open GitHub issues — read-only in v1 (`components/RepoIssueList.tsx` → `RepoIssueQueueRow.tsx` (the same `QueueRow` shell, with the issue's labels in the slot the PR rows give the repo slug — labels are the one thing that tells two same-shaped issues apart at a glance) → `RepoIssuePreview.tsx` wrapping `RepoIssueOverview.tsx`, which needs only two queries where `PullRequestOverview` needs six: an issue has no reviews, inline threads or commits, so its conversation is a plain oldest-first comment list). Names carry a **`RepoIssue`** prefix throughout because "issue" already means *a finding from the analysis agent* everywhere else in this app (`lib/issues.ts`, `IssuePane.tsx`, the `findIssues` IPC method). `listRepoIssues` is GraphQL, deliberately: REST's `/repos/{repo}/issues` returns pull requests mixed in, while the `issues` connection excludes them by construction. Comments are free — `listIssueComments` in `github/client.ts` (renamed from `listPullRequestComments`, which always hit `/issues/{n}/comments`) serves a PR's conversation and a real issue's alike, since GitHub numbers both in one sequence per repo. Reactions are off on issue comments (`showReactions={false}` on `CommentCard`) until `listReactions` grows a `repository.issue(number:)` twin; its `setReaction` half already works, taking a bare node id. The tab's list query is gated on the tab being open, so a user who never opens Issues never spends the request. Its trigger reads GitHub's repository total when available and falls back to the cached list length. `screens/RepoIssues/RepoIssues.tsx` owns the list and reading-panel layout. The `repoIssues` tab entry persists the selected issue number, filters, and page, while TanStack Query remains the source of issue data. The two lists share `lib/listFilters.ts` (`filterByPeople`/`sortListItems`, generic over a `Listable` shape both types satisfy) and `components/FilterSelect.tsx`; the two overviews share their whole layout — `components/ReadingPanel.tsx` owns the shape both reading panels take (container-queried hero over reading column + rail, and the measurements that go with it), with `RepoIssueHero`/`RepoIssueSidebar` mirroring the PR's pair: same title size and weight, same mono meta line (an issue has no branches or diff, so its line carries the comment count — and only once the comments have loaded, since a count that starts at zero and jumps reads as an issue nobody replied to), same rail sections minus the ones an issue has no answer for (no review status, no reviewers). One component rather than two copies of one grid, because the two are meant to feel like the same screen with different content and that only survives if the measurements live in one place. They also share `RailSection`, `UserList`, `SectionHeading`, `LabelBadges`, `OpenedUpdatedLine`, and `PanelState`'s loading/error states. The issue list pages 25 at a time — `components/ListPagination.tsx` over the *filtered* list, so the dropdowns still cover everything loaded; any filter change resets to page 1, and the page number is clamped on render rather than stored outright, so a refetch that returns fewer issues can't strand the list past its own end. One fetch returns the `REPO_ISSUE_LIMIT` (50, in `shared/types.ts` because both processes need it) most recently updated open issues, and the list says so once it is that full: filters run over the loaded slice, so a silent cap would let "no issues match" read as "this repo has no such issue". A comments fetch that fails is reported in place — `PanelSectionError` in `PanelState.tsx`, where the conversation would have been, with a Retry — never as a toast: every toast in this app belongs to a write the user triggered, and a toast for a failed read is gone in seconds while the gap it described stays on screen reading as "nobody replied". The pull-request overview uses the same notice, and no longer hides its whole conversation (reviews, commits and the comment box included) when only the comments failed. The closed-state badge only claims "completed" when GitHub says `completed` — issues closed before 2022 carry no reason at all, and "Closed" is the honest reading of that. In the queue's header, a "New pull request" trigger (`components/NewPullRequestDialog.tsx`, shown when the selected repo has a slug, keyed by slug; its `compact` prop makes the trigger an icon button, since the queue header has no room for a labelled one) opens a create dialog: `getBranchInfo` over IPC (query `["branchInfo", repo]`, `staleTime: 0` so a just-pushed branch always shows, fetched only while open) returns the repo's GitHub branches sorted newest commit first — a GraphQL `refs` query (REST can't sort branches by activity at all) paged alphabetically to ≤500 with `defaultBranchRef` in the same call, then **sorted by `committedDate` in the main process**: GitHub's only date-ish `RefOrder` field is `TAG_COMMIT_DATE` and for `refs/heads` it's silently ignored, so asking for it DESC just returns reverse alphabetical (branches with no commit date sort last; a repo over the 500 cap is truncated by name before the sort sees it) and — via `getLocalCheckoutBranch` in `repo/local.ts` (`git symbolic-ref`, null on detached HEAD/unregistered) — the local checkout's current branch, pinned to the top of the list when it's on GitHub; head defaults to that branch when pushed and non-default (an info alert says to push first when it isn't), base to the default branch (the title is deliberately never prefilled), and untouched fields use a null-means-suggestion pattern so late-loading data still prefills — this also carries the repo's PR template into the description: `getBranchInfo` returns `pullRequestTemplate` (read from the default branch via the contents API, probing the conventional `.github`/root/`docs` `PULL_REQUEST_TEMPLATE.md` paths in parallel, best-effort), and the body falls back to it until the user types; head/base are non-portalled searchable `Combobox`es (portalled menus stack under the dialog), each filtering the other's pick from its options and showing each branch's last-commit date (`RelativeTime`) so the newest-first order is visible — `getBranchInfo` returns `branchDates` (branch name → ISO committed date, from `target { ... on Commit { committedDate } }` in the same refs query; optional, so a response cached before it existed just shows no dates). `BranchSelect` is memoized with `useMemo`d branch arrays, since the dialog re-renders per title/description keystroke and the branch lists can hold hundreds of items; its input is controlled (the selection arrives async, after the branch list loads) and `onOpenChange` clears the filter — selecting a branch sets the input to its name, which would otherwise leave the list filtered to just that branch — and resets abandoned filter text on close; the description is a tall (`rows={16}`) `components/MarkdownEditor.tsx` (the Write/Preview editor extracted from CommentComposer — controlled mode so parents can reset it; its Preview pane's `minH` tracks `rows` so switching tabs doesn't resize the editor; its optional `attachments` prop turns on pasting, dropping, and picking image/video files — see `docs/attachments.md`) in an `xl` dialog with `scrollBehavior="inside"`, plus a draft checkbox; `createPullRequest` POSTs `/repos/{repo}/pulls` and on success invalidates `["pullRequests", repo]` + `["myPullRequests"]` and navigates straight into the new PR's review screen via the normal open path. Clicking a queue row doesn't navigate — it opens `components/PullRequestPreview.tsx`, the panel beside the queue embedding the PR's Overview, its header carrying the repo slug, a "View on GitHub" link and one primary "Review changes" button that opens the full review screen **on its Changes tab** — the reviewer has just read the overview in this panel, so a second copy of it is not what that button promises. Which pane a PR opens on is the caller's choice (`ReviewTab`, in `lib/tabs/tabs.ts` so that a file in lib never imports a screen), and every other way in — sidebar rows, a double-click on a queue row — defaults to the overview. The pane lives in the PR's own tab (`ui.tab`), so `Review` is controlled by props and needs no key: going to another tab and back returns to the pane you left, while "Review changes" on an already-open PR still moves it to the diff. Those paths each record the PR as recently viewed via `App.tsx`. Both preview panels' headers match the queue header's height so the two line up across the top of the window. GitHub usernames get a small avatar next to them (`components/UserAvatar.tsx`, images from `avatars.githubusercontent.com/{login}`, with an initials fallback; the CSP in `index.html` allows `img-src https:` since markdown comments embed images from arbitrary hosts — badges, screenshots — plus `gh-asset:`, a main-process protocol (`main/github/assets.ts`) that fetches private-repo attachment images with the stored GitHub token: `lib/githubImages.ts` rewrites `github.com/user-attachments/assets/…` srcs (and expired signed `private-user-images.githubusercontent.com` URLs, by extracting the trailing attachment id) to `gh-asset://proxy?url=…` in `Markdown`'s img override; the handler allowlists exact attachment URLs, sends the token to github.com only, and follows the redirect to the short-lived signed S3 URL without the token (S3 rejects requests carrying both a signature and an Authorization header); the CSP also allows `media-src 'self' https: gh-asset:` for attached videos, and the same handler serves byte ranges because media playback demands them — see `docs/attachments.md`; scripts/styles/connections stay `'self'`-only); used on the Overview's author line and reviewer badges, and on the sidebar's rows. Review screen: a header bar (PR title, Open in GitHub, Re-analyse, Submit review, and Merge — no Back button, since closing the tab is the way out and the tab row above owns the window controls) over three tabs — **Overview** (PR description + GitHub metadata, like the PR's front page), **Changes** (file list left, diff viewer center), and **Review** (agent summary + Q&A chat, the home for all smart behaviour). Each tab panel owns its own data query and local state; TanStack Query dedupes shared keys. Theme lives in `src/renderer/src/theme.ts` (mono type for slugs/PR numbers/diff stats). The UI face is **Google Sans Flex**, bundled as a variable font (`@fontsource-variable/google-sans-flex`, imported in `main.tsx` beside JetBrains Mono) and set on the `heading`/`body` font tokens: fonts ship with the app rather than being fetched from Google, since the renderer's CSP allows no outside connections and a desktop app shouldn't wait on a CDN to paint. The bare package entry is the **weight axis alone** (~200KB over ten unicode subsets, of which only latin loads at runtime); the family carries five more axes — width, grade, roundness, slant, optical size — behind `full.css` and one file per axis, at several times the size, so reach for those only if a design actually uses them. The system stack stays behind it for glyphs its subsets don't carry. Colour mode is user-configurable — Light/Dark/System: `lib/colorMode.ts` persists the setting in localStorage and toggles `.dark`/`.light` on `<html>` (plus `color-scheme` for native controls), tracking OS changes live when set to System; `index.html` ships `class="dark"` (also the default) so first paint isn't a white flash. Syntax highlighting is shiki (`lib/highlighter.ts` — sync core + the JS regex engine, real VS Code TextMate grammars, ~30 languages imported statically; picked over highlight.js because hljs has no TSX grammar and rendered comments inside JSX multicoloured): every token span carries its dark AND light colour as CSS variables (`defaultColor: false`), and `lib/syntaxColors.ts` is the two rules that pick one via the `.dark`/`.light` class on `<html>` — colour mode switching never re-highlights — plus `syntaxBackground(pair, selector?)`, the same trick for the theme's own canvas: token colours are designed against their theme's background, so every highlighted-code surface paints the selected theme's `bg` rather than the app surface — `DiffLines` (on the `minW="max-content"` row containers, since the root box stops at the scrollport width and would leave a seam on wide diffs), `FileView`, `DiffView`'s scroll panes (so the area past the last row matches), `ReviewThreadCard`'s mini hunks, and `Markdown`'s fenced code blocks (via the `"& pre"` selector; inline code keeps its neutral chip — it has no token colours to match); diff chrome (add/del tints, hunk headers, comment bands, selection) keeps its semantic colours on top. **Which** two themes those are is user-configurable, one per colour mode (a good dark theme is rarely a good light theme, so the setting is a pair): `lib/syntaxThemeCatalog.ts` statically imports all 65 themes shiki bundles and derives every entry's id, label, and light/dark grouping from the theme object's own `name`/`displayName`/`type`, so adding one is an import plus a line and nothing about it is hand-maintained; only the pair in use is registered, via `loadThemeSync` on first use (0.1ms), so the other 63 cost bundle size and nothing else — 1.3MB of it, which is the real price of this feature and is paid off local disk, not a network. `lib/syntaxTheme.ts` holds the choice: two localStorage keys, a `useSyncExternalStore` hook like `diffViewMode`, and a snapshot object kept referentially stable because that hook loops forever otherwise; each mode falls back on its own, so a theme id dropped by a shiki upgrade can't cost the user their other choice. The pair is threaded **explicitly** through `parsePatch`/`highlightToLines` rather than read from a module global: the html depends on it, so a hidden read would make `parsePatch` return different output for the same arguments and leave every `useMemo` unable to declare the dependency. Defaults stay github-dark/github-light, so nothing changes for an existing user until they pick. The pickers are in the Appearance tab (`components/SyntaxThemePicker.tsx`), side by side (light first), each with a live preview rendered **in that theme** — its own background and foreground included, read from the registration's `editor.background`/`editor.foreground` since raw shiki registrations carry no top-level bg/fg — regardless of the app's current mode, since otherwise choosing a light theme while working in dark mode is blind. A change re-highlights every mounted diff (~100-180ms per 1000 lines), which is why the picker commits on select and never on hover. Lines over 2,000 chars render plain (`tokenizeMaxLineLength`): TextMate grammars go superlinear on giant lines — one 21KB markdown paragraph took ~1s per theme and froze PR switching for seconds. The accent colour is user-configurable: `lib/accent.ts` persists a Chakra palette name in localStorage and stamps it as `data-accent` on `<html>` (applied at boot in `main.tsx`); `theme.ts` has a globalCss rule per palette, so the whole app — portals included — follows. One exception, also in `theme.ts`: the button recipe's `outline` variant pins `colorPalette: "gray"`, because outline buttons are secondary actions (toolbars, Cancel) and a toolbar of accent-coloured outlines reads as a row of primary buttons; a button that carries meaning still sets its own `colorPalette` (yellow "Refresh to update", green merge, red Remove), and a style prop beats the recipe. Default is orange, matching the app icon; the picker lives in the settings dialog's Appearance tab (`components/AppearanceSettings.tsx`; the dialog is a wide (`maxW="4xl"`, fixed-height) two-column panel: a tinted left rail holding the "Settings" label and five vertical tabs — Appearance / Review / Models / Connections / GitHub — beside a single scrolling content column, with no footer since the close button and Esc do the same job. Every tab is built from `components/SettingsLayout.tsx` — `SettingsPanel` (tab heading + one-line description, and the bottom padding that clears the modal's edge, since padding on the dialog's scroll box doesn't show below the content), `SettingsGroup` (a bordered card whose rows are separated), and `SettingRow` (label + description on the left, the control on the right, or stacked underneath for wide controls) — so the tabs read as one screen instead of five forms. Connections is Claude only: the access choice as `components/LlmProviderSettings.tsx`'s three `RadioCard`s over a status line, then the Claude key. GitHub has its own tab (`components/GitHubSettings.tsx`) holding the two things GitHub needs side by side — the personal access token and the attachment session (`components/GitHubSessionSettings.tsx`, query `["attachmentAuth"]`, connect/disconnect). Both tabs' key fields are `components/SecretKeyRow.tsx`, one row per stored secret owning its own field, save/remove, and the result of the main process's live validation call). The Review tab (`components/ReviewSettings.tsx`) picks the "review personality" — the voice the analysis text is written in (standard/technical/non_technical/simplified/ste/grug/mentor/concise, `ReviewPersonality` in `shared/types.ts`; `ste` is ASD-STE100 Simplified Technical English — a controlled language with rules, not a tone, so its prompt block spells the rules out: one word one meaning, active voice, sentence-length caps, no noun clusters over three words): `lib/reviewPersonality.ts` persists it in renderer localStorage and `ReviewPanel` passes it with each `analyzePullRequest` call; the pipeline appends the matching voice block to the system prompt (`PERSONALITY_PROMPTS` in `analysis/pipeline.ts`, wording only — never what gets reported). It applies at analyse time, so already-cached analyses keep their original voice.
- **Attachment uploads** — a second, separate GitHub credential: a signed-in github.com session kept in its own window partition (`main/github/attachments.ts`), because GitHub has **no API for comment attachments**. Its `/upload/policies/assets` endpoint answers 422 to a personal access token and takes a `user_session` cookie alone, so nothing token-based can attach a file. See `docs/attachments.md`.
- **Typed IPC** — `src/shared/ipc.ts` defines the `IpcApi` interface. `src/main/ipc/router.ts` implements it; `src/preload/index.ts` exposes it as `window.api`. To add an IPC call, add a method to `IpcApi` and the compiler forces implementations on both sides. `src/shared/types.ts` is the single source of truth for data shapes.
