# PR Reviewer

A desktop app that makes code review easier. Think of it as replacing GitHub's "manila folder dump" of files with a guided, agent-assisted review experience.

## The problem

- PR descriptions are often obtuse, empty, or don't explain what the PR is trying to achieve.
- Reviewing means scrolling a big unordered file list. No signal for how data flows, which changes are critical, or where to start.
- No way to ask questions about the code without interrupting the author.

## What the app does

1. **Agent-generated summaries with lenses.** When a PR is opened, an agent produces toggleable views: overview ("what changed and why"), risks, behavior changes (what callers/users experience differently), and scope ("what's NOT in this PR").
2. **Logical change groups + reading order.** The diff is split into narrative chunks ("Change 1: new endpoint, 3 files. Change 2: mechanical rename, 12 files"), each with a risk badge, presented as a guided tour rather than a flat file list.
3. **Q&A agent with full repo context.** Ask questions about specific changes or the whole PR. The agent has the entire repo cloned locally (not just the diff), so it can answer "what does this helper do?" and "who else calls this?".

Planned beyond MVP:

- **Blast radius**: for changed functions/signatures, find callers *outside* the diff that weren't updated — that's where bugs live.
- **Risk-ranked file ordering**: new logic > modified logic > mechanical renames > generated files > lockfiles.
- **Pre-review agent pass**: candidate issues flagged as suggestions for the human to verify, not auto-comments.
- **Diff vs. intent check**: does the PR do what its description/ticket says, and nothing surprising?
- **Changes since last review**: for repeat rounds, summarize what changed and how comments were addressed.
- **Comment drafting**: draft inline comments locally (agent can help phrase), batch-submit as a real GitHub review.

Trust principle: every agent claim must link to the exact lines it's based on, so verification is one click. A reviewer who trusts a wrong summary rubber-stamps a bad PR.

## Architecture

Electron (chosen over Tauri because the Codex Agent SDK, Octokit, and git tooling are all Node/TypeScript — Electron's main process runs them natively; Tauri would need a Node sidecar).

- **Main process (Node)** — all the real work: GitHub API (Octokit), local repo clones under `~/.pr-reviewer/repos` (blobless: `--filter=blob:none`), diff parsing, the analysis pipeline, Codex Agent SDK sessions, SQLite persistence. Secrets never reach the renderer.
- **Renderer (React + Chakra UI v3)** — purely presentational. Welcome screen: no top bar — a full-height split. Left, `components/HomeSidebar.tsx`: four sections — **Repositories** (`components/RepositoryList.tsx` — each row shows the owner org/user's avatar (rounded, `UserAvatar` with the folder icon as fallback — also used when the repo has no slug) and, at its right edge, the repo's open-PR count (query `["openPrCounts"]` → `getOpenPullRequestCounts`, one aliased GraphQL query over all registered slugs; no token or an inaccessible repo just omits that entry) in a fixed slot that swaps to the remove button on hover; rows are drag-sortable via dnd-kit: whole-row drag with a 4px pointer-distance activation so plain clicks still select, the dragged row rendered in a `DragOverlay` — the row left behind dims as the placeholder and the default drop animation glides the overlay into its slot instead of snapping; the new order is set optimistically in the `["repositories"]` cache and persisted through the `reorderRepositories` IPC call, which reorders the registry by path, appends any paths the renderer didn't send, and returns the saved list), **Review requests** (open PRs where the user's review is requested, via `listReviewRequestedPullRequests` over IPC — GitHub search `review-requested:@me`, filtered in the main process to the registered repos' slugs; query key `["reviewRequests"]`; compact rows with the author's avatar (PR icon fallback) and a comment-count chip), **My pull requests** (same shape for `author:@me` via `listMyPullRequests`, query key `["myPullRequests"]`, comment-count chip, default PR icon; both sections share `searchOpenPullRequests` in `github/client.ts` — one GraphQL `search(type: ISSUE)` query returning every field a `PullRequest` needs, so a 20-hit search costs 1 request instead of 41; and `Welcome.tsx` invalidates both queries when repos are added/removed since the registry drives the filter), and **Recently viewed** (compact rows, not full cards — PRs the user has opened from any repo, stored in renderer localStorage via `lib/recentPrs.ts`, recorded by `App.tsx` on select, capped at 10 — enforced on read too, so older longer lists trim themselves — each row shows the author's avatar (PR-icon fallback), with a clear button in the section header) — and a footer anchored at the bottom with two actions: "Add repository" (folders picked via the native directory dialog) and Settings (opens the settings dialog). The main column is tabbed: **Open pull requests** (the selected repo's open PRs — rendered by `components/OpenPullRequestList.tsx`, which adds GitHub-style Author / Assignee / Sort dropdowns (user options show their GitHub avatar next to the login); filtering and sorting are client-side over the already-loaded list (`lib/prFilters.ts` — sorts: newest/oldest/most/least commented/recently/least recently updated; assignee includes "Assigned to nobody"), and the component is keyed by repo slug so filters reset on repo switch; `PullRequest` carries `assignees`/`createdAt`/`updatedAt` to power this) and **Analysed pull requests** (`components/AnalyzedPanel.tsx` — scoped to the selected repo, newest analysis first; cards drop the repo slug since the scope implies it); at the right end of the tab bar, a "New pull request" button (`components/NewPullRequestDialog.tsx`, shown when the selected repo has a slug, keyed by slug) opens a create dialog: `getBranchInfo` over IPC (query `["branchInfo", repo]`, `staleTime: 0` so a just-pushed branch always shows, fetched only while open) returns the repo's GitHub branches sorted newest commit first (a GraphQL `refs` query ordered by `TAG_COMMIT_DATE` desc — REST can't sort branches by activity — ≤500, with `defaultBranchRef` in the same call) and — via `getLocalCheckoutBranch` in `repo/local.ts` (`git symbolic-ref`, null on detached HEAD/unregistered) — the local checkout's current branch, pinned to the top of the list when it's on GitHub; head defaults to that branch when pushed and non-default (an info alert says to push first when it isn't), base to the default branch (the title is deliberately never prefilled), and untouched fields use a null-means-suggestion pattern so late-loading data still prefills — this also carries the repo's PR template into the description: `getBranchInfo` returns `pullRequestTemplate` (read from the default branch via the contents API, probing the conventional `.github`/root/`docs` `PULL_REQUEST_TEMPLATE.md` paths in parallel, best-effort), and the body falls back to it until the user types; head/base are non-portalled selects (portalled menus stack under the dialog), each filtering the other's pick from its options, with the checked item highlighted via `_checked` bg — `BranchSelect` is memoized with `useMemo`d branch arrays and lazy-mounts its menu, since the dialog re-renders per title/description keystroke and the branch lists can hold hundreds of items; the description is a `components/MarkdownEditor.tsx` (the Write/Preview editor extracted from CommentComposer — controlled mode so parents can reset it) plus a draft checkbox; `createPullRequest` POSTs `/repos/{repo}/pulls` and on success invalidates `["pullRequests", repo]` + `["myPullRequests"]` and navigates straight into the new PR's review screen via the normal open path. PR lists in the main column render `components/PullRequestCard.tsx`. Clicking any PR on the home screen (card or sidebar row) doesn't navigate — it opens `components/PullRequestPreview.tsx`, a right-hand panel embedding the PR's Overview, with a "View PR" button that opens the full review screen (that's the only home-screen path that navigates, records the PR as recently viewed via `App.tsx`, and the previewed card gets an accent-coloured border (`selected` on `PullRequestCard`)). GitHub usernames get a small avatar next to them (`components/UserAvatar.tsx`, images from `avatars.githubusercontent.com/{login}`, with an initials fallback; the CSP in `index.html` allows `img-src https:` since markdown comments embed images from arbitrary hosts — badges, screenshots — plus `gh-asset:`, a main-process protocol (`main/github/assets.ts`) that fetches private-repo attachment images with the stored GitHub token: `lib/githubImages.ts` rewrites `github.com/user-attachments/assets/…` srcs (and expired signed `private-user-images.githubusercontent.com` URLs, by extracting the trailing attachment id) to `gh-asset://proxy?url=…` in `Markdown`'s img override; the handler allowlists exact attachment URLs, sends the token to github.com only, and follows the redirect to the short-lived signed S3 URL without the token (S3 rejects requests carrying both a signature and an Authorization header); scripts/styles/connections stay `'self'`-only); used on PR cards and the Overview's author line and reviewer badges. Review screen: a header bar (Back, PR title, Open in GitHub, Re-analyse, Submit review, and Merge) over three tabs — **Overview** (PR description + GitHub metadata, like the PR's front page), **Changes** (file list left, diff viewer center), and **Review** (agent summary + Q&A chat, the home for all smart behaviour). Each tab panel owns its own data query and local state; TanStack Query dedupes shared keys. Theme lives in `src/renderer/src/theme.ts` (mono type for slugs/PR numbers/diff stats). Colour mode is user-configurable — Light/Dark/System: `lib/colorMode.ts` persists the setting in localStorage and toggles `.dark`/`.light` on `<html>` (plus `color-scheme` for native controls), tracking OS changes live when set to System; `index.html` ships `class="dark"` (also the default) so first paint isn't a white flash. The highlight.js palettes in `lib/syntaxColors.ts` are scoped per mode (github-dark / github-light). The accent colour is user-configurable: `lib/accent.ts` persists a Chakra palette name in localStorage and stamps it as `data-accent` on `<html>` (applied at boot in `main.tsx`); `theme.ts` has a globalCss rule per palette, so the whole app — portals included — follows. Default is green; the picker lives in the settings dialog's Appearance tab (`components/AppearanceSettings.tsx`; the dialog is vertical side tabs — Appearance / Review / API keys — with the key form in `components/ApiKeysSettings.tsx`). The Review tab (`components/ReviewSettings.tsx`) picks the "review personality" — the voice the analysis text is written in (standard/technical/non_technical/simplified/grug/mentor/concise, `ReviewPersonality` in `shared/types.ts`): `lib/reviewPersonality.ts` persists it in renderer localStorage and `ReviewPanel` passes it with each `analyzePullRequest` call; the pipeline appends the matching voice block to the system prompt (`PERSONALITY_PROMPTS` in `analysis/pipeline.ts`, wording only — never what gets reported). It applies at analyse time, so already-cached analyses keep their original voice.
- **Typed IPC** — `src/shared/ipc.ts` defines the `IpcApi` interface. `src/main/ipc/router.ts` implements it; `src/preload/index.ts` exposes it as `window.api`. To add an IPC call, add a method to `IpcApi` and the compiler forces implementations on both sides. `src/shared/types.ts` is the single source of truth for data shapes.

### Analysis pipeline

Analysis is **explicitly user-triggered** (an "Analyse PR" button — never automatic, so API credits are only spent on purpose). `analysis/pipeline.ts` fetches the PR detail + file patches from GitHub, builds one prompt (mechanical files like lockfiles get name/stats only; per-file and total patch-size caps), and makes a single Codex Messages API call to `Codex-opus-4-8` (plain `fetch`, forced tool use for validated structured output). The result is an `AnalysisResult`: a plain-English `summary`, `groups` (logical change groups in reading order, each with a story, risk level `attention`/`routine`/`mechanical`, and files — every changed file is guaranteed to land in some group), plus `risks`/`behaviorChanges` claims (each with a short nav `title` + full text) carrying `DiffAnchor`s (file + new-file line number, so every claim is verifiable against the diff) and `outOfScope`. Cached by repo + PR + head SHA in `~/.pr-reviewer/analyses.json` (disk-backed so paid analyses survive restarts; pruned to the 100 newest; SQLite later) — `getExistingAnalysis` checks the cache without ever calling the model. Later: streaming progress stages, a cheap model for mechanical classification, background pre-analysis of the review queue.

### Pre-review findings pass

Also explicitly user-triggered (a "Find issues" button in the Review tab). `analysis/findings.ts` runs an **agentic tool loop** — the model gets the same PR context as the analysis plus the repo tools (`read_file`/`grep_repo`/`list_files`/`git_log`, shared with the chat) and ends by calling a `report_findings` structured-output tool. The point of the tools is to look *beyond the diff*: the standout `blast_radius` category greps for callers of a changed function/signature and reports the ones the diff didn't update. Both providers report findings by **calling a `report_findings` tool** rather than via structured-output formatting — the API path is a manual tool loop (final round forces `report_findings` so it always commits); the Codex path (`runFindingsAgentQuery`) exposes `report_findings` as an MCP tool whose handler captures the input, because the SDK's `outputFormat: json_schema` returns empty when combined with MCP repo tools (a "success" result with no `structured_output`). Each finding has a `category`, `severity` (reuses `RiskSeverity`), title, markdown `body`, a single diff anchor (`path` + new-file `line`), and a ready-to-post `suggestion`. `findingsNormalize.ts` (pure, covered by `findingsNormalize.test.ts`) validates every finding against the diff: the path must be a changed file and the line must sit in its diff (snapped to the nearest in-diff line if the model was slightly off, dropped if unanchorable), then assigns a **stable id** = `sha1(category|path|line)` so a re-run of the same issue keeps its identity, and dedups/sorts high→low. Runs are cached by head SHA in `~/.pr-reviewer/findings.json`; the user's per-finding **resolutions** (`accepted`/`dismissed`) live separately in `finding-resolutions.json` keyed per PR, so they survive re-runs and never nag twice — the store joins them onto each finding as `resolution` at read time. IPC: `getFindings` (cache-only, null if never run), `findIssues` (runs the model; `force` skips the cache), `setFindingResolution` (`"open"` clears it). Trust principle: the agent proposes, the human disposes — nothing is posted to GitHub automatically.

## Current status (as of 2026-07-14)

Scaffold complete and verified: `pnpm typecheck` and `pnpm build` pass, `pnpm dev` opens the app. The UI is built with Chakra UI v3. Three things are real: (1) repository management — add local git repos via the native folder dialog, the GitHub slug is read from the `origin` remote, list persists to `~/.pr-reviewer/repositories.json`; (2) API-key settings — a gear on the welcome screen opens a dialog to enter a Codex API key and a GitHub token. Keys are validated with a live API call before saving, encrypted with Electron `safeStorage` (macOS Keychain), and stored in `~/.pr-reviewer/secrets.json`. Raw keys never cross IPC to the renderer; only status (set/not-set) does. A stored key that fails to decrypt (keychain locked, or access denied to that launch of the app) reports as not set but is NEVER deleted — decrypt failures are often transient, and deleting on one destroys the key permanently. (3) live open PRs and diffs — `github/client.ts` uses the stored token to fetch a repo's open pull requests (plain `fetch`, no Octokit), including per-PR line/file counts, and each PR's changed files with their patches (`/pulls/{n}/files`). PR **lists** are a single GraphQL query built from the shared `PR_FIELDS` fragment (`listReviewRequests` and `searchOpenPullRequests`): REST needed three requests per PR — summary, detail, reviews — so a 50-PR repo fired 101 requests and the home screen's three lists together fired ~185, which tripped GitHub's secondary rate limit (it caps concurrency, not just volume). Two mapping details are deliberate: `latestOpinionatedReviews` is GitHub's own newest-opinionated-review-per-reviewer, which already applies the rules `reviewStatusFrom` derives by hand from REST; and the comment count is `comments.totalCount` + the sum of `reviews.comments.totalCount`, **not** `totalCommentsCount`, which also counts review summary bodies and so would disagree with the PR detail's own count. GraphQL reports a bot author as `renovate`, REST as `renovate[bot]`, so `actorLogin` restores the suffix from `__typename` — without it a list row's avatar (`avatars.githubusercontent.com/{login}`) resolves to a different account than the PR it opens. Every call to api.github.com — REST and GraphQL — goes through `githubRequest` in `github/rateLimit.ts`: a 6-slot concurrency pool plus a retry that honours `Retry-After`/`x-ratelimit-reset` and pauses every other queued request while it waits (the pause is re-checked in a loop, since a sibling can extend it mid-wait; waits over 30s fail fast rather than block a UI query — deliberately under GitHub's "wait at least a minute" guidance, because a frozen UI reads as a hang, with the shared pause still keeping siblings off the API). GraphQL needs special handling because it reports a limit **in-band, with HTTP 200**: a spent points budget is typed `RATE_LIMITED`, while a secondary limit only says so in the error message — `hasGraphQlRateLimitError` matches both, scoped to the `errors` array so a PR titled "fix rate limit handling" can't be mistaken for a limit. Rate-limit wording is a cross-process contract: `shared/rateLimit.ts` owns `RATE_LIMIT_MESSAGE` and `isRateLimitMessage`, `githubFetch` normalises every shape to that one message (centrally, so all ~10 GraphQL call sites report it identically), and the renderer's query retry uses the same matcher to skip rate-limit errors — retrying a list would re-run its whole fan-out. GraphQL callers only throw when there's no usable `data`: partial errors come back with what did resolve and `null` for what didn't, which the mappers skip. inline confirm step to close, Reopen on closed PRs, hidden on merged, success invalidates every open-PR view including `["openPrCounts"]`; only rendered in the full review screen via the `showActions` prop, not the home-screen preview panel) — state/draft badge, base ← head branches (the base is editable in place on open PRs — `components/BaseBranchSelect.tsx`, a searchable Chakra `Combobox` over `getBranchInfo`'s branches (kept in newest-commit-first order; head branch excluded; lazy-loaded when opened) that calls `setPullRequestBase` → PATCH `/pulls/{n}` with `{base}`, then invalidates the detail/files/commits/reviewDecision/list queries since the base drives the whole comparison; closed/merged PRs show a plain badge), labels (each GitHub label's hex colour is mapped by hue to the nearest Chakra palette in `lib/labelColor.ts` and rendered as a themed `Badge` — low-saturation or extreme-lightness colours fall back to gray), reviewers, commit/file/line counts, dates — via a new `getPullRequest` detail call, plus the PR's conversation timeline, which merges (oldest-first) conversation comments (GitHub issue comments via `listPullRequestComments`, `/issues/{n}/comments`; All of this lives in `DiffLines` behind an optional `commenting` prop (`DiffCommenting`), so it works in both inline and split modes — in split view the two-column layout is cut into segments so thread/composer bands span the full pane width between them — and is only wired up in the Changes tab's all-changes view (commit-by-commit diffs number lines differently than the PR diff, and Review-tab `FileDiffCard`s stay read-only); **Review** (`components/ReviewPanel.tsx`) holds the agent summary + Q&A chat. The PR description renders as real GitHub-flavored markdown (`components/Markdown.tsx`, react-markdown + remark-gfm, plus rehype-raw → rehype-sanitize so inline HTML — which GitHub allows and bots like Notion's rely on — renders instead of showing as escaped text, with untrusted tags/attributes stripped); external links open in the system browser (main-process `setWindowOpenHandler`/`will-navigate` guard via `shell.openExternal`). (4) the analysis pipeline is real — the stored Codex key powers a single structured-output call (see "Analysis pipeline" above), exposed over IPC as `getAnalysis` (cache-only check, returns null if not analysed) and `analyzePullRequest` (runs the model; takes the review personality and an optional `force` that skips the cache read — the summary pane's footer has a small "Re-analyse" button that uses it). The model sometimes leaks the groups JSON into the summary string; `splitLeakedGroups` in pipeline.ts strips it (and uses the leaked copy as groups if the real field came back empty). The Review tab is the guided review: an "Analyse PR" empty state (analysis is never automatic), then a three-panel layout — left, `components/AnalysisNav.tsx` (a Changes-style nav list: Summary, then **Issues** (the findings pass — with a count badge of open findings), then each risk, behavior change, and reading-guide group as a clickable row; claims show their short `title`, groups get risk-colored dots); middle, `components/AnalysisDetail.tsx` renders the selected item — the summary pane (+ "Not in this PR" + analysed-commit footer), the findings pane, or a claim/group with its full text and the relevant files' diffs embedded as collapsible cards (`components/FileDiffCard.tsx`, mechanical groups start collapsed) plus clickable `file:line` anchor chips that scroll to the diff within the pane; right, `components/ChatPanel.tsx` is the full-height Q&A column. The **findings pane** (`components/FindingsPane.tsx`) is the pre-review agent pass's home: a "Find issues" empty state, then the list of candidate issues as `components/FindingCard.tsx` (severity + category badges, markdown body, the anchored file's diff, and the "Suggested comment" text) with two actions — **Add as draft comment** (creates a draft review comment from the suggestion at the finding's line via `addDraftComment`, then marks the finding `accepted` so it leaves the list; blocked when the run is outdated, since the anchor line may have moved) and **Dismiss** — plus a collapsed "Resolved" section of accepted/dismissed findings, each restorable; a Re-run button (force) sits in the header, and an outdated banner appears when the run is behind the PR's current commit. It requires an analysis to exist first (the whole Review tab is gated on that), matching the Analyse → find issues → verify → draft → submit flow. Selection state (`AnalysisSelection`, exported from AnalysisNav) lives in `ReviewPanel` and falls back to Summary if a selected item no longer exists. Risk badges: `components/RiskBadge.tsx`. The chat is a repo-aware agent (`agent/session.ts` + `agent/tools.ts`): the main process keeps one context per PR (rebuilt if the PR gets new commits) and disk-backed conversation histories in `~/.pr-reviewer/chats.json` (capped at 100 messages per PR; the newest 20 go to the model as context) — exposed as `getChatHistory` over IPC, which `ChatPanel` loads via `useQuery(["chatHistory", …])` with local overlay state for streaming/failed messages, so conversations survive restarts; context = the same capped diff the analysis uses (`buildPullRequestContext`, exported from pipeline.ts) + the cached analysis JSON; model `Codex-sonnet-5` (fast for interactive use — Opus stays on the one-shot analysis); the context block is marked `cache_control: ephemeral` so follow-up questions hit Anthropic's prompt cache. Answers stream: the main process parses the SSE stream and pushes `text_delta`s to the renderer via `webContents.send` on the `chatChunk` channel (see `ChatChunk`/`RendererEvents` in `shared/ipc.ts`; preload exposes `onChatChunk` returning an unsubscribe); `askQuestion` still resolves with the full answer, which replaces the streamed text as the authoritative copy. On top of that runs a client-side tool loop (max 8 rounds; the final round is sent without tools to force a text answer): the model can call `read_file`, `list_files`, `grep_repo`, and `git_log` (defined + executed in `agent/tools.ts` against the workspace clone, pinned to the PR's head SHA). `grep_repo` triggers `ensureHeadBlobs` first — a targeted backfill that lists the blobs missing from the reviewed commit's tree (`rev-list --missing=print`, which counts donor/alternate objects as present) and batch-fetches just those by id; it also runs during PR warm-up, so the first grep rarely waits. Within a question's loop, the full tool conversation is kept and a moving `cache_control` breakpoint sits on the newest tool results so each round re-reads the prefix from Anthropic's prompt cache; stored history stays plain text (tool activity is not replayed across questions). Tool failures are returned to the model as `is_error` tool results — it's prompted to fall back to diff-only answers and say what it couldn't verify. Diff rendering is shared: `lib/diffParser.ts` (patch → lines + syntax highlighting — each hunk is highlighted as two whole documents, old side (del+context) and new side (add+context), and the HTML is split back into lines with open spans closed/reopened at newlines, so multi-line constructs like `/** */` block comments and template literals keep their state across lines (per-line highlighting rendered their middles as code); hunks are never concatenated since the unseen gap between them could invalidate carried-over state; plus `buildSplitRows` which pairs del/add runs into side-by-side rows) feeds `components/DiffLines.tsx`, used by both the full-pane `DiffView` (Changes tab) and `FileDiffCard` (Review tab); file status letters/colors live in `lib/fileStatus.ts`. On the Changes tab, `DiffView` also fetches the file's full contents at the diff's commit from the workspace clone (`getFileAtCommit` over IPC → `readFileAtCommit` in `repo/workspace.ts`, null for binary/unavailable — everything degrades to diff-only; query `["fileAtCommit", repo, sha, path]`, infinite staleTime, excluded from persistence) and hands it to `DiffLines` as `DiffExpansion`, which buys three things: (1) add/context rows swap their html for slices of the whole highlighted file — per-hunk fragment highlighting mis-colors hunks that start mid-construct (e.g. inside a JSX tag); a text-equality guard between the file and the diff drops the upgrade when they disagree; (2) hunk headers grow an expand button (and a tail row after the last hunk) that splices the hidden gap in as `expanded: true` context rows via `computeGaps`/`expandLines` in diffParser — expanded rows can't host comments (GitHub can't anchor outside the diff) and count as hunk separators so comment selections can't cross them; (3) a "View file" toggle in the header renders the entire file (`components/FileView.tsx`, same mono font + syntax palette as diff rows) — it also works for too-large-to-diff files, and deleted files opt out of all three (no file at that commit). Diffs render inline or split (side-by-side): the global layout mode lives in `lib/diffViewMode.ts` (localStorage + `useSyncExternalStore` hook so every mounted diff reacts), picked via `components/DiffViewModeSelect.tsx` at the right end of the Review screen's tab bar (its menu is portalled — non-portalled it stacked under the diff panes' sticky elements) — Inline / Split / Dynamic, where Dynamic goes split per diff when its container is ≥960px (ResizeObserver in DiffLines). Nothing is mock anymore, and the chat can see beyond the diff via its repo tools.

The repo workspace is real (`repo/workspace.ts` + `repo/git.ts`): opening a PR fires a best-effort background warm-up (from the `getPullRequest` IPC handler) that maintains a **bare, blobless** clone per repo at `~/.pr-reviewer/repos/owner__repo.git` — no checkout; everything is read from the object store pinned to a commit (`showFile`/`listFiles`/`logForPath`), so all PRs of a repo share one clone and blobs download lazily on first read. The PR's head commit comes from `refs/pull/<n>/head` (works for fork PRs). Clones use the user's registered local checkout as an object donor (`--reference-if-able`) when available — the alternates link persists, so donor objects count as present forever. Warm-up finishes by backfilling the head commit's tree (`ensureHeadBlobs`): batch-fetch only the blobs missing after the donor and previously-fetched PRs are counted, so grep never has to lazy-fetch file-by-file and each PR only downloads its own delta. Auth: the GitHub token is injected per-command via `GIT_CONFIG_*` env vars (never written to the clone's config); every git command gets it because lazy blob fetches can happen on any read. Syncs are deduped in-flight and rate-limited (5-min TTL).

7. **Explain a selection (drag-to-explain) — next up.** On the Changes-tab diff, extend the existing drag-to-select-a-range affordance (today it only opens the comment composer) with an **"Explain"** action alongside "Comment". Dragging a range and choosing Explain hands the selected lines (path + line range) to the Q&A agent with a templated prompt and the selection quoted, so the answer references the exact lines (trust principle — one-click verification). The drag affordance and range math already exist in `DiffLines`/`DiffCommenting`; the new work is a second action on the selection plus the surfaces below. Read-only, lowest risk — build this one first.
   - **Primary surface: an inline "AI explanation" card anchored to the selected lines**, local-only (never posted to GitHub). Model it as a *third kind of anchored artifact* alongside real review threads and local draft comments: its own disk-backed store (`explanations.json`, keyed `repo#number`, mirroring `store/drafts.json`), each entry carrying id, path, line range, the answer markdown, the **head SHA it was generated against**, and a snapshot of the explained code. Render it as a distinct card under the anchor line (sparkle icon, an "AI explanation" label, an accent tint) so it never reads as a GitHub comment and gets no "post to GitHub" action.
   - **Coexists with your own comments.** `DiffCommenting` already carries real threads and drafts as separate bands; explanations become a third band, so the gutter "+" (leave your own comment) is untouched and a bot explanation and your own thread can sit on the same lines.
   - **Staleness — reuse the findings approach.** On a new commit, re-validate the anchor against the current diff (snap to the nearest in-diff line if it just moved); if the explained lines actually changed, keep the card but badge it "explains an earlier version" with one-click **Re-explain** (re-run against the new code) and **Dismiss**. Local-only, so be forgiving — badge, don't auto-delete.
   - **Two bridges out:** **Promote to draft comment** (one click turns an explanation into a draft review comment via `addDraftComment`, like findings' "Add as draft comment") and **Continue in chat** (opens the Review tab's `ChatPanel` seeded with the selection + explanation, via a small shared "pending question" hand-off — keeps v1 explanations single-shot while allowing a deeper conversation).
8. **Agent-authored PR changes (the foundation for editing).** Let the agent make real code changes to the PR from inside the tool, so the reviewer never has to drop to an editor or the CLI. Key pieces: (a) a **writable checkout** — today's review clone is bare + blobless (read-only, pinned to the head SHA), so this needs a separate per-PR git worktree/clone checked out to the PR head branch under `~/.pr-reviewer/…`, kept apart from the pinned read path so the review diffs stay stable; (b) **edit tools** for the agent (`write_file`/`apply_patch`, plus an optional sandboxed `run_command` for formatters/tests), either via the Codex Agent SDK's native file editing or by extending the manual tool loop in `agent/`; (c) **human-in-the-loop, always** — the agent produces a *proposed* changeset rendered as a diff (reuse `DiffView`) that the user reviews; nothing is committed or pushed automatically. Accept → commit to the local checkout; a separate, explicitly confirmed step pushes to the PR's head branch. Proposed edits are held locally (like draft review comments) so they survive restarts and can stack. (d) **Fork/permission handling** — pushing to a fork's head branch needs push access or the PR's "maintainer can modify" flag; detect this and degrade gracefully (offer push-to-a-new-branch, or an exportable patch) when it isn't allowed. Mirrors the existing drafts → Submit review pattern and the app's "confirm outward-facing actions" rule: the agent proposes, the human disposes and is the only one who triggers the push.
9. **Drag-to-modify + conversational edits.** Built on #8: the same diff drag affordance gains an **"Edit with agent"** action — describe a change in plain English scoped to the selected lines — and the chat can be asked to make changes conversationally ("rename this everywhere", "add a null check here"). Both funnel into #8's propose → review-diff → accept → commit → push flow. Drag-to-modify is the second of the two drag features (Explain in #7 first, since it's read-only and proves the selection → agent hand-off before any write path exists).

## Development

- `pnpm dev` — run the app. `pnpm typecheck` — both tsconfig projects. `pnpm build` — production build.
- `pnpm test` — Vitest, single run. `pnpm test:watch` — watch mode. Config in `vitest.config.ts` (deliberately a separate file from `electron.vite.config.ts`, which describes the three app bundles and is irrelevant to unit tests). Tests live beside the code as `*.test.ts`.
  - **Environment is `node`, not jsdom.** Everything covered so far is main-process code or a renderer module importing nothing but types. Component tests would need jsdom plus a Chakra/TanStack harness — a separate decision, deliberately not paid for yet.
  - **No `globals: true`** — import `describe`/`it`/`expect` from `vitest`. Both tsconfigs include `src/**/*`, so test files are typechecked by `pnpm typecheck`; explicit imports keep that working without adding a `types` entry to two tsconfigs.
  - **Module-level state must be reset per test.** `github/rateLimit.ts` keeps its pool and shared pause in module scope, so its tests call `vi.resetModules()` and re-`import()` in a helper rather than sharing one instance — otherwise a `pausedUntil` left behind stalls every later test.
  - **Use fake timers for backoff, real timers for concurrency.** `vi.advanceTimersByTimeAsync` drives the retry waits so the suite doesn't actually sleep; the concurrency test needs real timers because it has no backoff to skip.
  - Tests are worth only what they catch: the rate-limit and normalisation suites were checked by mutating the source (breaking the pause loop, the dedup, the snapping, the sort) and confirming a test went red for each. One weak test was found and rewritten that way.
- `pnpm format` — Biome formatter (write). `pnpm lint` — Biome linter (check only). `pnpm check` — Biome format + lint + import sorting (write). Config in `biome.json`: 2-space indent, double quotes, respects `.gitignore`.
- pnpm 10 blocks dependency install scripts; `electron` and `esbuild` are allowlisted in package.json (`pnpm.onlyBuiltDependencies`). If `node_modules/electron/dist` is missing after install, run `node node_modules/electron/install.js`.
- Branding: the app is "Reviewr" (`productName` in package.json). Icon source is `resources/icon.svg` → rendered to `resources/icon.png` (1024px, via `rsvg-convert`) → `build/icon.icns` (via `sips` + `iconutil`). The main process sets the dock icon at runtime (`setDockIcon` in `main/index.ts`). Because dev runs the stock Electron binary, `scripts/brand-dev-electron.sh` (postinstall) rewrites the bundled Electron.app's Info.plist name, swaps its icns, and re-signs it ad-hoc so the dock says "Reviewr" during `pnpm dev`.

## Testing policy — write the test first

**New logic is written test-first, red-green-refactor.** Not a suggestion: the burden is on the change to explain why it is exempt, not on the reviewer to ask for tests.

1. **Red.** Write the failing test and *run it*. A test that has never failed has not been shown to test anything.
2. **Green.** Write the least code that passes it.
3. **Refactor.** Clean up with the test as the safety net.

### What must be test-first

- Pure logic anywhere: parsing, normalisation, filtering, sorting, id/hash derivation, formatting.
- Main-process logic: anything in `main/` that isn't a thin pass-through to an API call.
- **Bug fixes, without exception.** Reproduce the bug as a failing test *before* the fix. That test is the deliverable — it is what stops the bug coming back.
- Anything that crosses the main/renderer boundary, since the compiler can't check a string that travels over IPC.

### What is exempt for now

- React components, until the harness in issue #17 exists (jsdom project, provider wrapper, typed `window.api` fake). Do not hand-roll a one-off jsdom setup to get around this — `lib/colorMode.ts` calls `window.matchMedia` at module scope, so it throws on import under jsdom without a setup file, and the 69-method `IpcApi` needs one shared fake rather than 35 ad-hoc ones.
- Thin wrappers whose whole body is one `fetch`/`git` call with no branching. Test the logic that reads their result instead.
- Electron lifecycle and window setup.

### Rules that make the tests worth having

- **Prove the test can fail.** Break the code, watch it go red, put it back. The one weak test found while writing the first suites — a shared-pause case that passed against the reverted fix — was found exactly this way and would have shipped false confidence otherwise.
- **Assert on behaviour, not incidental shape.** Pin the contract a caller depends on, not the exact wording of a log line.
- **Name the test as the claim it makes** — "promotes an orphaned reply to a root rather than losing it", not "works correctly".
- **Comment the non-obvious why**, in the same voice as the code: what breaks in the product if this behaviour regresses.
- **A test that needs the network, the clock, or a real repo is not a unit test.** Inject the seam (`vi.stubGlobal`, fake timers) or move the logic somewhere testable.
- Run `pnpm test` with `pnpm typecheck` and `pnpm lint` before committing.

## Conventions

- UI is Chakra UI v3 (`@chakra-ui/react` + `@emotion/react`, icons from `react-icons/lu`). Use Chakra components and style props, not CSS files. A Chakra MCP server is available for component examples and props.
- Data fetching goes through TanStack Query (`@tanstack/react-query`). The client lives in `renderer/src/lib/queryClient.ts` and wraps the app in `main.tsx` via `PersistQueryClientProvider`: the query cache persists to localStorage (24h max age, `pullRequestFiles`/`commitFiles`/`fileAtCommit` excluded — patches and file contents are too big for the ~5MB quota and cheap to refetch), so screens paint instantly from the last session while refetching in the background. The renderer cache is NOT the source of truth for analyses — the main process's disk cache is; `getAnalysis` stays correct after restarts because of it. Query keys in use: `["repositories"]`, `["pullRequests", slug]`, `["reviewRequests"]`, `["myPullRequests"]`, `["openPrCounts"]` (open-PR count per registered repo slug, for the sidebar's repo rows), `["branchInfo", repo]` (branches + local-checkout defaults for the new-PR dialog), `["repoMergeSettings", repo]` (the merge methods the repo allows — `components/MergeDialog.tsx` only offers those, defaulting to the first, so squash-only repos behave like GitHub), `["reviewDecision", repo, number]` (GitHub's GraphQL `reviewDecision`, fetched by MergeDialog for open PRs: while it's REVIEW_REQUIRED or CHANGES_REQUESTED — or still loading — the merge button is hidden entirely; null means no review requirement and a failed lookup fails open; SubmitReviewDialog invalidates it so an approval reveals the button), `["pullRequest", repo, number]`, `["pullRequestFiles", repo, number]`, `["pullRequestCommits", repo, number]`, `["commitFiles", repo, sha]`, `["fileAtCommit", repo, sha, path]` (full file text from the workspace clone, for the diff viewer), `["pullRequestComments", repo, number]`, `["pullRequestReviews", repo, number]`, `["reviewComments", repo, number]`, `["resolvedThreads", repo, number]`, `["viewedFiles", repo, number]` (paths the viewer marked as viewed, synced with GitHub's checkboxes), `["draftComments", repo, number]` (locally drafted review comments; source of truth is the main process's drafts.json), `["analysis", repo, number]`, `["findings", repo, number]` (pre-review agent findings — cache-only; the FindingsPane runs the model on demand and writes the result back with `setQueryData`), `["viewer"]` (the GitHub login the stored token belongs to), `["secretsStatus"]`. Mutations (add/remove repo, save/clear key) update the cache via `setQueryData` or `invalidateQueries` so dependent views (setup banner, PR list) refresh automatically.
- React components and functions inside them use the `function` keyword, not arrow functions.
- Component props: `interface Props {}` (or a descriptive exported name if they must be exported).
- No unnecessary comments; TODOs mark unimplemented stubs.
- Formatting and linting are handled by Biome (2-space indent, double quotes). Run `pnpm check` before committing.
- New logic is written test-first — see the Testing policy above.
- Tests are named `*.test.ts` and sit beside the file they cover.
- Conventional commits (`feat:`, `fix:`, `chore:`).
