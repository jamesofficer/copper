# PR Reviewer

A desktop app that makes code review easier. Think of it as replacing GitHub's "manila folder dump" of files with a guided, agent-assisted review experience.

## The problem

- PR descriptions are often obtuse, empty, or don't explain what the PR is trying to achieve.
- Reviewing means scrolling a big unordered file list. No signal for how data flows, which changes are critical, or where to start.
- No way to ask questions about the code without interrupting the author.

## What the app does

1. **Agent-generated summaries with lenses.** When a PR is opened, an agent produces toggleable views: overview ("what changed and why"), risks, behavior changes (what callers/users experience differently), and scope ("what's NOT in this PR").
2. **Logical change groups + reading order.** The diff is split into narrative chunks ("Change 1: new endpoint, 3 files. Change 2: mechanical rename, 12 files"), each with a risk badge, presented as a guided tour rather than a flat file list.
3. **Q&A agent with full repo context.** Ask questions about specific changes or the whole PR. The agent has the entire repo cloned locally (not just the diff), so it can answer "what does this helper do?" and "who else calls this?".

Planned beyond MVP:

- **Blast radius**: for changed functions/signatures, find callers *outside* the diff that weren't updated — that's where bugs live.
- **Risk-ranked file ordering**: new logic > modified logic > mechanical renames > generated files > lockfiles.
- **Pre-review agent pass**: candidate issues flagged as suggestions for the human to verify, not auto-comments.
- **Diff vs. intent check**: does the PR do what its description/ticket says, and nothing surprising?
- **Changes since last review**: for repeat rounds, summarize what changed and how comments were addressed.
- **Comment drafting**: draft inline comments locally (agent can help phrase), batch-submit as a real GitHub review.

Trust principle: every agent claim must link to the exact lines it's based on, so verification is one click. A reviewer who trusts a wrong summary rubber-stamps a bad PR.

## Architecture

Electron (chosen over Tauri because the Claude Agent SDK, Octokit, and git tooling are all Node/TypeScript — Electron's main process runs them natively; Tauri would need a Node sidecar).

- **Main process (Node)** — all the real work: GitHub API (Octokit), local repo clones under `~/.pr-reviewer/repos` (blobless: `--filter=blob:none`), diff parsing, the analysis pipeline, Claude Agent SDK sessions, SQLite persistence. Secrets never reach the renderer.
- **Tab navigation** — the app holds several things open at once, as a row of tabs across the top (`components/TabBar/`). A reviewer jumping between three PRs and a working tree does not have to close one to look at the next. `lib/tabs/tabs.ts` is the state: a `Tab` is a discriminated union of the **queue** tab, a **pull request** tab, and a **local changes** tab (one per worktree; not wired up yet, so Current changes is still a tab inside the queue). Every change is a pure `(state, args) => state` function, tested in the node environment; `lib/tabs/useTabs.ts` is the Zustand store over them, persisted to localStorage so the row survives a restart. Zustand rather than the `useSyncExternalStore` pattern the settings stores use (issue #49), for the selectors: a PR tab records the text in its file filter, and the tab bar must not render again for each key press. Rules worth knowing: a tab's id comes from its content (`pr:owner/repo#7`), so opening a PR that is already open focuses that tab and shows the pane the caller asked for rather than adding a second tab; the **queue tab is pinned first and cannot be closed**, because it is the way back to the lists; closing the active tab activates the tab to its right, then the left at the end of the row; the `PullRequest` in a tab is a copy taken when it opened and is only ever read to draw the tab, so the query cache stays the one source of truth for what the screen shows; and a stored tab the app cannot parse is dropped on its own rather than failing the whole row. **There is one queue tab, not one per repository** — picking a repository points that tab at it and closes nothing, which is the whole win: the PRs you had open stay open. `App.tsx` therefore holds only what the queue needs (the active repository path, the preview PR, the settings dialog) and the tabs store holds the rest. Shortcuts in `lib/hotkeys.ts`: Cmd/Ctrl+W closes, Control+Tab and Control+Shift+Tab move along the row (Control on macOS too, since Command+Tab belongs to the OS), and Cmd/Ctrl+1–9 select by position with 9 meaning the last tab. `MAX_LIVE_TABS` and `pickLiveTabIds` are in place for keeping more than one tab in the DOM, but **App still mounts only the active tab**: switching repaints from the query cache at once, and scroll position resets. Chromium clears `scrollTop` when an element goes to `display: none`, so keep-alive has to keep the layout box (`visibility: hidden`, or `content-visibility: hidden`) — measure which one holds the scroll in the running app before writing that code.
- **Renderer (React + Chakra UI v3)** — purely presentational. Below the tab row, a full-height split. Left, `components/HomeSidebar.tsx`, which `App.tsx` renders **beside every tab**, so a reviewer can jump straight from one PR to the next. Its PR rows always open the PR itself — no preview step, since picking a PR from a list you deliberately keep in the sidebar means you want to read it; the preview panel is for the **Repositories** flow, where the main column lists a repo's open PRs and you may be skimming. Picking a repository leaves the review screen for the home screen's open-PR list (and drops any preview, which belonged to the old repo). The row for the PR being reviewed is marked (`selected` on `SidebarPullRequestRow`, the same style as the active repo). Because the sidebar now outlives the home screen, the state it needs sits in `App.tsx`: the registry and its three mutations in `lib/useRepositoryActions.ts` (shared with the home screen's empty-state "Add repository"), the recently-viewed list, the preview PR, and the settings dialog. It can be hidden — useful when reading a wide diff: `lib/sidebarCollapsed.ts` (localStorage + `useSyncExternalStore`, so both screens react), hidden with the panel button right of Settings in the sidebar's header, brought back with `components/ShowSidebarButton.tsx` at the left of either screen's top bar, and toggled with **Cmd+B / Ctrl+B** — the app's keyboard shortcuts go through TanStack Hotkeys (`@tanstack/react-hotkeys`, alpha; `HotkeysProvider` in `main.tsx`, `useHotkey` in `App.tsx`), with the binding and its platform-aware tooltip label in `lib/hotkeys.ts`: the library's `Mod` resolves to Command on macOS and Control elsewhere, and `formatForDisplay` writes it as "⌘ B" or "Ctrl+B" for the two buttons' tooltips; that bar also takes over the macOS traffic-light padding while the sidebar is away. The sidebar has five sections, each collapsible (a Chakra `Collapsible` per section — the chevron sits in the heading trigger, section-level actions stay outside it so buttons aren't nested, and the collapsed set persists in localStorage via `lib/sidebarSections.ts`, keyed by section id so a newly added section starts open; headings carry a count so a collapsed section still says how much is in it) — **Repositories** (`components/RepositoryList.tsx` — each row shows the owner org/user's avatar (rounded, `UserAvatar` with the folder icon as fallback — also used when the repo has no slug) and, at its right edge, the repo's open-PR count (query `["openPrCounts"]` → `getOpenPullRequestCounts`, one aliased GraphQL query over all registered slugs; no token or an inaccessible repo just omits that entry) in a fixed slot that swaps to the remove button on hover; rows are drag-sortable via dnd-kit: whole-row drag with a 4px pointer-distance activation so plain clicks still select, the dragged row rendered in a `DragOverlay` — the row left behind dims as the placeholder and the default drop animation glides the overlay into its slot instead of snapping; the new order is set optimistically in the `["repositories"]` cache and persisted through the `reorderRepositories` IPC call, which reorders the registry by path, appends any paths the renderer didn't send, and returns the saved list), **Review requests** (open PRs where the user's review is requested, via `listReviewRequestedPullRequests` over IPC — GitHub issue search `review-requested:@me`, filtered in the main process to the registered repos' slugs before the per-PR detail fetches; query key `["reviewRequests"]`; compact rows with the author's avatar (PR icon fallback) and a comment-count chip), **My pull requests** (same shape for `author:@me` via `listMyPullRequests`, query key `["myPullRequests"]`, comment-count chip, default PR icon; both sections share `searchOpenPullRequests` in `github/client.ts`, and `Welcome.tsx` invalidates both queries when repos are added/removed since the registry drives the filter), **Analysed** (`components/AnalyzedSidebarList.tsx` — PRs the user has run the analysis on, newest first, across every repo (not scoped to the selected one, unlike the old tab) and capped at the 7 newest since the section shares the sidebar with four others; the main process's cache only stores repo/number/sha, so each row fetches live detail through `peekPullRequest` under the shared `["pullRequest", …]` key, showing a skeleton until it lands; the row's meta is the analysis's age, turning orange when the analysis was run against a commit that's no longer the head), and **Recently viewed** (compact rows, not full cards — PRs the user has opened from any repo, stored in renderer localStorage via `lib/recentPrs.ts`, recorded by `App.tsx` on select, capped at 7 — enforced on read too, so older longer lists trim themselves — each row shows the author's avatar (PR-icon fallback), with a clear button in the section header) — and a footer anchored at the bottom with two actions: "Add repository" (folders picked via the native directory dialog) and Settings (opens the settings dialog). The main column is the **review queue**: a header naming it (with a refresh button, a compact New-pull-request trigger, and `components/QueueActionsMenu.tsx` — open the repo on GitHub, add a repository, Settings, since the sidebar that also offers the last two can be hidden), then three tabs carrying counts — **Open (n)**, **Issues (n)**, and **Changes (n)**. On the two list tabs the queue is a narrow, drag-resizable column (`lib/usePanelWidth.ts`, key `reviewQueueWidth`, 380–700px, default 480) with the preview panel filling the rest of the window beside it — a list read top to bottom doesn't need the width, and the thing being read does; on the Changes tab the split is different again: the tab bar caps a narrower file-list column (`localChangesFileListPanel`, 220–600px, default 300) and the diff fills the rest of the window from directly under the top bar, so nothing sits in a strip of empty space above the diff. That is why the queue's chrome is two components — `components/QueueHeader.tsx` is the full-width top bar, `components/QueueTabs.tsx` the tab triggers, placed over whichever column the tab in question uses. Everything in the column shares a `4` gutter, rows included, so the tabs, the filter box and the row text all line up. With nothing picked on a list tab, the space beside the queue holds a one-line placeholder rather than letting the column stretch. Current changes is a review of the selected repo's *uncommitted* work with real git actions (for reviewing an agent's slice before it becomes a PR, then committing it): `components/LocalChangesColumn.tsx` (the file list, filter and commit box) beside `components/LocalChangesPane.tsx` (the diff), with `lib/useLocalChanges.ts` holding the state they share — the two are separate components because the tab bar caps the column and not the window, so they can't be one. It is the Changes-tab layout minus every PR-only affordance (no commenting, viewed state, or context expansion). The file list splits into **Staged** and **Unstaged changes** groups the way git sees them — a partially staged file appears in both, which is git's model, not a bug; staged rows' names tint green. Rows reveal hover actions (unstage on staged rows; stage and discard on unstaged ones — `FileList`'s optional `rowActions`, drawn in the diff-counts slot), each group has a bulk button whose label says "shown" instead of "all" while a filter is active (`lib/localChangesSelection.ts`, which also carries a staged rename's old path along so unstaging can't leave the deletion half behind), `components/CommitComposer.tsx` under the list commits exactly the index — never "commit -a", so the Staged group is the record of what's about to be committed (Cmd/Ctrl+Enter; success toast carries the short SHA) — and discard goes through `components/DiscardChangesDialog.tsx`, a real confirmation dialog since it's the app's one irreversible action: tracked paths revert to the index, untracked ones are deleted outright, and the dialog is told which are untracked by the data (`LocalChanges.untracked`), never guessed from status letters. The tab also reads the branch's **committed** history, through the same affordance the PR Changes tab uses: the same `CommitsPanel` at the foot of the column (over `CommitList`, generalized with `allLabel`/`newestFirst` — here the top row says "Uncommitted changes" rather than "All changes", the panel's `hint` names the base while nothing is picked, and git log is already newest first). Picking a commit points the whole tab at it — a flat file list of what it changed, its diffs, and its own message above them (`components/CommitMessageHeader.tsx`) — read-only, with the commit box **disabled rather than removed**: a commit box under a past commit's files reads as an offer to change that commit, and unmounting it made the panels above it jump every time a commit was picked. `listLocalCommits` (`repo/commits.ts`) picks the range rather than taking one: the trunk first (`origin/HEAD`, else the well-known names) so `trunk..HEAD` is exactly the work done on this branch, then `@{upstream}` — which is what answers on the trunk itself, making the list the unpushed commits — and recent history (capped at 200) when the checkout is level with both, with `base` returned so the heading can say "vs origin/main" instead of showing a number with no unit. `getLocalCommitFiles` diffs a merge against its first parent (`-m --first-parent`): git's combined diff is a different format, and the question is what the commit brought in. Both go through the same `parseGitDiff` the uncommitted lists use, so a commit's files render through the existing `FileList`/`DiffView` unchanged. Queries `["localCommits", path]` (staleTime 0, refetch on focus — new commits land while the app runs) and `["localCommitFiles", path, sha]` (infinite staleTime, since a commit is immutable); neither is persisted, and a selected commit the list no longer holds (amended, rebased away) drops back to the uncommitted work rather than leaving an empty pane. Reads come from `getLocalChanges(repoPath)` over IPC → `main/repo/changes.ts`, which diffs the index against HEAD (`diff --cached`; the empty tree only when the repo has no commits yet) and the working tree against the index as separate diffs, diffs each untracked file against `/dev/null` (a small worker pool caps process spawn), and parses the output into the same `PullRequestFile[]` shape the diff UI already renders — binary files and patches over 1MB get `patch: null` (the viewer's existing "too large" state), and header paths handle git's C-quoting plus the trailing tab it appends to unquoted spaced paths. Writes (`stageFiles`/`unstageFiles`/`discardChanges`/`commitChanges`) are wrapped by `main/ipc/localChanges.ts`: every mutation first checks the path is a registered repo or one of its listed worktrees, and writes are serialized per checkout because git holds one index lock. In `changes.ts` itself, every git call runs with `GIT_LITERAL_PATHSPECS=1` so a filename like `pages/[id].tsx` can never glob onto other files; unstage falls back to `rm --cached` in an unborn repo; discard splits paths by `ls-files`, restoring tracked ones and `clean -f` (never `-x`, so ignored files survive) on the rest; and failures surface git's stderr/stdout so hook output and "nothing to commit" reach the user's error toast. No token, no network — it's the one view that works on a repo with no slug. The tab label's count comes from the cheap `getLocalChangeCount` (porcelain status only — no patches are built just for the badge; query `["localChangeCount", repoPath]`, always-on for the selected repo), while the detailed `["localChanges", repoPath]` query (options for both exported from `lib/useLocalChanges.ts`) runs only while the tab is showing; both are `staleTime: 0` + refetch-on-focus since the working tree moves constantly, and never persisted; while the tab is showing, the top bar's right side swaps the New-PR button for a refresh button refetching those queries. The checkout's branch name sits at the **head of the file-list column**, under the tabs and over the files — it belongs with the files it decides, not in the window's top bar (`components/BranchLabel.tsx`). When the repo has linked git worktrees (agents often work in several at once), that branch label becomes a worktree switcher (`components/WorktreeSelect.tsx`, fed by `listWorktrees` over IPC → `git worktree list --porcelain -z` in `repo/local.ts`, skipping bare/prunable entries; query `["worktrees", repoPath]`, never persisted): picking a worktree points the whole tab — file list, diffs, branch label, count — at that checkout's path (`useLocalChanges` takes the whole `WorktreeSelection` — the column draws the picker itself — and every query was already keyed by path), and the selection lives in `Welcome.tsx`, only honoured while it names a listed worktree so a removed worktree or a repo switch falls back to the registered checkout. The Open tab is the selected repo's open PRs — rendered by `components/OpenPullRequestList.tsx` as rows, not cards (`components/QueueRow.tsx` is the shared shell — icon, truncated title, a trailing slot, a meta line and a footer line, hairline-separated, the selected row marked with an accent bar down its left edge; `components/PullRequestQueueRow.tsx` fills it in: the PR icon tinted by **state** since the rows carry no state badge — grey draft, green open, purple merged, red closed, from `prStateMeta` exported by `PrStateBadge.tsx` so the icon and the badge can't disagree about whether a PR is merged or merely closed (the row paints open green where the badge uses blue: GitHub's colour, and a column of blue icons reads as links). The summary type has no `state`/`merged`, which is honest — every list feeding these rows asks GitHub for open PRs only, so a row is a draft or it's open — then `+adds −dels`, `#number author · n commits · n files` with the comment chip, and the repo slug over a relative time. `PullRequest` carries an optional `commits` (optional because lists persisted before it existed don't have it, and a row would rather leave the segment out than claim zero)). Above the rows sits `components/QueueFilterBar.tsx`: an always-there filter box (`filterByText` in `lib/listFilters.ts` — title, author, or the number with or without its "#") over the Author / Assignee / Sort dropdowns, which hide behind a sliders button because the column is too narrow for three selects side by side and the text box is what a reviewer reaches for nine times in ten; a dropdown away from its default puts a dot on that button, so a filter can't hide rows while the control that set it is out of sight. Filtering and sorting stay client-side over the already-loaded list (sorts: newest/oldest/most/least commented/recently/least recently updated; assignee includes "Assigned to nobody"), and the component is keyed by repo slug so filters reset on repo switch. Each row's time follows the sort (`sortTimeField`) — created for the "newest" sorts, updated for the two update sorts — since "updated 5m ago" on a row in a list ordered by opening date reads as a broken sort. One fetch returns the `OPEN_PULL_REQUEST_LIMIT` (50, in `shared/types.ts`, used by the GraphQL query itself) most recently updated open PRs; unlike the issue list, the queue deliberately doesn't say so on screen — a standing notice above the rows a reviewer reads all day earns its space less than the rows do; the **Issues** tab is the same shape for the repo's open GitHub issues — read-only in v1 (`components/RepoIssueList.tsx` → `RepoIssueQueueRow.tsx` (the same `QueueRow` shell, with the issue's labels in the slot the PR rows give the repo slug — labels are the one thing that tells two same-shaped issues apart at a glance) → `RepoIssuePreview.tsx` wrapping `RepoIssueOverview.tsx`, which needs only two queries where `PullRequestOverview` needs six: an issue has no reviews, inline threads or commits, so its conversation is a plain oldest-first comment list). Names carry a **`RepoIssue`** prefix throughout because "issue" already means *a finding from the analysis agent* everywhere else in this app (`lib/issues.ts`, `IssuePane.tsx`, the `findIssues` IPC method). `listRepoIssues` is GraphQL, deliberately: REST's `/repos/{repo}/issues` returns pull requests mixed in, while the `issues` connection excludes them by construction. Comments are free — `listIssueComments` in `github/client.ts` (renamed from `listPullRequestComments`, which always hit `/issues/{n}/comments`) serves a PR's conversation and a real issue's alike, since GitHub numbers both in one sequence per repo. Reactions are off on issue comments (`showReactions={false}` on `CommentCard`) until `listReactions` grows a `repository.issue(number:)` twin; its `setReaction` half already works, taking a bare node id. The tab's list query is gated on the tab being open, so a user who never opens Issues never spends the request; its trigger's count is simply the loaded list's length, so it appears once the tab has been visited and never costs a request of its own (the Changes count is a cheap local git call, and Open's is the loaded PR list). Its preview state lives in `Welcome.tsx` rather than `App.tsx`: it has no full screen to survive a trip to, and a guard on the repo slug drops a panel left over from the previous repo without an effect to clear it. The two lists share `lib/listFilters.ts` (`filterByPeople`/`sortListItems`, generic over a `Listable` shape both types satisfy) and `components/FilterSelect.tsx`; the two overviews share their whole layout — `components/ReadingPanel.tsx` owns the shape both reading panels take (container-queried hero over reading column + rail, and the measurements that go with it), with `RepoIssueHero`/`RepoIssueSidebar` mirroring the PR's pair: same title size and weight, same mono meta line (an issue has no branches or diff, so its line carries the comment count — and only once the comments have loaded, since a count that starts at zero and jumps reads as an issue nobody replied to), same rail sections minus the ones an issue has no answer for (no review status, no reviewers). One component rather than two copies of one grid, because the two are meant to feel like the same screen with different content and that only survives if the measurements live in one place. They also share `RailSection`, `UserList`, `SectionHeading`, `LabelBadges`, `OpenedUpdatedLine`, and `PanelState`'s loading/error states. The issue list pages 25 at a time — `components/ListPagination.tsx` over the *filtered* list, so the dropdowns still cover everything loaded; any filter change resets to page 1, and the page number is clamped on render rather than stored outright, so a refetch that returns fewer issues can't strand the list past its own end. One fetch returns the `REPO_ISSUE_LIMIT` (50, in `shared/types.ts` because both processes need it) most recently updated open issues, and the list says so once it is that full: filters run over the loaded slice, so a silent cap would let "no issues match" read as "this repo has no such issue". A comments fetch that fails is reported in place — `PanelSectionError` in `PanelState.tsx`, where the conversation would have been, with a Retry — never as a toast: every toast in this app belongs to a write the user triggered, and a toast for a failed read is gone in seconds while the gap it described stays on screen reading as "nobody replied". The pull-request overview uses the same notice, and no longer hides its whole conversation (reviews, commits and the comment box included) when only the comments failed. The closed-state badge only claims "completed" when GitHub says `completed` — issues closed before 2022 carry no reason at all, and "Closed" is the honest reading of that. In the queue's header, a "New pull request" trigger (`components/NewPullRequestDialog.tsx`, shown when the selected repo has a slug, keyed by slug; its `compact` prop makes the trigger an icon button, since the queue header has no room for a labelled one) opens a create dialog: `getBranchInfo` over IPC (query `["branchInfo", repo]`, `staleTime: 0` so a just-pushed branch always shows, fetched only while open) returns the repo's GitHub branches sorted newest commit first — a GraphQL `refs` query (REST can't sort branches by activity at all) paged alphabetically to ≤500 with `defaultBranchRef` in the same call, then **sorted by `committedDate` in the main process**: GitHub's only date-ish `RefOrder` field is `TAG_COMMIT_DATE` and for `refs/heads` it's silently ignored, so asking for it DESC just returns reverse alphabetical (branches with no commit date sort last; a repo over the 500 cap is truncated by name before the sort sees it) and — via `getLocalCheckoutBranch` in `repo/local.ts` (`git symbolic-ref`, null on detached HEAD/unregistered) — the local checkout's current branch, pinned to the top of the list when it's on GitHub; head defaults to that branch when pushed and non-default (an info alert says to push first when it isn't), base to the default branch (the title is deliberately never prefilled), and untouched fields use a null-means-suggestion pattern so late-loading data still prefills — this also carries the repo's PR template into the description: `getBranchInfo` returns `pullRequestTemplate` (read from the default branch via the contents API, probing the conventional `.github`/root/`docs` `PULL_REQUEST_TEMPLATE.md` paths in parallel, best-effort), and the body falls back to it until the user types; head/base are non-portalled searchable `Combobox`es (portalled menus stack under the dialog), each filtering the other's pick from its options and showing each branch's last-commit date (`RelativeTime`) so the newest-first order is visible — `getBranchInfo` returns `branchDates` (branch name → ISO committed date, from `target { ... on Commit { committedDate } }` in the same refs query; optional, so a response cached before it existed just shows no dates). `BranchSelect` is memoized with `useMemo`d branch arrays, since the dialog re-renders per title/description keystroke and the branch lists can hold hundreds of items; its input is controlled (the selection arrives async, after the branch list loads) and `onOpenChange` clears the filter — selecting a branch sets the input to its name, which would otherwise leave the list filtered to just that branch — and resets abandoned filter text on close; the description is a tall (`rows={16}`) `components/MarkdownEditor.tsx` (the Write/Preview editor extracted from CommentComposer — controlled mode so parents can reset it; its Preview pane's `minH` tracks `rows` so switching tabs doesn't resize the editor; its optional `attachments` prop turns on pasting, dropping, and picking image/video files — see "Attachments" below) in an `xl` dialog with `scrollBehavior="inside"`, plus a draft checkbox; `createPullRequest` POSTs `/repos/{repo}/pulls` and on success invalidates `["pullRequests", repo]` + `["myPullRequests"]` and navigates straight into the new PR's review screen via the normal open path. Clicking a queue row doesn't navigate — it opens `components/PullRequestPreview.tsx`, the panel beside the queue embedding the PR's Overview, its header carrying the repo slug, a "View on GitHub" link and one primary "Review changes" button that opens the full review screen **on its Changes tab** — the reviewer has just read the overview in this panel, so a second copy of it is not what that button promises. Which pane a PR opens on is the caller's choice (`ReviewTab`, in `lib/tabs/tabs.ts` so that a file in lib never imports a screen), and every other way in — sidebar rows, a double-click on a queue row — defaults to the overview. The pane lives in the PR's own tab (`ui.tab`), so `Review` is controlled by props and needs no key: going to another tab and back returns to the pane you left, while "Review changes" on an already-open PR still moves it to the diff. Those paths each record the PR as recently viewed via `App.tsx`. Both preview panels' headers match the queue header's height so the two line up across the top of the window. GitHub usernames get a small avatar next to them (`components/UserAvatar.tsx`, images from `avatars.githubusercontent.com/{login}`, with an initials fallback; the CSP in `index.html` allows `img-src https:` since markdown comments embed images from arbitrary hosts — badges, screenshots — plus `gh-asset:`, a main-process protocol (`main/github/assets.ts`) that fetches private-repo attachment images with the stored GitHub token: `lib/githubImages.ts` rewrites `github.com/user-attachments/assets/…` srcs (and expired signed `private-user-images.githubusercontent.com` URLs, by extracting the trailing attachment id) to `gh-asset://proxy?url=…` in `Markdown`'s img override; the handler allowlists exact attachment URLs, sends the token to github.com only, and follows the redirect to the short-lived signed S3 URL without the token (S3 rejects requests carrying both a signature and an Authorization header); the CSP also allows `media-src 'self' https: gh-asset:` for attached videos, and the same handler serves byte ranges because media playback demands them — see "Attachments" below; scripts/styles/connections stay `'self'`-only); used on the Overview's author line and reviewer badges, and on the sidebar's rows. Review screen: a header bar (PR title, Open in GitHub, Re-analyse, Submit review, and Merge — no Back button, since closing the tab is the way out and the tab row above owns the window controls) over three tabs — **Overview** (PR description + GitHub metadata, like the PR's front page), **Changes** (file list left, diff viewer center), and **Review** (agent summary + Q&A chat, the home for all smart behaviour). Each tab panel owns its own data query and local state; TanStack Query dedupes shared keys. Theme lives in `src/renderer/src/theme.ts` (mono type for slugs/PR numbers/diff stats). The UI face is **Google Sans Flex**, bundled as a variable font (`@fontsource-variable/google-sans-flex`, imported in `main.tsx` beside JetBrains Mono) and set on the `heading`/`body` font tokens: fonts ship with the app rather than being fetched from Google, since the renderer's CSP allows no outside connections and a desktop app shouldn't wait on a CDN to paint. The bare package entry is the **weight axis alone** (~200KB over ten unicode subsets, of which only latin loads at runtime); the family carries five more axes — width, grade, roundness, slant, optical size — behind `full.css` and one file per axis, at several times the size, so reach for those only if a design actually uses them. The system stack stays behind it for glyphs its subsets don't carry. Colour mode is user-configurable — Light/Dark/System: `lib/colorMode.ts` persists the setting in localStorage and toggles `.dark`/`.light` on `<html>` (plus `color-scheme` for native controls), tracking OS changes live when set to System; `index.html` ships `class="dark"` (also the default) so first paint isn't a white flash. only the pair in use is registered, via `loadThemeSync` on first use (0.1ms), so the other 63 cost bundle size and nothing else — 1.3MB of it, which is the real price of this feature and is paid off local disk, not a network. `lib/syntaxTheme.ts` holds the choice: two localStorage keys, a `useSyncExternalStore` hook like `diffViewMode`, and a snapshot object kept referentially stable because that hook loops forever otherwise; each mode falls back on its own, so a theme id dropped by a shiki upgrade can't cost the user their other choice. The pair is threaded **explicitly** through `parsePatch`/`highlightToLines` rather than read from a module global: the html depends on it, so a hidden read would make `parsePatch` return different output for the same arguments and leave every `useMemo` unable to declare the dependency. Defaults stay github-dark/github-light, so nothing changes for an existing user until they pick. The pickers are in the Appearance tab (`components/SyntaxThemePicker.tsx`), side by side (light first), each with a live preview rendered **in that theme** — its own background and foreground included, read from the registration's `editor.background`/`editor.foreground` since raw shiki registrations carry no top-level bg/fg — regardless of the app's current mode, since otherwise choosing a light theme while working in dark mode is blind. A change re-highlights every mounted diff (~100-180ms per 1000 lines), which is why the picker commits on select and never on hover. To add an IPC call, add a method to `IpcApi` and the compiler forces implementations on both sides. `src/shared/types.ts` is the single source of truth for data shapes.

### Attachments (images and videos)

Dropping a screenshot or screen recording into a PR description is how a "demo" section gets written, and it's the one GitHub feature with no API behind it: `/upload/policies/assets` refuses a PAT and wants a browser session cookie. Rather than call that internal endpoint ourselves, the app **drives GitHub's own composer** — so GitHub can change its upload protocol without breaking us.

- **The session.** `main/github/attachments.ts` keeps a logged-in github.com session in the `persist:github-web` partition, apart from the token the rest of the app uses. `signInForAttachments` opens a real GitHub sign-in window and polls for the `user_session` cookie (it can't be read any other way); `dotcom_user` names the account for the settings badge. Every path settles — cookie found, window closed, page failed to load, or a 10-minute cap — because the renderer keeps a button spinning until it returns. First paste triggers the sign-in on its own, so Settings is optional.
- **The upload.** A hidden window loads a page with a comment composer (the PR itself, or `issues/new` for the new-PR dialog, which has no PR yet), the file is written to a temp dir (a pasted screenshot arrives as bytes with no path), handed to the composer's file input via the DevTools protocol's `DOM.setFileInputFiles`, and the permanent `user-attachments/assets/…` URL is read back out of the textarea. `backgroundThrottling: false` — a hidden window throttles timers and can stall GitHub's upload script.
- **Two traps worth remembering.** (1) The composer is client-rendered, so the *first* `input[type=file]` on the page is somebody else's — usually Copilot's chat attachment field, which has its own narrower allowlist and produced a baffling "we don't support that file type" naming MOV *in the list of supported types*. Page script picks the input (the one sharing a container with the comment textarea, Copilot's excluded), tags it, and CDP addresses the tag. (2) GitHub ships that same allowlist message into the page **hidden**, ready to show, so scraping error text reports a failure the instant the page loads whatever the file is — only an error that is not in a `<template>`, `hidden`, `display:none`, `visibility:hidden`, or `aria-hidden` counts. Deliberately no geometry check: the upload window is never shown, so `getBoundingClientRect` returns zeros for everything and would hide real errors.
- **The renderer side.** `lib/useAttachmentUpload.ts` holds a placeholder (`![Uploading name…]()`) at the cursor, uploads in parallel, and swaps in the real markdown — every edit goes through a ref holding the latest text, since uploads finish out of order. A failure removes its placeholder and toasts. `MarkdownEditor`'s optional `attachments` prop turns on paste, drop, and a file picker; it's set on all three editors (PR description, conversation comments, new-PR dialog).
- **Rendering them back.** An uploaded video is written into the body as a bare attachment link, and attachment URLs carry no file extension — GitHub decides "player or link" from the content type it serves. A bare attachment autolink (link text identical to the href) renders `components/AttachmentMedia.tsx`, which tries to play it and falls back to the plain link for a zip, a PDF, or a codec Chromium can't decode (ProRes, some HEVC). Bodies written on github.com use real `<video>` tags, which the default sanitize schema dropped — `video`/`source` are now allowed with player attributes only, `src` proxied like images.
- **Byte ranges are mandatory for media.** Chromium's media loader asks for a range and treats a plain 200 as an unsupported source (`MEDIA_ERR_SRC_NOT_SUPPORTED`) even when the bytes are correct, so the `gh-asset://` handler passes `Range` through to the signed storage URL, returns its 206 and `Content-Range` untouched, and adds `Accept-Ranges: bytes` when upstream omits it. Measured, not guessed: a scheme with `stream: true` and no range support still fails; range support without it plays. The signed URL is cached 60s, because seeking otherwise asks github.com to mint a fresh one per range; an expired one is re-minted automatically. The CSP needs `media-src` — without it video falls back to `default-src 'self'` and is blocked outright.

### Analysis pipeline

Analysis is **explicitly user-triggered** (an "Analyse PR" button — never automatic, so API credits are only spent on purpose) and runs as a **background job**: `lib/analysisJobs.ts` (a module store + `useSyncExternalStore`, like the other renderer-global settings) owns the run rather than a component's mutation, so leaving the review screen doesn't lose track of it. It holds one job per PR (`analysing` → `checking` while the chained findings pass runs, keyed repo#number, a second start ignored so credits aren't spent twice), writes the result into the query cache itself, and reports the end with a toast — success with the issue count, a warning when the analysis landed but the issue check failed, an error when the analysis itself failed (which restores the previous analysis rather than leaving a blank tab). `AnalyzedSidebarList` renders running jobs with a spinner — a PR analysed for the first time gets its own row at the top of the Analysed section until the cache list picks it up — and `ReviewPanel`/`ReanalyzeButton` read the same store for their loading states. `analysis/pipeline.ts` fetches the PR detail + file patches from GitHub, builds one prompt (mechanical files like lockfiles get name/stats only; per-file and total patch-size caps), and makes a single Claude Messages API call to `claude-opus-4-8` (plain `fetch`, forced tool use for validated structured output). The result is an `AnalysisResult`: a plain-English `summary`, `groups` (logical change groups in reading order, each with a story, risk level `attention`/`routine`/`mechanical`, and files — every changed file is guaranteed to land in some group), plus `risks`/`behaviorChanges` claims (each with a short nav `title` + full text) carrying `DiffAnchor`s (file + new-file line number, so every claim is verifiable against the diff) and `outOfScope`. Each risk gets a **stable id** (`riskId` — `sha1("risk|" + title + "|" + first anchor)`), so its dismissal survives a re-analysis that reports the same risk; `withRiskMeta` backfills ids on pre-id cached analyses and joins each risk's `resolution` from the findings resolution store at read time (never persisted in the cache). Cached by repo + PR + head SHA in `~/.pr-reviewer/analyses.json` (disk-backed so paid analyses survive restarts; pruned to the 100 newest; SQLite later) — `getExistingAnalysis` checks the cache without ever calling the model. Later: streaming progress stages, a cheap model for mechanical classification, background pre-analysis of the review queue.

### Pre-review findings pass

Runs as the second half of a **deep review** — the Review tab's empty state offers two buttons, "Quick review" (the analysis alone) and "Deep review" (chains `findIssues` once the analysis lands), and the Re-analyse dialog carries the same choice as a Depth field, defaulting to deep. Depth is a **required argument** to `startAnalysis` (`ReviewDepth` in `lib/analysisJobs.ts`), not a setting with a default: the two cost noticeably different amounts, so every entry point has to say which one the user asked for. After a quick review the pass can still be run on its own from the Issues section in the Review tab's nav — that's how a quick review is upgraded to a deep one without paying for the analysis again. `analysis/findings.ts` runs an **agentic tool loop** — the model gets the same PR context as the analysis plus the repo tools (`read_file`/`grep_repo`/`list_files`/`git_log`, shared with the chat) and ends by calling a `report_findings` structured-output tool. When a same-commit analysis exists, its risks are appended to the prompt as numbered **leads** — unverified hypotheses the agent must investigate and either confirm (the finding carries the lead's number in `lead`) or clear (`clearedLeads`, with a one-line note); `buildLeadVerdicts` maps those back to risk ids as `FindingsResult.leadVerdicts` (`confirmed` verdicts carry the finding's id), which is how the renderer knows a risk became a verified finding or was checked and cleared. The point of the tools is to look *beyond the diff*: the standout `blast_radius` category greps for callers of a changed function/signature and reports the ones the diff didn't update. Both providers report findings by **calling a `report_findings` tool** rather than via structured-output formatting — the API path is a manual tool loop (final round forces `report_findings` so it always commits); the Claude Code path (`runFindingsAgentQuery`) exposes `report_findings` as an MCP tool whose handler captures the input, because the SDK's `outputFormat: json_schema` returns empty when combined with MCP repo tools (a "success" result with no `structured_output`). Each finding has a `category`, `severity` (reuses `RiskSeverity`), title, markdown `body`, a single diff anchor (`path` + new-file `line`), and a ready-to-post `suggestion`. `findingsNormalize.ts` (pure, unit-tested) validates every finding against the diff: the path must be a changed file and the line must sit in its diff (snapped to the nearest in-diff line if the model was slightly off, dropped if unanchorable), then assigns a **stable id** = `sha1(category|path|line)` so a re-run of the same issue keeps its identity, and dedups/sorts high→low. Runs are cached by head SHA in `~/.pr-reviewer/findings.json`; the user's per-issue **resolutions** (`accepted`/`dismissed`) live separately in `finding-resolutions.json` keyed per PR, so they survive re-runs and never nag twice — the store joins them onto each finding as `resolution` at read time, and risk ids key into the same store (dismissing an unverified risk uses the same `setFindingResolution` IPC; the pipeline joins those onto the analysis's risks). IPC: `getFindings` (cache-only, null if never run), `findIssues` (runs the model; `force` skips the cache), `setFindingResolution` (`"open"` clears it). Trust principle: the agent proposes, the human disposes — nothing is posted to GitHub automatically.

The findings pass runs when the user picks a deep review (both `ReviewPanel`'s empty state and `ReanalyzeButton` chain it with `force`, sharing the `["findIssues", repo, number]` mutation key so `useIsMutating` drives every loading state); after a quick review, the telescope icon button in the Issues section header runs it on its own (it becomes a re-run icon once findings exist). Selection state (`AnalysisSelection`, exported from AnalysisNav) lives in `ReviewPanel` and falls back to Summary if a selected item no longer exists. Risk badges: `components/RiskBadge.tsx`. The chat is a repo-aware agent (`agent/session.ts` + `agent/tools.ts`): the main process keeps one context per PR (rebuilt if the PR gets new commits) and disk-backed conversation histories in `~/.pr-reviewer/chats.json` (capped at 100 messages per PR; the newest 20 go to the model as context) — exposed as `getChatHistory` over IPC, which `ChatPanel` loads via `useQuery(["chatHistory", …])` with local overlay state for streaming/failed messages, so conversations survive restarts; context = the same capped diff the analysis uses (`buildPullRequestContext`, exported from pipeline.ts) + the cached analysis JSON; model `claude-sonnet-5` (fast for interactive use — Opus stays on the one-shot analysis); the context block is marked `cache_control: ephemeral` so follow-up questions hit Anthropic's prompt cache. Answers stream: the main process parses the SSE stream and pushes `text_delta`s to the renderer via `webContents.send` on the `chatChunk` channel (see `ChatChunk`/`RendererEvents` in `shared/ipc.ts`; preload exposes `onChatChunk` returning an unsubscribe); `askQuestion` still resolves with the full answer, which replaces the streamed text as the authoritative copy. On top of that runs a client-side tool loop (max 8 rounds; the final round is sent without tools to force a text answer): the model can call `read_file`, `list_files`, `grep_repo`, and `git_log` (defined + executed in `agent/tools.ts` against the workspace clone, pinned to the PR's head SHA). `grep_repo` triggers `ensureHeadBlobs` first — a targeted backfill that lists the blobs missing from the reviewed commit's tree (`rev-list --missing=print`, which counts donor/alternate objects as present) and batch-fetches just those by id; it also runs during PR warm-up, so the first grep rarely waits. Within a question's loop, the full tool conversation is kept and a moving `cache_control` breakpoint sits on the newest tool results so each round re-reads the prefix from Anthropic's prompt cache; stored history stays plain text (tool activity is not replayed across questions). Tool failures are returned to the model as `is_error` tool results — it's prompted to fall back to diff-only answers and say what it couldn't verify. Diff rendering is shared: `lib/diffParser.ts` (patch → lines + syntax highlighting via `lib/highlighter.ts` (shiki) — each hunk is highlighted as two whole documents, old side (del+context) and new side (add+context), and shiki hands the tokens back already split by line, so multi-line constructs like `/** */` block comments and template literals keep their state across lines; hunks are never concatenated since the unseen gap between them could invalidate carried-over state; plus `buildSplitRows` which pairs del/add runs into side-by-side rows) feeds `components/DiffLines.tsx`, used by both the full-pane `DiffView` (Changes tab) and `FileDiffCard` (Review tab); file status letters/colors live in `lib/fileStatus.ts`. On the Changes tab, `DiffView` also fetches the file's full contents at the diff's commit from the workspace clone (`getFileAtCommit` over IPC → `readFileAtCommit` in `repo/workspace.ts`, null for binary/unavailable — everything degrades to diff-only; query `["fileAtCommit", repo, sha, path]`, infinite staleTime, excluded from persistence) and hands it to `DiffLines` as `DiffExpansion`, which buys three things: (1) add/context rows swap their html for slices of the whole highlighted file — per-hunk fragment highlighting mis-colors hunks that start mid-construct (e.g. inside a JSX tag); a text-equality guard between the file and the diff drops the upgrade when they disagree; (2) hunk headers grow an expand button (and a tail row after the last hunk) that splices the hidden gap in as `expanded: true` context rows via `computeGaps`/`expandLines` in diffParser — expanded rows can't host comments (GitHub can't anchor outside the diff) and count as hunk separators so comment selections can't cross them; (3) a "View file" toggle in the header renders the entire file (`components/FileView.tsx`, same mono font + syntax palette as diff rows) — it also works for too-large-to-diff files, and deleted files opt out of all three (no file at that commit). Diffs render inline or split (side-by-side): the global layout mode lives in `lib/diffViewMode.ts` (localStorage + `useSyncExternalStore` hook so every mounted diff reacts), picked via `components/DiffViewModeSelect.tsx` at the right end of the Review screen's tab bar (its menu is portalled — non-portalled it stacked under the diff panes' sticky elements) — Inline / Split / Dynamic, where Dynamic goes split per diff when its container is ≥960px (ResizeObserver in DiffLines). Nothing is mock anymore, and the chat can see beyond the diff via its repo tools. (5) attachments are real — images and videos can be pasted, dropped, or picked in any markdown editor and are uploaded to GitHub through a signed-in github.com session (there is no API for it), then render back as inline images and video players (see "Attachments" above).

The repo workspace is real (`repo/workspace.ts` + `repo/git.ts`): opening a PR fires a best-effort background warm-up (from the `getPullRequest` IPC handler) that maintains a **bare, blobless** clone per repo at `~/.pr-reviewer/repos/owner__repo.git` — no checkout; everything is read from the object store pinned to a commit (`showFile`/`listFiles`/`logForPath`), so all PRs of a repo share one clone and blobs download lazily on first read. The PR's head commit comes from `refs/pull/<n>/head` (works for fork PRs). Clones use the user's registered local checkout as an object donor (`--reference-if-able`) when available — the alternates link persists, so donor objects count as present forever. Warm-up finishes by backfilling the head commit's tree (`ensureHeadBlobs`): batch-fetch only the blobs missing after the donor and previously-fetched PRs are counted, so grep never has to lazy-fetch file-by-file and each PR only downloads its own delta. Auth: the GitHub token is injected per-command via `GIT_CONFIG_*` env vars (never written to the clone's config); every git command gets it because lazy blob fetches can happen on any read. Syncs are deduped in-flight and rate-limited (5-min TTL).

7. **Explain a selection (drag-to-explain) — next up.** On the Changes-tab diff, extend the existing drag-to-select-a-range affordance (today it only opens the comment composer) with an **"Explain"** action alongside "Comment". Dragging a range and choosing Explain hands the selected lines (path + line range) to the Q&A agent with a templated prompt and the selection quoted, so the answer references the exact lines (trust principle — one-click verification). The drag affordance and range math already exist in `DiffLines`/`DiffCommenting`; the new work is a second action on the selection plus the surfaces below. Read-only, lowest risk — build this one first.
   - **Primary surface: an inline "AI explanation" card anchored to the selected lines**, local-only (never posted to GitHub). Model it as a *third kind of anchored artifact* alongside real review threads and local draft comments: its own disk-backed store (`explanations.json`, keyed `repo#number`, mirroring `store/drafts.json`), each entry carrying id, path, line range, the answer markdown, the **head SHA it was generated against**, and a snapshot of the explained code. Render it as a distinct card under the anchor line (sparkle icon, an "AI explanation" label, an accent tint) so it never reads as a GitHub comment and gets no "post to GitHub" action.
   - **Coexists with your own comments.** `DiffCommenting` already carries real threads and drafts as separate bands; explanations become a third band, so the gutter "+" (leave your own comment) is untouched and a bot explanation and your own thread can sit on the same lines.
   - **Staleness (done).** Every explanation is re-anchored against the diff on screen before it renders — `lib/explanationStatus.ts`'s `resolveExplanation` (pure), fed by `DiffLines` with the current text of every anchorable line. Three outcomes: written against the current head SHA (or the stored code snapshot still sits at the stored line numbers) → unchanged; the snapshot's lines found intact elsewhere on that side, as a run consecutive by line number so a match can't span a hunk → **snap silently** to the new anchor (any edit earlier in the file renumbers everything below it, so this is the common case and badging it would teach people to ignore the badge); otherwise → **stale**: an orange "Explains an earlier version" badge plus a warning strip and a **Re-explain** button (re-runs `explainSelection` over whatever is at those lines now, then deletes the old entry — explaining first, so a failure leaves the old card rather than losing it). A stale card keeps its stored anchor when those line numbers still exist and otherwise snaps to the nearest line on that side, so it can never silently disappear. Local-only, so it badges and never auto-deletes.
   - **Two bridges out:** **Promote to draft comment** (one click turns an explanation into a draft review comment via `addDraftComment`, like findings' "Add as draft comment") and **Continue in chat** (opens the Review tab's `ChatPanel` seeded with the selection + explanation, via a small shared "pending question" hand-off — keeps v1 explanations single-shot while allowing a deeper conversation).
8. **Agent-authored PR changes (the foundation for editing).** Let the agent make real code changes to the PR from inside the tool, so the reviewer never has to drop to an editor or the CLI. Key pieces: (a) a **writable checkout** — today's review clone is bare + blobless (read-only, pinned to the head SHA), so this needs a separate per-PR git worktree/clone checked out to the PR head branch under `~/.pr-reviewer/…`, kept apart from the pinned read path so the review diffs stay stable; (b) **edit tools** for the agent (`write_file`/`apply_patch`, plus an optional sandboxed `run_command` for formatters/tests), either via the Claude Agent SDK's native file editing or by extending the manual tool loop in `agent/`; (c) **human-in-the-loop, always** — the agent produces a *proposed* changeset rendered as a diff (reuse `DiffView`) that the user reviews; nothing is committed or pushed automatically. Accept → commit to the local checkout; a separate, explicitly confirmed step pushes to the PR's head branch. Proposed edits are held locally (like draft review comments) so they survive restarts and can stack. (d) **Fork/permission handling** — pushing to a fork's head branch needs push access or the PR's "maintainer can modify" flag; detect this and degrade gracefully (offer push-to-a-new-branch, or an exportable patch) when it isn't allowed. Mirrors the existing drafts → Submit review pattern and the app's "confirm outward-facing actions" rule: the agent proposes, the human disposes and is the only one who triggers the push.
9. **Drag-to-modify + conversational edits.** Built on #8: the same diff drag affordance gains an **"Edit with agent"** action — describe a change in plain English scoped to the selected lines — and the chat can be asked to make changes conversationally ("rename this everywhere", "add a null check here"). Both funnel into #8's propose → review-diff → accept → commit → push flow. Drag-to-modify is the second of the two drag features (Explain in #7 first, since it's read-only and proves the selection → agent hand-off before any write path exists).
10. **Go-to-definition in diffs (idea, not scheduled).** Cmd+click an identifier in a diff and see where it's defined — the "what does this helper do / who else calls it" question, answered without leaving the review. **Independent of #8 and #9** — read-only, no writable checkout, buildable at any point. The design decision that makes it cheap: resolve symbols with the existing `grepAtCommit` (a definition-shaped regex — `(function|class|interface|type|enum|const|let)\s+Foo\b`, `def`/`func` for Python/Go) rather than a language server. `git grep` runs against the *commit object*, so the bare blobless clone is enough (no checkout, no installed deps, no per-language servers — those were the whole reason this looked like weeks of work). It's also fast enough for a click, which the chat agent is not: it can already answer "where is this defined", but seconds and API credits are the wrong trade for a cmd+click. Three pieces: (a) **word under the cursor** — `CodeText` injects highlighted HTML, so the line is real text nodes; `document.caretPositionFromPoint` gives node + offset, expand to word boundaries with a regex (~30 lines, independent of how the highlighter nested its spans); (b) **resolve** — grep, jump on a single hit, small picker on several; (c) **show it as a *peek*** — an inline expandable panel under the line (reusing `FileView`'s rendering), not a navigation away: a reviewer's place in the diff is the thing worth protecting, and peeking avoids building a file-browser screen with breadcrumbs. Accuracy trade-off accepted deliberately: grep finds "a thing named `save` is defined here", not *which* one — showing "2 definitions" and letting the human pick degrades honestly instead of jumping somewhere wrong. Upgrade path if that annoys: a tree-sitter tags index built during warm-up and cached per head SHA (same pattern as the analysis/findings caches) — an add-on, not a rewrite. Rough cost: 3–4 days for TS/JS, no new dependencies. Explicitly rejected: embedding CodeMirror or Monaco (only needed for *typing*, and Monaco's diff editor would fight `DiffLines`'s comment threads, draft bands, explanation cards, range selection and context expansion), and running real language servers (needs files on disk + installed dependencies, which would drag in #8's checkout and turn days into weeks).

## Conventions

- UI is Chakra UI v3 (`@chakra-ui/react` + `@emotion/react`, icons from `react-icons/lu`). Use Chakra components and style props, not CSS files. A Chakra MCP server is available for component examples and props.
- Data fetching goes through TanStack Query (`@tanstack/react-query`). The client lives in `renderer/src/lib/queryClient.ts` and wraps the app in `main.tsx` via `PersistQueryClientProvider`: the query cache persists to localStorage (24h max age, `pullRequestFiles`/`commitFiles`/`fileAtCommit`/`localChanges`/`localChangeCount` excluded — patches and file contents are too big for the ~5MB quota and cheap to refetch, and local change data goes stale the moment the working tree moves), so screens paint instantly from the last session while refetching in the background. The renderer cache is NOT the source of truth for analyses — the main process's disk cache is; `getAnalysis` stays correct after restarts because of it. Query keys in use: `["repositories"]`, `["localChangeCount", repoPath]` (cheap porcelain-status count for the always-visible Current changes tab badge — always-on for the selected repo; local git only, no token), `["localChanges", repoPath]` (the checkout's uncommitted work, staged/unstaged split with full patches, fetched only while the Current changes tab is showing; writes go through the `["localChangesWrite", repoPath]` mutation key — `lib/localChangesMutations.ts` — so every stage/unstage/discard/commit surface shares one busy state and invalidates both queries on settle), `["worktrees", repoPath]` (the repo's main + linked git worktrees for the Current changes worktree switcher; local git only, never persisted), `["pullRequests", slug]`, `["repoIssues", slug]` (the repo's open GitHub issues, fetched only while the Issues tab is showing), `["repoIssue", repo, number]`, `["repoIssueComments", repo, number]`, `["reviewRequests"]`, `["myPullRequests"]`, `["openPrCounts"]` (open-PR count per registered repo slug, for the sidebar's repo rows), `["branchInfo", repo]` (branches + local-checkout defaults for the new-PR dialog), `["repoMergeSettings", repo]` (the merge methods the repo allows — `components/MergeDialog.tsx` only offers those, defaulting to the first, so squash-only repos behave like GitHub), `["reviewDecision", repo, number]` (GitHub's GraphQL `reviewDecision`, fetched by MergeDialog for open PRs: while it's REVIEW_REQUIRED or CHANGES_REQUESTED — or still loading — the merge button is hidden entirely; null means no review requirement and a failed lookup fails open; SubmitReviewDialog invalidates it so an approval reveals the button; an APPROVED decision also turns the Actions trigger and its "Merge pull request" item green, via the `approved` flag on `useMergeAvailability`), `["pullRequest", repo, number]`, `["prActivity", repo, number]` (a 60s background poll on the review screen — `peekPullRequestActivity` is an ETag conditional request, so unchanged polls are 304s that don't count against the rate limit; the renderer compares the snapshot against the `["pullRequest"]` cache and, when something is newer, swaps the header's refresh icon button for a yellow outline "Refresh to update" button whose tooltip names what changed ("Refresh — 2 new commits, 1 new comment"); best-effort — null on any failure just skips the highlight, and the refresh button's invalidate-by-repo+number predicate clears it), `["pullRequestFiles", repo, number]`, `["pullRequestCommits", repo, number]`, `["commitFiles", repo, sha]`, `["fileAtCommit", repo, sha, path]` (full file text from the workspace clone, for the diff viewer), `["pullRequestComments", repo, number]`, `["pullRequestReviews", repo, number]`, `["reviewComments", repo, number]`, `["resolvedThreads", repo, number]`, `["reactions", repo, number]` (emoji reactions on all of the PR's comments, keyed by comment id — one lookup shared by every comment bar), `["viewedFiles", repo, number]` (paths the viewer marked as viewed, synced with GitHub's checkboxes), `["draftComments", repo, number]` (locally drafted review comments; source of truth is the main process's drafts.json), `["analysis", repo, number]`, `["findings", repo, number]` (pre-review agent findings — the query is cache-only; the model runs through the `["findIssues", repo, number]` mutation, auto-chained after an analysis or fired from the nav, writing back with `setQueryData`), `["viewer"]` (the GitHub login the stored token belongs to), `["secretsStatus"]`, `["attachmentAuth"]` (whether a signed-in github.com session exists for attachments, and which account — separate from the token, since GitHub has no upload API). Mutations (add/remove repo, save/clear key) update the cache via `setQueryData` or `invalidateQueries` so dependent views (setup banner, PR list) refresh automatically.
- **Group code in folders, not in one flat list.** A feature with more than a couple of files gets a folder of its own: `components/TabBar/` holds one component per file, `lib/tabs/` holds the logic and a test beside each file. Names in `components/` are PascalCase and names in `lib/` are camelCase, folders included — a lib folder is named after what it holds (`lib/tabs/`), not after the component that reads it. No barrel files (`index.ts`): an import says which file it comes from, so a grep for a name finds every caller.
- **Non-trivial React logic goes lib → hook → component.** Pure functions in a lib file (no React import, no side effects, explicit input and output types, a colocated test that covers them), a hook per responsibility that only orchestrates, and a component that wires hook output to JSX. `lib/tabs/tabs.ts` (every state change as a pure `(state, args) => state`) under `lib/tabs/useTabs.ts` (Zustand and `persist`, and nothing else) under `components/TabBar/` is the worked example. Skip the hook layer when the logic is small enough to call straight from the component. Split hooks by responsibility rather than one big hook, name a hook after the lib function it wraps, and keep hooks flat — a hook calling another domain hook hides the coupling. Because the logic is tested in the lib layer, hook and component tests only need to cover the wiring; a pure test also runs in the fast node environment, where a component test needs jsdom.
- React components and functions inside them use the `function` keyword, not arrow functions.
- Component props: `interface Props {}` (or a descriptive exported name if they must be exported).
- Comments are written in **ASD-STE100 Simplified Technical English**: one idea per sentence, active voice, present tense, no idiom or metaphor, 25 words at most for a descriptive sentence. Say *why*, in short plain sentences. This applies to new and changed code; a file the change does not touch keeps the comments it has, because a half-converted file reads worse than either style alone.
- No unnecessary comments; TODOs mark unimplemented stubs.
- Formatting and linting are handled by Biome (2-space indent, double quotes). Run `pnpm check` before committing.
- Conventional commits (`feat:`, `fix:`, `chore:`).
