# PR Reviewer

A desktop app that makes code review easier. Think of it as replacing GitHub's "manila folder dump" of files with a guided, agent-assisted review experience.

## The problem

- PR descriptions are often obtuse, empty, or don't explain what the PR is trying to achieve.
- Reviewing means scrolling a big unordered file list. No signal for how data flows, which changes are critical, or where to start.
- No way to ask questions about the code without interrupting the author.

## What the app does

1. **Agent-generated summaries with lenses.** When a PR is opened, an agent produces toggleable views: overview ("what changed and why"), risks, behavior changes (what callers/users experience differently), and scope ("what's NOT in this PR").
2. **Logical change groups + reading order.** The diff is split into narrative chunks ("Change 1: new endpoint, 3 files. Change 2: mechanical rename, 12 files"), each with a risk badge, presented as a guided tour rather than a flat file list.
3. **Q&A agent with full repo context.** Ask questions about specific changes or the whole PR. The agent has the entire repo cloned locally (not just the diff), so it can answer "what does this helper do?" and "who else calls this?".

Planned beyond MVP:

- **Blast radius**: for changed functions/signatures, find callers *outside* the diff that weren't updated — that's where bugs live.
- **Risk-ranked file ordering**: new logic > modified logic > mechanical renames > generated files > lockfiles.
- **Pre-review agent pass**: candidate issues flagged as suggestions for the human to verify, not auto-comments.
- **Diff vs. intent check**: does the PR do what its description/ticket says, and nothing surprising?
- **Changes since last review**: for repeat rounds, summarize what changed and how comments were addressed.
- **Comment drafting**: draft inline comments locally (agent can help phrase), batch-submit as a real GitHub review.

Trust principle: every agent claim must link to the exact lines it's based on, so verification is one click. A reviewer who trusts a wrong summary rubber-stamps a bad PR.

## Architecture

Electron (chosen over Tauri because the Claude Agent SDK, Octokit, and git tooling are all Node/TypeScript — Electron's main process runs them natively; Tauri would need a Node sidecar).

- **Main process (Node)** — all the real work: GitHub API (Octokit), local repo clones under `~/.pr-reviewer/repos` (blobless: `--filter=blob:none`), diff parsing, the analysis pipeline, Claude Agent SDK sessions, SQLite persistence. Secrets never reach the renderer.
- **Tab navigation** — a row of tabs across the top (`components/TabBar/`), state in `lib/tabs/tabs.ts` (pure `(state, args) => state` functions) and `lib/tabs/useTabs.ts` (Zustand, persisted to localStorage). One pinned Pull Requests tab, one tab per open pull request, one Issues tab per repository, and one Current Changes tab per worktree. Full detail, including hotkeys and keep-alive rules: `docs/architecture.md`.
- **Renderer (React + Chakra UI v3)** — purely presentational. A collapsible sidebar sits beside the active screen. Each repository expands to Pull Requests, Issues, Current Changes, and linked-worktree destinations. The pinned Pull Requests tab holds one repository's open PRs. Each repository can have a top-level Issues tab, each worktree can have a Current Changes tab, and each PR has a review screen (Overview / Changes / Review tabs). Full detail on layout, theming, and every screen: `docs/architecture.md`.
- **Attachment uploads** — a second, separate GitHub credential: a signed-in github.com session, because GitHub has **no API for comment attachments**. Full detail: `docs/attachments.md`.
- **Typed IPC** — `src/shared/ipc.ts` defines the `IpcApi` interface. `src/main/ipc/router.ts` implements it; `src/preload/index.ts` exposes it as `window.api`. To add an IPC call, add a method to `IpcApi` and the compiler forces implementations on both sides. `src/shared/types.ts` is the single source of truth for data shapes.

The analysis pipeline (one Claude call → plain-English summary, change groups, risks) and the pre-review findings pass (an agentic tool loop that looks beyond the diff for blast-radius bugs) are documented in `docs/analysis-pipeline.md`.

## Development

- `pnpm dev` — run the app. `pnpm typecheck` — both tsconfig projects. `pnpm build` — production build.
- `pnpm format` — Biome formatter (write). `pnpm lint` — Biome linter (check only). `pnpm check` — Biome format + lint + import sorting (write). Config in `biome.json`: 2-space indent, double quotes, respects `.gitignore`.
- pnpm 10 blocks dependency install scripts; `electron` and `esbuild` are allowlisted in package.json (`pnpm.onlyBuiltDependencies`). If `node_modules/electron/dist` is missing after install, run `node node_modules/electron/install.js`.
- Branding: the app is "Copper" (`productName` in package.json, `appId: com.jamesofficer.copper`). `main/index.ts` also pins `app.setName("Copper")` before the app is ready — the name titles the macOS app menu and keys safeStorage's keychain item, so leaving it to whatever bundle we run under means a worktree with an unbranded Electron.app encrypts secrets under a second name. The icon is raster artwork at `resources/icon.png` (1024px, transparent margin) → `build/icon.icns` (an iconset of 16–512 at 1x/2x, via `magick` + `iconutil`). Artwork is fitted to an 824px content box inside the 1024px canvas — Apple's proportion, so the icon doesn't read as undersized next to other dock icons; resizing runs in premultiplied alpha (`-alpha associate` … `-alpha disassociate`) so the small sizes get no dark halo. The main process sets the dock icon at runtime (`setDockIcon` in `main/index.ts`). Because dev runs the stock Electron binary, `scripts/brand-dev-electron.sh` (postinstall) rewrites the bundled Electron.app's Info.plist name, swaps its icns, re-signs it ad-hoc (an edited plist breaks the signature), and re-registers the bundle with LaunchServices. Two traps there: macOS caches a bundle's name, so without the re-registration the dock keeps saying "Electron" however the plist reads; and stock Electron's `CFBundleIdentifier` is `com.github.Electron`, which every other Electron dev build on the machine also claims — LaunchServices resolves a running app's name by identifier, so with several bundles sharing one it answers with somebody else's record. The script rewrites the identifier to `com.jamesofficer.copper.dev` to get a record of our own, and unregisters the old path before re-registering so the cache can't survive a rename.
- Pinned: vite 7 + @vitejs/plugin-react 5 (electron-vite 5 doesn't support vite 8 yet).

## Conventions

- UI is Chakra UI v3 (`@chakra-ui/react` + `@emotion/react`, icons from `react-icons/lu`). Use Chakra components and style props, not CSS files. A Chakra MCP server is available for component examples and props.
- Data fetching goes through TanStack Query (`@tanstack/react-query`). The client lives in `renderer/src/lib/queryClient.ts` and wraps the app in `main.tsx` via `PersistQueryClientProvider`: the query cache persists to localStorage (24h max age, `pullRequestFiles`/`commitFiles`/`fileAtCommit`/`localChanges`/`localChangeCount` excluded — patches and file contents are too big for the ~5MB quota and cheap to refetch, and local change data goes stale the moment the working tree moves), so screens paint instantly from the last session while refetching in the background. The renderer cache is NOT the source of truth for analyses — the main process's disk cache is; `getAnalysis` stays correct after restarts because of it. Query keys in use: `["repositories"]`, `["localChangeCount", repoPath]` (cheap porcelain-status count for each visible Current Changes destination in the repository tree; local git only, no token), `["localChanges", repoPath]` (the checkout's uncommitted work, staged/unstaged split with full patches, fetched only while that checkout's Current Changes tab is showing; writes go through the `["localChangesWrite", repoPath]` mutation key — `lib/localChangesMutations.ts` — so every stage/unstage/discard/commit surface shares one busy state and invalidates both queries on settle), `["worktrees", repoPath]` (the repo's main + linked git worktrees for opening worktree-specific Current Changes tabs; local git only, never persisted), `["pullRequests", slug]`, `["repoIssues", slug]` (the repo's open GitHub issues, fetched only while the Issues tab is showing), `["repoIssue", repo, number]`, `["repoIssueComments", repo, number]`, `["reviewRequests"]`, `["myPullRequests"]`, `["openPrCounts"]` (open-PR count per registered repo slug, for the sidebar's repo rows), `["branchInfo", repo]` (branches + local-checkout defaults for the new-PR dialog), `["repoMergeSettings", repo]` (the merge methods the repo allows — `components/MergeDialog.tsx` only offers those, defaulting to the first, so squash-only repos behave like GitHub), `["reviewDecision", repo, number]` (GitHub's GraphQL `reviewDecision`, fetched by MergeDialog for open PRs: while it's REVIEW_REQUIRED or CHANGES_REQUESTED — or still loading — the merge button is hidden entirely; null means no review requirement and a failed lookup fails open; SubmitReviewDialog invalidates it so an approval reveals the button; an APPROVED decision also turns the Actions trigger and its "Merge pull request" item green, via the `approved` flag on `useMergeAvailability`), `["pullRequest", repo, number]`, `["prActivity", repo, number]` (a 60s background poll on the review screen — `peekPullRequestActivity` is an ETag conditional request, so unchanged polls are 304s that don't count against the rate limit; the renderer compares the snapshot against the `["pullRequest"]` cache and, when something is newer, swaps the header's refresh icon button for a yellow outline "Refresh to update" button whose tooltip names what changed ("Refresh — 2 new commits, 1 new comment"); best-effort — null on any failure just skips the highlight, and the refresh button's invalidate-by-repo+number predicate clears it), `["pullRequestFiles", repo, number]`, `["pullRequestCommits", repo, number]`, `["commitFiles", repo, sha]`, `["fileAtCommit", repo, sha, path]` (full file text from the workspace clone, for the diff viewer), `["pullRequestComments", repo, number]`, `["pullRequestReviews", repo, number]`, `["reviewComments", repo, number]`, `["resolvedThreads", repo, number]`, `["reactions", repo, number]` (emoji reactions on all of the PR's comments, keyed by comment id — one lookup shared by every comment bar), `["viewedFiles", repo, number]` (paths the viewer marked as viewed, synced with GitHub's checkboxes), `["draftComments", repo, number]` (locally drafted review comments; source of truth is the main process's drafts.json), `["analysis", repo, number]`, `["findings", repo, number]` (pre-review agent findings — the query is cache-only; the model runs through the `["findIssues", repo, number]` mutation, auto-chained after an analysis or fired from the nav, writing back with `setQueryData`), `["viewer"]` (the GitHub login the stored token belongs to), `["secretsStatus"]`, `["attachmentAuth"]` (whether a signed-in github.com session exists for attachments, and which account — separate from the token, since GitHub has no upload API). Mutations (add/remove repo, save/clear key) update the cache via `setQueryData` or `invalidateQueries` so dependent views (setup banner, PR list) refresh automatically.
- **Group code in folders, not in one flat list.** A feature with more than a couple of files gets a folder of its own: `components/TabBar/` holds one component per file, `lib/tabs/` holds the logic and a test beside each file. Names in `components/` are PascalCase and names in `lib/` are camelCase, folders included — a lib folder is named after what it holds (`lib/tabs/`), not after the component that reads it. No barrel files (`index.ts`): an import says which file it comes from, so a grep for a name finds every caller.
- **Non-trivial React logic goes lib → hook → component.** Pure functions in a lib file (no React import, no side effects, explicit input and output types, a colocated test that covers them), a hook per responsibility that only orchestrates, and a component that wires hook output to JSX. `lib/tabs/tabs.ts` (every state change as a pure `(state, args) => state`) under `lib/tabs/useTabs.ts` (Zustand and `persist`, and nothing else) under `components/TabBar/` is the worked example. Skip the hook layer when the logic is small enough to call straight from the component. Split hooks by responsibility rather than one big hook, name a hook after the lib function it wraps, and keep hooks flat — a hook calling another domain hook hides the coupling. Because the logic is tested in the lib layer, hook and component tests only need to cover the wiring; a pure test also runs in the fast node environment, where a component test needs jsdom.
- React components and functions inside them use the `function` keyword, not arrow functions.
- Component props: `interface Props {}` (or a descriptive exported name if they must be exported).
- Comments are written in **ASD-STE100 Simplified Technical English**: one idea per sentence, active voice, present tense, no idiom or metaphor, 25 words at most for a descriptive sentence. Say *why*, in short plain sentences. This applies to new and changed code; a file the change does not touch keeps the comments it has, because a half-converted file reads worse than either style alone.
- No unnecessary comments; TODOs mark unimplemented stubs.
- Formatting and linting are handled by Biome (2-space indent, double quotes). Run `pnpm check` before committing.
- Conventional commits (`feat:`, `fix:`, `chore:`).
