# PR Reviewer

A desktop app that makes code review easier. Think of it as replacing GitHub's "manila folder dump" of files with a guided, agent-assisted review experience.

## The problem

- PR descriptions are often obtuse, empty, or don't explain what the PR is trying to achieve.
- Reviewing means scrolling a big unordered file list. No signal for how data flows, which changes are critical, or where to start.
- No way to ask questions about the code without interrupting the author.

## What the app does

1. **Agent-generated summaries with lenses.** When a PR is opened, an agent produces toggleable views: overview ("what changed and why"), risks, behavior changes (what callers/users experience differently), and scope ("what's NOT in this PR").
2. **Logical change groups + reading order.** The diff is split into narrative chunks ("Change 1: new endpoint, 3 files. Change 2: mechanical rename, 12 files"), each with a risk badge, presented as a guided tour rather than a flat file list.
3. **Q&A agent with full repo context.** Ask questions about specific changes or the whole PR. The agent has the entire repo cloned locally (not just the diff), so it can answer "what does this helper do?" and "who else calls this?".

Planned beyond MVP:

- **Blast radius**: for changed functions/signatures, find callers *outside* the diff that weren't updated — that's where bugs live.
- **Risk-ranked file ordering**: new logic > modified logic > mechanical renames > generated files > lockfiles.
- **Pre-review agent pass**: candidate issues flagged as suggestions for the human to verify, not auto-comments.
- **Diff vs. intent check**: does the PR do what its description/ticket says, and nothing surprising?
- **Changes since last review**: for repeat rounds, summarize what changed and how comments were addressed.
- **Comment drafting**: draft inline comments locally (agent can help phrase), batch-submit as a real GitHub review.

Trust principle: every agent claim must link to the exact lines it's based on, so verification is one click. A reviewer who trusts a wrong summary rubber-stamps a bad PR.

## Architecture

Electron (chosen over Tauri because the Claude Agent SDK, Octokit, and git tooling are all Node/TypeScript — Electron's main process runs them natively; Tauri would need a Node sidecar).

- **Main process (Node)** — all the real work: GitHub API (Octokit), local repo clones under `~/.pr-reviewer/repos` (blobless: `--filter=blob:none`), diff parsing, the analysis pipeline, Claude Agent SDK sessions, SQLite persistence. Secrets never reach the renderer.
- **Renderer (React + Chakra UI v3)** — purely presentational. No top bar of its own — a full-height split. Left, `components/HomeSidebar.tsx`, which `App.tsx` renders **beside both screens**, not just the home one, so a reviewer can jump straight from one PR to the next without going back. Its PR rows always open the PR itself — no preview step, since picking a PR from a list you deliberately keep in the sidebar means you want to read it; the preview panel is for the **Repositories** flow, where the main column lists a repo's open PRs and you may be skimming. Picking a repository leaves the review screen for the home screen's open-PR list (and drops any preview, which belonged to the old repo). The row for the PR being reviewed is marked (`selected` on `SidebarPullRequestRow`, the same style as the active repo). Because the sidebar now outlives the home screen, the state it needs sits in `App.tsx`: the registry and its three mutations in `lib/useRepositoryActions.ts` (shared with the home screen's empty-state "Add repository"), the recently-viewed list, the preview PR, and the settings dialog. It can be hidden — useful when reading a wide diff: `lib/sidebarCollapsed.ts` (localStorage + `useSyncExternalStore`, so both screens react), hidden with the panel button right of Settings in the sidebar's header, brought back with `components/ShowSidebarButton.tsx` at the left of either screen's top bar, and toggled with **Cmd+B / Ctrl+B** — the app's keyboard shortcuts go through TanStack Hotkeys (`@tanstack/react-hotkeys`, alpha; `HotkeysProvider` in `main.tsx`, `useHotkey` in `App.tsx`), with the binding and its platform-aware tooltip label in `lib/hotkeys.ts`: the library's `Mod` resolves to Command on macOS and Control elsewhere, and `formatForDisplay` writes it as "⌘ B" or "Ctrl+B" for the two buttons' tooltips; that bar also takes over the macOS traffic-light padding while the sidebar is away. The sidebar has five sections, each collapsible (a Chakra `Collapsible` per section — the chevron sits in the heading trigger, section-level actions stay outside it so buttons aren't nested, and the collapsed set persists in localStorage via `lib/sidebarSections.ts`, keyed by section id so a newly added section starts open; headings carry a count so a collapsed section still says how much is in it) — **Repositories** (`components/RepositoryList.tsx` — each row shows the owner org/user's avatar (rounded, `UserAvatar` with the folder icon as fallback — also used when the repo has no slug) and, at its right edge, the repo's open-PR count (query `["openPrCounts"]` → `getOpenPullRequestCounts`, one aliased GraphQL query over all registered slugs; no token or an inaccessible repo just omits that entry) in a fixed slot that swaps to the remove button on hover; rows are drag-sortable via dnd-kit: whole-row drag with a 4px pointer-distance activation so plain clicks still select, the dragged row rendered in a `DragOverlay` — the row left behind dims as the placeholder and the default drop animation glides the overlay into its slot instead of snapping; query key `["reviewRequests"]`; compact rows with the author's avatar (PR icon fallback) and a comment-count chip), **My pull requests** (same shape for `author:@me` via `listMyPullRequests`, query key `["myPullRequests"]`, comment-count chip, default PR icon; both sections share `searchOpenPullRequests` in `github/client.ts`, and `Welcome.tsx` invalidates both queries when repos are added/removed since the registry drives the filter), **Analysed** (`components/AnalyzedSidebarList.tsx` — PRs the user has run the analysis on, newest first, across every repo (not scoped to the selected one, unlike the old tab) and capped at the 7 newest since the section shares the sidebar with four others; the main process's cache only stores repo/number/sha, so each row fetches live detail through `peekPullRequest` under the shared `["pullRequest", …]` key, showing a skeleton until it lands; the row's meta is the analysis's age, turning orange when the analysis was run against a commit that's no longer the head), and **Recently viewed** (compact rows, not full cards — PRs the user has opened from any repo, stored in renderer localStorage via `lib/recentPrs.ts`, recorded by `App.tsx` on select, capped at 7 — enforced on read too, so older longer lists trim themselves — each row shows the author's avatar (PR-icon fallback), with a clear button in the section header) — and a footer anchored at the bottom with two actions: "Add repository" (folders picked via the native directory dialog) and Settings (opens the settings dialog). The main column has two tabs in its top bar — **Open pull requests** and **Current changes (n)**. Current changes is a browse-only review of the selected repo's *uncommitted* work (staged + unstaged + untracked — for reviewing an agent's slice before it becomes a PR): `components/LocalChangesView.tsx`, the Changes-tab layout (resizable file list, filter, shared `DiffView`) minus every PR-only affordance (no commenting, viewed state, or context expansion). The pull-requests tab is the selected repo's open PRs — rendered by `components/OpenPullRequestList.tsx`, which adds GitHub-style Author / Assignee / Sort dropdowns (user options show their GitHub avatar next to the login); `PullRequest` carries `assignees`/`createdAt`/`updatedAt` to power this); at the right end of the column's header bar, a "New pull request" button (`components/NewPullRequestDialog.tsx`, shown when the selected repo has a slug, keyed by slug) opens a create dialog: `getBranchInfo` over IPC (query `["branchInfo", repo]`, `staleTime: 0` so a just-pushed branch always shows, fetched only while open) returns the repo's GitHub branches sorted newest commit first — a GraphQL `refs` query (REST can't sort branches by activity at all) paged alphabetically to ≤500 with `defaultBranchRef` in the same call, then **sorted by `committedDate` in the main process**: GitHub's only date-ish `RefOrder` field is `TAG_COMMIT_DATE` and for `refs/heads` it's silently ignored, so asking for it DESC just returns reverse alphabetical (branches with no commit date sort last; a repo over the 500 cap is truncated by name before the sort sees it) and — via `getLocalCheckoutBranch` in `repo/local.ts` (`git symbolic-ref`, null on detached HEAD/unregistered) — the local checkout's current branch, pinned to the top of the list when it's on GitHub; head defaults to that branch when pushed and non-default (an info alert says to push first when it isn't), base to the default branch (the title is deliberately never prefilled), and untouched fields use a null-means-suggestion pattern so late-loading data still prefills — this also carries the repo's PR template into the description: `getBranchInfo` returns `pullRequestTemplate` (read from the default branch via the contents API, probing the conventional `.github`/root/`docs` `PULL_REQUEST_TEMPLATE.md` paths in parallel, best-effort), and the body falls back to it until the user types; head/base are non-portalled searchable `Combobox`es (portalled menus stack under the dialog), each filtering the other's pick from its options and showing each branch's last-commit date (`RelativeTime`) so the newest-first order is visible — `getBranchInfo` returns `branchDates` (branch name → ISO committed date, from `target { ... on Commit { committedDate } }` in the same refs query; optional, so a response cached before it existed just shows no dates). `BranchSelect` is memoized with `useMemo`d branch arrays, since the dialog re-renders per title/description keystroke and the branch lists can hold hundreds of items; its input is controlled (the selection arrives async, after the branch list loads) and `onOpenChange` clears the filter — selecting a branch sets the input to its name, which would otherwise leave the list filtered to just that branch — and resets abandoned filter text on close; the description is a tall (`rows={16}`) `components/MarkdownEditor.tsx` (the Write/Preview editor extracted from CommentComposer — controlled mode so parents can reset it; its Preview pane's `minH` tracks `rows` so switching tabs doesn't resize the editor; its optional `attachments` prop turns on pasting, dropping, and picking image/video files — see "Attachments" below) in an `xl` dialog with `scrollBehavior="inside"`, plus a draft checkbox; `createPullRequest` POSTs `/repos/{repo}/pulls` and on success invalidates `["pullRequests", repo]` + `["myPullRequests"]` and navigates straight into the new PR's review screen via the normal open path. PR lists in the main column render `components/PullRequestCard.tsx`. Clicking a PR card in the main column doesn't navigate — it opens `components/PullRequestPreview.tsx`, a right-hand panel embedding the PR's Overview, with a "View PR" button that opens the full review screen (it and the sidebar's rows are the paths that navigate, records the PR as recently viewed via `App.tsx`, and the previewed card gets an accent-coloured border (`selected` on `PullRequestCard`)). GitHub usernames get a small avatar next to them (`components/UserAvatar.tsx`, images from `avatars.githubusercontent.com/{login}`, with an initials fallback; the CSP in `index.html` allows `img-src https:` since markdown comments embed images from arbitrary hosts — badges, screenshots — plus `gh-asset:`, a main-process protocol (`main/github/assets.ts`) that fetches private-repo attachment images with the stored GitHub token: `lib/githubImages.ts` rewrites `github.com/user-attachments/assets/…` srcs (and expired signed `private-user-images.githubusercontent.com` URLs, by extracting the trailing attachment id) to `gh-asset://proxy?url=…` in `Markdown`'s img override; the handler allowlists exact attachment URLs, sends the token to github.com only, and follows the redirect to the short-lived signed S3 URL without the token (S3 rejects requests carrying both a signature and an Authorization header); the CSP also allows `media-src 'self' https: gh-asset:` for attached videos, and the same handler serves byte ranges because media playback demands them — see "Attachments" below; scripts/styles/connections stay `'self'`-only); used on PR cards and the Overview's author line and reviewer badges. Review screen: a header bar (Back, PR title, Open in GitHub, Re-analyse, Submit review, and Merge) over three tabs — **Overview** (PR description + GitHub metadata, like the PR's front page), **Changes** (file list left, diff viewer center), and **Review** (agent summary + Q&A chat, the home for all smart behaviour). Each tab panel owns its own data query and local state; TanStack Query dedupes shared keys. Theme lives in `src/renderer/src/theme.ts` (mono type for slugs/PR numbers/diff stats). Colour mode is user-configurable — Light/Dark/System: `lib/colorMode.ts` persists the setting in localStorage and toggles `.dark`/`.light` on `<html>` (plus `color-scheme` for native controls), tracking OS changes live when set to System; `index.html` ships `class="dark"` (also the default) so first paint isn't a white flash. Syntax highlighting is shiki (`lib/highlighter.ts` — sync core + the JS regex engine, real VS Code TextMate grammars, ~30 languages imported statically; picked over highlight.js because hljs has no TSX grammar and rendered comments inside JSX multicoloured): every token span carries its github-dark AND github-light colour as CSS variables (`defaultColor: false`), and `lib/syntaxColors.ts` is just the two rules that pick one via the `.dark`/`.light` class on `<html>` — colour mode switching never re-highlights. The accent colour is user-configurable: `lib/accent.ts` persists a Chakra palette name in localStorage and stamps it as `data-accent` on `<html>` (applied at boot in `main.tsx`); `theme.ts` has a globalCss rule per palette, so the whole app — portals included — follows. One exception, also in `theme.ts`: the button recipe's `outline` variant pins `colorPalette: "gray"`, because outline buttons are secondary actions (toolbars, Cancel) and a toolbar of accent-coloured outlines reads as a row of primary buttons; a button that carries meaning still sets its own `colorPalette` (yellow "Refresh to update", green merge, red Remove), and a style prop beats the recipe. Default is green; the picker lives in the settings dialog's Appearance tab (`components/AppearanceSettings.tsx`; the dialog is a wide (`maxW="4xl"`, fixed-height) two-column panel: a tinted left rail holding the "Settings" label and five vertical tabs — Appearance / Review / Models / Connections / GitHub — beside a single scrolling content column, with no footer since the close button and Esc do the same job. Every tab is built from `components/SettingsLayout.tsx` — `SettingsPanel` (tab heading + one-line description, and the bottom padding that clears the modal's edge, since padding on the dialog's scroll box doesn't show below the content), `SettingsGroup` (a bordered card whose rows are separated), and `SettingRow` (label + description on the left, the control on the right, or stacked underneath for wide controls) — so the tabs read as one screen instead of five forms. Connections is Claude only: the access choice as `components/LlmProviderSettings.tsx`'s three `RadioCard`s over a status line, then the Claude key. GitHub has its own tab (`components/GitHubSettings.tsx`) holding the two things GitHub needs side by side — the personal access token and the attachment session (`components/GitHubSessionSettings.tsx`, query `["attachmentAuth"]`, connect/disconnect). Both tabs' key fields are `components/SecretKeyRow.tsx`, one row per stored secret owning its own field, save/remove, and the result of the main process's live validation call). The Review tab (`components/ReviewSettings.tsx`) picks the "review personality" — the voice the analysis text is written in (standard/technical/non_technical/simplified/grug/mentor/concise, `ReviewPersonality` in `shared/types.ts`): `lib/reviewPersonality.ts` persists it in renderer localStorage and `ReviewPanel` passes it with each `analyzePullRequest` call; the pipeline appends the matching voice block to the system prompt (`PERSONALITY_PROMPTS` in `analysis/pipeline.ts`, wording only — never what gets reported). It applies at analyse time, so already-cached analyses keep their original voice.
- **Attachment uploads** — a second, separate GitHub credential: a signed-in github.com session kept in its own window partition (`main/github/attachments.ts`), because GitHub has **no API for comment attachments**. Its `/upload/policies/assets` endpoint answers 422 to a personal access token and takes a `user_session` cookie alone, so nothing token-based can attach a file. See "Attachments" below.
- **Typed IPC** — `src/shared/ipc.ts` defines the `IpcApi` interface. `src/main/ipc/router.ts` implements it; `src/preload/index.ts` exposes it as `window.api`. To add an IPC call, add a method to `IpcApi` and the compiler forces implementations on both sides. `src/shared/types.ts` is the single source of truth for data shapes.

### Attachments (images and videos)

Dropping a screenshot or screen recording into a PR description is how a "demo" section gets written, and it's the one GitHub feature with no API behind it: `/upload/policies/assets` refuses a PAT and wants a browser session cookie. Rather than call that internal endpoint ourselves, the app **drives GitHub's own composer** — so GitHub can change its upload protocol without breaking us.

- **The session.** `main/github/attachments.ts` keeps a logged-in github.com session in the `persist:github-web` partition, apart from the token the rest of the app uses. `signInForAttachments` opens a real GitHub sign-in window and polls for the `user_session` cookie (it can't be read any other way); `dotcom_user` names the account for the settings badge. Every path settles — cookie found, window closed, page failed to load, or a 10-minute cap — because the renderer keeps a button spinning until it returns. First paste triggers the sign-in on its own, so Settings is optional.
- **The upload.** A hidden window loads a page with a comment composer (the PR itself, or `issues/new` for the new-PR dialog, which has no PR yet), the file is written to a temp dir (a pasted screenshot arrives as bytes with no path), handed to the composer's file input via the DevTools protocol's `DOM.setFileInputFiles`, and the permanent `user-attachments/assets/…` URL is read back out of the textarea. `backgroundThrottling: false` — a hidden window throttles timers and can stall GitHub's upload script.
- **Two traps worth remembering.** (1) The composer is client-rendered, so the *first* `input[type=file]` on the page is somebody else's — usually Copilot's chat attachment field, which has its own narrower allowlist and produced a baffling "we don't support that file type" naming MOV *in the list of supported types*. Page script picks the input (the one sharing a container with the comment textarea, Copilot's excluded), tags it, and CDP addresses the tag. (2) GitHub ships that same allowlist message into the page **hidden**, ready to show, so scraping error text reports a failure the instant the page loads whatever the file is — only an error that is not in a `<template>`, `hidden`, `display:none`, `visibility:hidden`, or `aria-hidden` counts. Deliberately no geometry check: the upload window is never shown, so `getBoundingClientRect` returns zeros for everything and would hide real errors.
- **The renderer side.** `lib/useAttachmentUpload.ts` holds a placeholder (`![Uploading name…]()`) at the cursor, uploads in parallel, and swaps in the real markdown — every edit goes through a ref holding the latest text, since uploads finish out of order. A failure removes its placeholder and toasts. `MarkdownEditor`'s optional `attachments` prop turns on paste, drop, and a file picker; it's set on all three editors (PR description, conversation comments, new-PR dialog).
- **Rendering them back.** An uploaded video is written into the body as a bare attachment link, and attachment URLs carry no file extension — GitHub decides "player or link" from the content type it serves. A bare attachment autolink (link text identical to the href) renders `components/AttachmentMedia.tsx`, which tries to play it and falls back to the plain link for a zip, a PDF, or a codec Chromium can't decode (ProRes, some HEVC). Bodies written on github.com use real `<video>` tags, which the default sanitize schema dropped — `video`/`source` are now allowed with player attributes only, `src` proxied like images.
- **Byte ranges are mandatory for media.** Chromium's media loader asks for a range and treats a plain 200 as an unsupported source (`MEDIA_ERR_SRC_NOT_SUPPORTED`) even when the bytes are correct, so the `gh-asset://` handler passes `Range` through to the signed storage URL, returns its 206 and `Content-Range` untouched, and adds `Accept-Ranges: bytes` when upstream omits it. Measured, not guessed: a scheme with `stream: true` and no range support still fails; range support without it plays. The signed URL is cached 60s, because seeking otherwise asks github.com to mint a fresh one per range; an expired one is re-minted automatically. The CSP needs `media-src` — without it video falls back to `default-src 'self'` and is blocked outright.

### Analysis pipeline

Analysis is **explicitly user-triggered** (an "Analyse PR" button — never automatic, so API credits are only spent on purpose) and runs as a **background job**: `lib/analysisJobs.ts` (a module store + `useSyncExternalStore`, like the other renderer-global settings) owns the run rather than a component's mutation, so leaving the review screen doesn't lose track of it. It holds one job per PR (`analysing` → `checking` while the chained findings pass runs, keyed repo#number, a second start ignored so credits aren't spent twice), writes the result into the query cache itself, and reports the end with a toast — success with the issue count, a warning when the analysis landed but the issue check failed, an error when the analysis itself failed (which restores the previous analysis rather than leaving a blank tab). `AnalyzedSidebarList` renders running jobs with a spinner — a PR analysed for the first time gets its own row at the top of the Analysed section until the cache list picks it up — and `ReviewPanel`/`ReanalyzeButton` read the same store for their loading states. `analysis/pipeline.ts` fetches the PR detail + file patches from GitHub, builds one prompt (mechanical files like lockfiles get name/stats only; per-file and total patch-size caps), and makes a single Claude Messages API call to `claude-opus-4-8` (plain `fetch`, forced tool use for validated structured output). The result is an `AnalysisResult`: a plain-English `summary`, `groups` (logical change groups in reading order, each with a story, risk level `attention`/`routine`/`mechanical`, and files — every changed file is guaranteed to land in some group), plus `risks`/`behaviorChanges` claims (each with a short nav `title` + full text) carrying `DiffAnchor`s (file + new-file line number, so every claim is verifiable against the diff) and `outOfScope`. Each risk gets a **stable id** (`riskId` — `sha1("risk|" + title + "|" + first anchor)`), so its dismissal survives a re-analysis that reports the same risk; `withRiskMeta` backfills ids on pre-id cached analyses and joins each risk's `resolution` from the findings resolution store at read time (never persisted in the cache). Cached by repo + PR + head SHA in `~/.pr-reviewer/analyses.json` (disk-backed so paid analyses survive restarts; pruned to the 100 newest; SQLite later) — `getExistingAnalysis` checks the cache without ever calling the model. Later: streaming progress stages, a cheap model for mechanical classification, background pre-analysis of the review queue.

### Pre-review findings pass

Runs **automatically after each analysis** by default — "Analyse PR" (and Re-analyse) chains `findIssues` once the analysis lands, controlled by the "Find issues when analysing" toggle in Settings → Review (`lib/findIssuesOnAnalyse.ts`, localStorage, default on); with the toggle off it's run manually from the Issues section in the Review tab's nav. `analysis/findings.ts` runs an **agentic tool loop** — the model gets the same PR context as the analysis plus the repo tools (`read_file`/`grep_repo`/`list_files`/`git_log`, shared with the chat) and ends by calling a `report_findings` structured-output tool. When a same-commit analysis exists, its risks are appended to the prompt as numbered **leads** — unverified hypotheses the agent must investigate and either confirm (the finding carries the lead's number in `lead`) or clear (`clearedLeads`, with a one-line note); `buildLeadVerdicts` maps those back to risk ids as `FindingsResult.leadVerdicts` (`confirmed` verdicts carry the finding's id), which is how the renderer knows a risk became a verified finding or was checked and cleared. The point of the tools is to look *beyond the diff*: the standout `blast_radius` category greps for callers of a changed function/signature and reports the ones the diff didn't update. Both providers report findings by **calling a `report_findings` tool** rather than via structured-output formatting — the API path is a manual tool loop (final round forces `report_findings` so it always commits); the Claude Code path (`runFindingsAgentQuery`) exposes `report_findings` as an MCP tool whose handler captures the input, because the SDK's `outputFormat: json_schema` returns empty when combined with MCP repo tools (a "success" result with no `structured_output`). Each finding has a `category`, `severity` (reuses `RiskSeverity`), title, markdown `body`, a single diff anchor (`path` + new-file `line`), and a ready-to-post `suggestion`. `findingsNormalize.ts` (pure, unit-tested) validates every finding against the diff: the path must be a changed file and the line must sit in its diff (snapped to the nearest in-diff line if the model was slightly off, dropped if unanchorable), then assigns a **stable id** = `sha1(category|path|line)` so a re-run of the same issue keeps its identity, and dedups/sorts high→low. Runs are cached by head SHA in `~/.pr-reviewer/findings.json`; the user's per-issue **resolutions** (`accepted`/`dismissed`) live separately in `finding-resolutions.json` keyed per PR, so they survive re-runs and never nag twice — the store joins them onto each finding as `resolution` at read time, and risk ids key into the same store (dismissing an unverified risk uses the same `setFindingResolution` IPC; the pipeline joins those onto the analysis's risks). IPC: `getFindings` (cache-only, null if never run), `findIssues` (runs the model; `force` skips the cache), `setFindingResolution` (`"open"` clears it). Trust principle: the agent proposes, the human disposes — nothing is posted to GitHub automatically.

The design decision that makes it cheap: resolve symbols with the existing `grepAtCommit` (a definition-shaped regex — `(function|class|interface|type|enum|const|let)\s+Foo\b`, `def`/`func` for Python/Go) rather than a language server. `git grep` runs against the *commit object*, so the bare blobless clone is enough (no checkout, no installed deps, no per-language servers — those were the whole reason this looked like weeks of work). It's also fast enough for a click, which the chat agent is not: it can already answer "where is this defined", but seconds and API credits are the wrong trade for a cmd+click. Three pieces: (a) **word under the cursor** — `CodeText` injects highlighted HTML, so the line is real text nodes; `document.caretPositionFromPoint` gives node + offset, expand to word boundaries with a regex (~30 lines, independent of how the highlighter nested its spans); (b) **resolve** — grep, jump on a single hit, small picker on several; (c) **show it as a *peek*** — an inline expandable panel under the line (reusing `FileView`'s rendering), not a navigation away: a reviewer's place in the diff is the thing worth protecting, and peeking avoids building a file-browser screen with breadcrumbs. Accuracy trade-off accepted deliberately: grep finds "a thing named `save` is defined here", not *which* one — showing "2 definitions" and letting the human pick degrades honestly instead of jumping somewhere wrong. Upgrade path if that annoys: a tree-sitter tags index built during warm-up and cached per head SHA (same pattern as the analysis/findings caches) — an add-on, not a rewrite. Rough cost: 3–4 days for TS/JS, no new dependencies. Explicitly rejected: embedding CodeMirror or Monaco (only needed for *typing*, and Monaco's diff editor would fight `DiffLines`'s comment threads, draft bands, explanation cards, range selection and context expansion), and running real language servers (needs files on disk + installed dependencies, which would drag in #8's checkout and turn days into weeks).

## Development

- `pnpm dev` — run the app. `pnpm typecheck` — both tsconfig projects. `pnpm build` — production build.
- `pnpm format` — Biome formatter (write). `pnpm lint` — Biome linter (check only). `pnpm check` — Biome format + lint + import sorting (write). Config in `biome.json`: 2-space indent, double quotes, respects `.gitignore`.
- pnpm 10 blocks dependency install scripts; `electron` and `esbuild` are allowlisted in package.json (`pnpm.onlyBuiltDependencies`). If `node_modules/electron/dist` is missing after install, run `node node_modules/electron/install.js`.
- Branding: the app is "Reviewr" (`productName` in package.json). The icon is raster artwork at `resources/icon.png` (1024px, transparent margin) → `build/icon.icns` (an iconset of 16–512 at 1x/2x, via `magick` + `iconutil`). Artwork is fitted to an 824px content box inside the 1024px canvas — Apple's proportion, so the icon doesn't read as undersized next to other dock icons. The main process sets the dock icon at runtime (`setDockIcon` in `main/index.ts`). Because dev runs the stock Electron binary, `scripts/brand-dev-electron.sh` (postinstall) rewrites the bundled Electron.app's Info.plist name, swaps its icns, re-signs it ad-hoc (an edited plist breaks the signature), and re-registers the bundle with LaunchServices — macOS caches a bundle's name, so without that last step the dock keeps saying "Electron" however the plist reads.
- Pinned: vite 7 + @vitejs/plugin-react 5 (electron-vite 5 doesn't support vite 8 yet).

## Conventions

- UI is Chakra UI v3 (`@chakra-ui/react` + `@emotion/react`, icons from `react-icons/lu`). Use Chakra components and style props, not CSS files. A Chakra MCP server is available for component examples and props.
- Data fetching goes through TanStack Query (`@tanstack/react-query`). The client lives in `renderer/src/lib/queryClient.ts` and wraps the app in `main.tsx` via `PersistQueryClientProvider`: the query cache persists to localStorage (24h max age, `pullRequestFiles`/`commitFiles`/`fileAtCommit`/`localChanges` excluded — patches and file contents are too big for the ~5MB quota and cheap to refetch, and local changes go stale the moment the working tree moves), so screens paint instantly from the last session while refetching in the background. The renderer cache is NOT the source of truth for analyses — the main process's disk cache is; `getAnalysis` stays correct after restarts because of it. Query keys in use: `["repositories"]`, `["localChanges", repoPath]` (the checkout's uncommitted work for the home screen's Current changes tab — always-on for the selected repo so the tab count stays live; local git only, no token), `["pullRequests", slug]`, `["reviewRequests"]`, `["myPullRequests"]`, `["openPrCounts"]` (open-PR count per registered repo slug, for the sidebar's repo rows), `["branchInfo", repo]` (branches + local-checkout defaults for the new-PR dialog), `["repoMergeSettings", repo]` (the merge methods the repo allows — `components/MergeDialog.tsx` only offers those, defaulting to the first, so squash-only repos behave like GitHub), `["reviewDecision", repo, number]` (GitHub's GraphQL `reviewDecision`, fetched by MergeDialog for open PRs: while it's REVIEW_REQUIRED or CHANGES_REQUESTED — or still loading — the merge button is hidden entirely; null means no review requirement and a failed lookup fails open; SubmitReviewDialog invalidates it so an approval reveals the button; an APPROVED decision also turns the Actions trigger and its "Merge pull request" item green, via the `approved` flag on `useMergeAvailability`), `["pullRequest", repo, number]`, `["prActivity", repo, number]` (a 60s background poll on the review screen — `peekPullRequestActivity` is an ETag conditional request, so unchanged polls are 304s that don't count against the rate limit; the renderer compares the snapshot against the `["pullRequest"]` cache and, when something is newer, swaps the header's refresh icon button for a yellow outline "Refresh to update" button whose tooltip names what changed ("Refresh — 2 new commits, 1 new comment"); best-effort — null on any failure just skips the highlight, and the refresh button's invalidate-by-repo+number predicate clears it), `["pullRequestFiles", repo, number]`, `["pullRequestCommits", repo, number]`, `["commitFiles", repo, sha]`, `["fileAtCommit", repo, sha, path]` (full file text from the workspace clone, for the diff viewer), `["pullRequestComments", repo, number]`, `["pullRequestReviews", repo, number]`, `["reviewComments", repo, number]`, `["resolvedThreads", repo, number]`, `["reactions", repo, number]` (emoji reactions on all of the PR's comments, keyed by comment id — one lookup shared by every comment bar), `["viewedFiles", repo, number]` (paths the viewer marked as viewed, synced with GitHub's checkboxes), `["draftComments", repo, number]` (locally drafted review comments; source of truth is the main process's drafts.json), `["analysis", repo, number]`, `["findings", repo, number]` (pre-review agent findings — the query is cache-only; the model runs through the `["findIssues", repo, number]` mutation, auto-chained after an analysis or fired from the nav, writing back with `setQueryData`), `["viewer"]` (the GitHub login the stored token belongs to), `["secretsStatus"]`, `["attachmentAuth"]` (whether a signed-in github.com session exists for attachments, and which account — separate from the token, since GitHub has no upload API). Mutations (add/remove repo, save/clear key) update the cache via `setQueryData` or `invalidateQueries` so dependent views (setup banner, PR list) refresh automatically.
- React components and functions inside them use the `function` keyword, not arrow functions.
- Component props: `interface Props {}` (or a descriptive exported name if they must be exported).
- No unnecessary comments; TODOs mark unimplemented stubs.
- Formatting and linting are handled by Biome (2-space indent, double quotes). Run `pnpm check` before committing.
- Conventional commits (`feat:`, `fix:`, `chore:`).
