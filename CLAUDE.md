# PR Reviewer

A desktop app that makes code review easier. Think of it as replacing GitHub's "manila folder dump" of files with a guided, agent-assisted review experience.

## The problem

- PR descriptions are often obtuse, empty, or don't explain what the PR is trying to achieve.
- Reviewing means scrolling a big unordered file list. No signal for how data flows, which changes are critical, or where to start.
- No way to ask questions about the code without interrupting the author.

## What the app does

1. **Agent-generated summaries with lenses.** When a PR is opened, an agent produces toggleable views: overview ("what changed and why"), risks, behavior changes (what callers/users experience differently), and scope ("what's NOT in this PR").
2. **Logical change groups + reading order.** The diff is split into narrative chunks ("Change 1: new endpoint, 3 files. Change 2: mechanical rename, 12 files"), each with a risk badge, presented as a guided tour rather than a flat file list.
3. **Q&A agent with full repo context.** Ask questions about specific changes or the whole PR. The agent has the entire repo cloned locally (not just the diff), so it can answer "what does this helper do?" and "who else calls this?".

Planned beyond MVP:

- **Blast radius**: for changed functions/signatures, find callers *outside* the diff that weren't updated — that's where bugs live.
- **Risk-ranked file ordering**: new logic > modified logic > mechanical renames > generated files > lockfiles.
- **Pre-review agent pass**: candidate issues flagged as suggestions for the human to verify, not auto-comments.
- **Diff vs. intent check**: does the PR do what its description/ticket says, and nothing surprising?
- **Changes since last review**: for repeat rounds, summarize what changed and how comments were addressed.
- **Comment drafting**: draft inline comments locally (agent can help phrase), batch-submit as a real GitHub review.

Trust principle: every agent claim must link to the exact lines it's based on, so verification is one click. A reviewer who trusts a wrong summary rubber-stamps a bad PR.

## Architecture

Electron (chosen over Tauri because the Claude Agent SDK, Octokit, and git tooling are all Node/TypeScript — Electron's main process runs them natively; Tauri would need a Node sidecar).

- **Main process (Node)** — all the real work: GitHub API (Octokit), local repo clones under `~/.pr-reviewer/repos` (blobless: `--filter=blob:none`), diff parsing, the analysis pipeline, Claude Agent SDK sessions, SQLite persistence. Secrets never reach the renderer.
- **Renderer (React + Chakra UI v3)** — purely presentational. Welcome screen: no top bar — a full-height split. Left, `components/HomeSidebar.tsx`: four sections — **Repositories** (`components/RepositoryList.tsx` — each row reveals a remove button on hover, and rows are drag-sortable via dnd-kit: whole-row drag with a 4px pointer-distance activation so plain clicks still select; the new order is set optimistically in the `["repositories"]` cache and persisted through the `reorderRepositories` IPC call, which reorders the registry by path, appends any paths the renderer didn't send, and returns the saved list), **Review requests** (open PRs where the user's review is requested, via `listReviewRequestedPullRequests` over IPC — GitHub issue search `review-requested:@me`, filtered in the main process to the registered repos' slugs before the per-PR detail fetches; query key `["reviewRequests"]`; compact rows with +/− stats), **My pull requests** (same shape for `author:@me` via `listMyPullRequests`, query key `["myPullRequests"]`; both sections share `searchOpenPullRequests` in `github/client.ts`, and `Welcome.tsx` invalidates both queries when repos are added/removed since the registry drives the filter), and **Recently viewed** (compact rows, not full cards — PRs the user has opened from any repo, stored in renderer localStorage via `lib/recentPrs.ts`, recorded by `App.tsx` on select, capped at 10 — enforced on read too, so older longer lists trim themselves — with a clear button in the section header) — and a footer anchored at the bottom with two actions: "Add repository" (folders picked via the native directory dialog) and Settings (opens the settings dialog). The main column is tabbed: **Open pull requests** (the selected repo's open PRs — rendered by `components/OpenPullRequestList.tsx`, which adds GitHub-style Author / Assignee / Sort dropdowns (user options show their GitHub avatar next to the login); filtering and sorting are client-side over the already-loaded list (`lib/prFilters.ts` — sorts: newest/oldest/most/least commented/recently/least recently updated; assignee includes "Assigned to nobody"), and the component is keyed by repo slug so filters reset on repo switch; `PullRequest` carries `assignees`/`createdAt`/`updatedAt` to power this) and **Analysed pull requests** (`components/AnalyzedPanel.tsx`); at the right end of the tab bar, a "New pull request" button (`components/NewPullRequestDialog.tsx`, shown when the selected repo has a slug, keyed by slug) opens a create dialog: `getBranchInfo` over IPC (query `["branchInfo", repo]`, `staleTime: 0` so a just-pushed branch always shows, fetched only while open) returns the repo's GitHub branches sorted newest commit first (a GraphQL `refs` query ordered by `TAG_COMMIT_DATE` desc — REST can't sort branches by activity — ≤500, with `defaultBranchRef` in the same call) and — via `getLocalCheckoutBranch` in `repo/local.ts` (`git symbolic-ref`, null on detached HEAD/unregistered) — the local checkout's current branch, pinned to the top of the list when it's on GitHub; head defaults to that branch when pushed and non-default (an info alert says to push first when it isn't), base to the default branch (the title is deliberately never prefilled), and untouched selects use a null-means-suggestion pattern so late-loading data still prefills; head/base are non-portalled selects (portalled menus stack under the dialog), each filtering the other's pick from its options, with the checked item highlighted via `_checked` bg; the description is a `components/MarkdownEditor.tsx` (the Write/Preview editor extracted from CommentComposer — controlled mode so parents can reset it) plus a draft checkbox; `createPullRequest` POSTs `/repos/{repo}/pulls` and on success invalidates `["pullRequests", repo]` + `["myPullRequests"]` and navigates straight into the new PR's review screen via the normal open path. PR lists in the main column render `components/PullRequestCard.tsx`. Clicking any PR on the home screen (card or sidebar row) doesn't navigate — it opens `components/PullRequestPreview.tsx`, a right-hand panel embedding the PR's Overview, with a "View PR" button that opens the full review screen (that's the only home-screen path that navigates, records the PR as recently viewed via `App.tsx`, and the previewed card gets a highlighted border). GitHub usernames get a small avatar next to them (`components/UserAvatar.tsx`, images from `avatars.githubusercontent.com/{login}`, with an initials fallback; the CSP in `index.html` allows `img-src https:` since markdown comments embed images from arbitrary hosts — badges, screenshots — plus `gh-asset:`, a main-process protocol (`main/github/assets.ts`) that fetches private-repo attachment images with the stored GitHub token: `lib/githubImages.ts` rewrites `github.com/user-attachments/assets/…` srcs (and expired signed `private-user-images.githubusercontent.com` URLs, by extracting the trailing attachment id) to `gh-asset://proxy?url=…` in `Markdown`'s img override; the handler allowlists exact attachment URLs, sends the token to github.com only, and follows the redirect to the short-lived signed S3 URL without the token (S3 rejects requests carrying both a signature and an Authorization header); scripts/styles/connections stay `'self'`-only); used on PR cards and the Overview's author line and reviewer badges. Review screen: three tabs — **Overview** (PR description + GitHub metadata, like the PR's front page), **Changes** (file list left, diff viewer center), and **Review** (agent summary + Q&A chat, the home for all smart behaviour). Each tab panel owns its own data query and local state; TanStack Query dedupes shared keys. Theme lives in `src/renderer/src/theme.ts` (mono type for slugs/PR numbers/diff stats). Colour mode is user-configurable — Light/Dark/System: `lib/colorMode.ts` persists the setting in localStorage and toggles `.dark`/`.light` on `<html>` (plus `color-scheme` for native controls), tracking OS changes live when set to System; `index.html` ships `class="dark"` (also the default) so first paint isn't a white flash. The highlight.js palettes in `lib/syntaxColors.ts` are scoped per mode (github-dark / github-light). The accent colour is user-configurable: `lib/accent.ts` persists a Chakra palette name in localStorage and stamps it as `data-accent` on `<html>` (applied at boot in `main.tsx`); `theme.ts` has a globalCss rule per palette, so the whole app — portals included — follows. Default is green; the picker lives in the settings dialog's Appearance tab (`components/AppearanceSettings.tsx`; the dialog is vertical side tabs — Appearance / Review / API keys — with the key form in `components/ApiKeysSettings.tsx`). The Review tab (`components/ReviewSettings.tsx`) picks the "review personality" — the voice the analysis text is written in (standard/technical/non_technical/simplified/grug/mentor/concise, `ReviewPersonality` in `shared/types.ts`): `lib/reviewPersonality.ts` persists it in renderer localStorage and `ReviewPanel` passes it with each `analyzePullRequest` call; the pipeline appends the matching voice block to the system prompt (`PERSONALITY_PROMPTS` in `analysis/pipeline.ts`, wording only — never what gets reported). It applies at analyse time, so already-cached analyses keep their original voice.
- **Typed IPC** — `src/shared/ipc.ts` defines the `IpcApi` interface. `src/main/ipc/router.ts` implements it; `src/preload/index.ts` exposes it as `window.api`. To add an IPC call, add a method to `IpcApi` and the compiler forces implementations on both sides. `src/shared/types.ts` is the single source of truth for data shapes.

### Analysis pipeline

Analysis is **explicitly user-triggered** (an "Analyse PR" button — never automatic, so API credits are only spent on purpose). `analysis/pipeline.ts` fetches the PR detail + file patches from GitHub, builds one prompt (mechanical files like lockfiles get name/stats only; per-file and total patch-size caps), and makes a single Claude Messages API call to `claude-opus-4-8` (plain `fetch`, forced tool use for validated structured output). The result is an `AnalysisResult`: a plain-English `summary`, `groups` (logical change groups in reading order, each with a story, risk level `attention`/`routine`/`mechanical`, and files — every changed file is guaranteed to land in some group), plus `risks`/`behaviorChanges` claims (each with a short nav `title` + full text) carrying `DiffAnchor`s (file + new-file line number, so every claim is verifiable against the diff) and `outOfScope`. Cached by repo + PR + head SHA in `~/.pr-reviewer/analyses.json` (disk-backed so paid analyses survive restarts; pruned to the 100 newest; SQLite later) — `getExistingAnalysis` checks the cache without ever calling the model. Later: streaming progress stages, a cheap model for mechanical classification, background pre-analysis of the review queue.

## Current status (as of 2026-07-14)

Scaffold complete and verified: `pnpm typecheck` and `pnpm build` pass, `pnpm dev` opens the app. The UI is built with Chakra UI v3. Three things are real: (1) repository management — add local git repos via the native folder dialog, the GitHub slug is read from the `origin` remote, list persists to `~/.pr-reviewer/repositories.json`; (2) API-key settings — a gear on the welcome screen opens a dialog to enter a Claude API key and a GitHub token. Keys are validated with a live API call before saving, encrypted with Electron `safeStorage` (macOS Keychain), and stored in `~/.pr-reviewer/secrets.json`. Raw keys never cross IPC to the renderer; only status (set/not-set) does. A stored key that fails to decrypt (keychain locked, or access denied to that launch of the app) reports as not set but is NEVER deleted — decrypt failures are often transient, and deleting on one destroys the key permanently. (3) live open PRs and diffs — `github/client.ts` uses the stored token to fetch a repo's open pull requests via the GitHub REST API (plain `fetch`, no Octokit), including per-PR line/file counts, and each PR's changed files with their patches (`/pulls/{n}/files`). The Review screen is split into three tabs: **Overview** (`components/PullRequestOverview.tsx`) shows the PR's description and live GitHub metadata — state/draft badge, base ← head branches, labels (each GitHub label's hex colour is mapped by hue to the nearest Chakra palette in `lib/labelColor.ts` and rendered as a themed `Badge` — low-saturation or extreme-lightness colours fall back to gray), reviewers, commit/file/line counts, dates — via a new `getPullRequest` detail call, plus the PR's conversation comments (GitHub issue comments via `listPullRequestComments`, `/issues/{n}/comments`; rendered as `components/CommentCard.tsx` — avatar + author + date header over a markdown body; below them, `components/CommentComposer.tsx` posts new comments (a `MarkdownEditor` with Write/Preview tabs, Cmd/Ctrl+Enter submits, `addPullRequestComment` POSTs and the created comment is appended to the query cache via `setQueryData`); inline diff review comments are a separate endpoint — each inline thread also joins the conversation timeline as `components/ReviewThreadCard.tsx`: a header with the file path and line range (or an "Outdated" badge when `line` is null), the tail of the comment's `diff_hunk` as a mini highlighted diff (trimmed to the commented range, min 4 lines), then the thread itself; resolved threads collapse to just that header with an orange "Resolved" badge and a Show/Hide toggle, like GitHub — resolution isn't in the REST comments, so `listResolvedReviewThreads` (a GraphQL `reviewThreads.isResolved` lookup, joined by the thread's first-comment `databaseId` = REST comment id, paginated past 100) feeds `["resolvedThreads", repo, number]` and a failed lookup just shows threads unresolved; on-diff rendering is on the Changes tab — see below); **Changes** (`components/ChangesView.tsx`) is the real selectable file list + unified diff (`components/DiffView.tsx`) — the file-list sidebar is drag-resizable via `lib/usePanelWidth.ts` (a shared hook that also powers the Review tab's chat column: pointer-drag from the panel edge, width clamped and persisted per localStorage key) and has a filter input above the list (case-insensitive substring match on path/previousPath, Esc clears, the Files heading shows matched/total while filtering; the value is debounced 150ms via `use-debounce`, and `DiffLines` is `memo`ized — with ChangesView memoizing its `commenting` prop for referential stability — so filter keystrokes re-render only the sidebar, never the diff rows) — with an optional commit-by-commit mode — a collapsible (collapsed by default) compact scrollable commit list (`components/CommitList.tsx`, shown only when the PR has 2+ commits, fed by `/pulls/{n}/commits` via `listPullRequestCommits`) sits above the file list; picking a commit swaps the file list/diffs to just that commit's changes (`listCommitFiles`, `/commits/{sha}`), and an "All changes" row at the top reverts to the full changelist (the default). The Changes tab also has GitHub-style inline review comments: `listReviewComments` (`/pulls/{n}/comments` — the review-comments API, distinct from the conversation's issue comments) loads existing inline discussions, grouped into per-file threads by `lib/reviewComments.ts` (replies attach via `in_reply_to_id`; a reply orphaned by a deleted root is promoted to root so the thread survives; outdated threads — `line: null` — are dropped from the diff but still shown in the Overview timeline), each rendered by `components/DiffCommentThread.tsx` under its anchor line with a reply box (`replyToReviewComment`, `/pulls/{n}/comments/{id}/replies`) and, on the viewer's own comments (login via `getViewer`, cached under `["viewer"]`), a hover-revealed delete button with an inline confirm step (`deleteReviewComment`, DELETE `/pulls/comments/{id}`; success refetches the list rather than editing the cache, because deleting a thread's root re-roots its replies server-side). Diff lines covered by an existing thread's range get a yellow marker stripe on their left edge (`isCommented` in DiffLines, works in both view modes). Hovering a diff line shows a "+" gutter button — click for one line, or press-and-drag for a range (one side, one hunk; GitHub's rule: deleted lines anchor LEFT, added/context lines RIGHT) — opening `components/DiffCommentComposer.tsx`, which posts via `addReviewComment` (`commit_id` = the detail query's full `headSha`; the summary `PullRequest.headSha` is truncated and must not be used). The PR description renders as real GitHub-flavored markdown (`components/Markdown.tsx`, react-markdown + remark-gfm, plus rehype-raw → rehype-sanitize so inline HTML — which GitHub allows and bots like Notion's rely on — renders instead of showing as escaped text, with untrusted tags/attributes stripped); external links open in the system browser (main-process `setWindowOpenHandler`/`will-navigate` guard via `shell.openExternal`). The model sometimes leaks the groups JSON into the summary string; `splitLeakedGroups` in pipeline.ts strips it (and uses the leaked copy as groups if the real field came back empty). The Review tab is the guided review: an "Analyse PR" empty state (analysis is never automatic), then a three-panel layout — left, `components/AnalysisNav.tsx` (a Changes-style nav list: Summary, then each risk, behavior change, and reading-guide group as a clickable row; claims show their short `title`, groups get risk-colored dots); middle, `components/AnalysisDetail.tsx` renders the selected item — the summary pane (+ "Not in this PR" + analysed-commit footer), or a claim/group with its full text and the relevant files' diffs embedded as collapsible cards (`components/FileDiffCard.tsx`, mechanical groups start collapsed) plus clickable `file:line` anchor chips that scroll to the diff within the pane; right, `components/ChatPanel.tsx` is the full-height Q&A column. Selection state (`AnalysisSelection`, exported from AnalysisNav) lives in `ReviewPanel` and falls back to Summary if a selected item no longer exists. Risk badges: `components/RiskBadge.tsx`. The chat is a repo-aware agent (`agent/session.ts` + `agent/tools.ts`): the main process keeps one context per PR (rebuilt if the PR gets new commits) and disk-backed conversation histories in `~/.pr-reviewer/chats.json` (capped at 100 messages per PR; the newest 20 go to the model as context) — exposed as `getChatHistory` over IPC, which `ChatPanel` loads via `useQuery(["chatHistory", …])` with local overlay state for streaming/failed messages, so conversations survive restarts; context = the same capped diff the analysis uses (`buildPullRequestContext`, exported from pipeline.ts) + the cached analysis JSON; model `claude-sonnet-5` (fast for interactive use — Opus stays on the one-shot analysis); the context block is marked `cache_control: ephemeral` so follow-up questions hit Anthropic's prompt cache. Answers stream: the main process parses the SSE stream and pushes `text_delta`s to the renderer via `webContents.send` on the `chatChunk` channel (see `ChatChunk`/`RendererEvents` in `shared/ipc.ts`; preload exposes `onChatChunk` returning an unsubscribe); `askQuestion` still resolves with the full answer, which replaces the streamed text as the authoritative copy. On top of that runs a client-side tool loop (max 8 rounds; the final round is sent without tools to force a text answer): the model can call `read_file`, `list_files`, `grep_repo`, and `git_log` (defined + executed in `agent/tools.ts` against the workspace clone, pinned to the PR's head SHA). `grep_repo` triggers `ensureHeadBlobs` first — a targeted backfill that lists the blobs missing from the reviewed commit's tree (`rev-list --missing=print`, which counts donor/alternate objects as present) and batch-fetches just those by id; it also runs during PR warm-up, so the first grep rarely waits. Within a question's loop, the full tool conversation is kept and a moving `cache_control` breakpoint sits on the newest tool results so each round re-reads the prefix from Anthropic's prompt cache; stored history stays plain text (tool activity is not replayed across questions). Tool failures are returned to the model as `is_error` tool results — it's prompted to fall back to diff-only answers and say what it couldn't verify. Diff rendering is shared: `lib/diffParser.ts` (patch → lines + syntax highlighting, plus `buildSplitRows` which pairs del/add runs into side-by-side rows) feeds `components/DiffLines.tsx`, used by both the full-pane `DiffView` (Changes tab) and `FileDiffCard` (Review tab); file status letters/colors live in `lib/fileStatus.ts`. Diffs render inline or split (side-by-side): the global layout mode lives in `lib/diffViewMode.ts` (localStorage + `useSyncExternalStore` hook so every mounted diff reacts), picked via `components/DiffViewModeSelect.tsx` at the right end of the Review screen's tab bar — Inline / Split / Dynamic, where Dynamic goes split per diff when its container is ≥960px (ResizeObserver in DiffLines). Nothing is mock anymore, and the chat can see beyond the diff via its repo tools.

The repo workspace is real (`repo/workspace.ts` + `repo/git.ts`): opening a PR fires a best-effort background warm-up (from the `getPullRequest` IPC handler) that maintains a **bare, blobless** clone per repo at `~/.pr-reviewer/repos/owner__repo.git` — no checkout; everything is read from the object store pinned to a commit (`showFile`/`listFiles`/`logForPath`), so all PRs of a repo share one clone and blobs download lazily on first read. The PR's head commit comes from `refs/pull/<n>/head` (works for fork PRs). Clones use the user's registered local checkout as an object donor (`--reference-if-able`) when available — the alternates link persists, so donor objects count as present forever. Warm-up finishes by backfilling the head commit's tree (`ensureHeadBlobs`): batch-fetch only the blobs missing after the donor and previously-fetched PRs are counted, so grep never has to lazy-fetch file-by-file and each PR only downloads its own delta. Auth: the GitHub token is injected per-command via `GIT_CONFIG_*` env vars (never written to the clone's config); every git command gets it because lazy blob fetches can happen on any read. Syncs are deduped in-flight and rate-limited (5-min TTL).

## Conventions

- UI is Chakra UI v3 (`@chakra-ui/react` + `@emotion/react`, icons from `react-icons/lu`). Use Chakra components and style props, not CSS files. A Chakra MCP server is available for component examples and props.
- Data fetching goes through TanStack Query (`@tanstack/react-query`). The client lives in `renderer/src/lib/queryClient.ts` and wraps the app in `main.tsx` via `PersistQueryClientProvider`: the query cache persists to localStorage (24h max age, `pullRequestFiles` and `commitFiles` excluded — patches are too big for the ~5MB quota and cheap to refetch), so screens paint instantly from the last session while refetching in the background. The renderer cache is NOT the source of truth for analyses — the main process's disk cache is; `getAnalysis` stays correct after restarts because of it. Query keys in use: `["repositories"]`, `["pullRequests", slug]`, `["reviewRequests"]`, `["myPullRequests"]`, `["branchInfo", repo]` (branches + local-checkout defaults for the new-PR dialog), `["repoMergeSettings", repo]` (the merge methods the repo allows — `components/MergeDialog.tsx` only offers those, defaulting to the first, so squash-only repos behave like GitHub), `["pullRequest", repo, number]`, `["pullRequestFiles", repo, number]`, `["pullRequestCommits", repo, number]`, `["commitFiles", repo, sha]`, `["pullRequestComments", repo, number]`, `["pullRequestReviews", repo, number]`, `["reviewComments", repo, number]`, `["resolvedThreads", repo, number]`, `["analysis", repo, number]`, `["viewer"]` (the GitHub login the stored token belongs to), `["secretsStatus"]`. Mutations (add/remove repo, save/clear key) update the cache via `setQueryData` or `invalidateQueries` so dependent views (setup banner, PR list) refresh automatically.
- React components and functions inside them use the `function` keyword, not arrow functions.
- Component props: `interface Props {}` (or a descriptive exported name if they must be exported).
- No unnecessary comments; TODOs mark unimplemented stubs.
- Formatting and linting are handled by Biome (2-space indent, double quotes). Run `pnpm check` before committing.
- Conventional commits (`feat:`, `fix:`, `chore:`).
