# PR Reviewer

A desktop app that makes code review easier. Think of it as replacing GitHub's "manila folder dump" of files with a guided, agent-assisted review experience.

## The problem

- PR descriptions are often obtuse, empty, or don't explain what the PR is trying to achieve.
- Reviewing means scrolling a big unordered file list. No signal for how data flows, which changes are critical, or where to start.
- No way to ask questions about the code without interrupting the author.

## What the app does

1. **Agent-generated summaries with lenses.** When a PR is opened, an agent produces toggleable views: overview ("what changed and why"), risks, behavior changes (what callers/users experience differently), and scope ("what's NOT in this PR").
2. **Logical change groups + reading order.** The diff is split into narrative chunks ("Change 1: new endpoint, 3 files. Change 2: mechanical rename, 12 files"), each with a risk badge, presented as a guided tour rather than a flat file list.
3. **Q&A agent with full repo context.** Ask questions about specific changes or the whole PR. The agent has the entire repo cloned locally (not just the diff), so it can answer "what does this helper do?" and "who else calls this?".

Planned beyond MVP:

- **Blast radius**: for changed functions/signatures, find callers *outside* the diff that weren't updated — that's where bugs live.
- **Risk-ranked file ordering**: new logic > modified logic > mechanical renames > generated files > lockfiles.
- **Pre-review agent pass**: candidate issues flagged as suggestions for the human to verify, not auto-comments.
- **Diff vs. intent check**: does the PR do what its description/ticket says, and nothing surprising?
- **Changes since last review**: for repeat rounds, summarize what changed and how comments were addressed.
- **Comment drafting**: draft inline comments locally (agent can help phrase), batch-submit as a real GitHub review.

Trust principle: every agent claim must link to the exact lines it's based on, so verification is one click. A reviewer who trusts a wrong summary rubber-stamps a bad PR.

## Architecture

Electron (chosen over Tauri because the Claude Agent SDK, Octokit, and git tooling are all Node/TypeScript — Electron's main process runs them natively; Tauri would need a Node sidecar).

- **Main process (Node)** — all the real work: GitHub API (Octokit), local repo clones under `~/.pr-reviewer/repos` (blobless: `--filter=blob:none`), diff parsing, the analysis pipeline, Claude Agent SDK sessions, SQLite persistence. Secrets never reach the renderer.
- **Renderer (React + Chakra UI v3)** — purely presentational. Welcome screen: a top bar (app title + settings gear, same style as the Review screen header) over a full-height three-panel split — left, `components/RepoSidebar.tsx` (the repo list with add/remove buttons anchored at the bottom; folders picked via the native directory dialog); middle, the selected repo's open PRs; right, `components/RecentPanel.tsx` — a "Recently viewed" column (PRs the user has opened, stored in renderer localStorage via `lib/recentPrs.ts`, recorded by `App.tsx` on select, capped at 20; hidden when empty, with a Clear button). Both PR lists render `components/PullRequestCard.tsx`. Review screen: three tabs — **Overview** (PR description + GitHub metadata, like the PR's front page), **Changes** (file list left, diff viewer center), and **Review** (agent summary + Q&A chat, the home for all smart behaviour). Each tab panel owns its own data query and local state; TanStack Query dedupes shared keys. Theme lives in `src/renderer/src/theme.ts` (mono type for slugs/PR numbers/diff stats). Colour mode is user-configurable — Light/Dark/System: `lib/colorMode.ts` persists the setting in localStorage and toggles `.dark`/`.light` on `<html>` (plus `color-scheme` for native controls), tracking OS changes live when set to System; `index.html` ships `class="dark"` (also the default) so first paint isn't a white flash. The highlight.js palettes in `lib/syntaxColors.ts` are scoped per mode (github-dark / github-light). The accent colour is user-configurable: `lib/accent.ts` persists a Chakra palette name in localStorage and stamps it as `data-accent` on `<html>` (applied at boot in `main.tsx`); `theme.ts` has a globalCss rule per palette, so the whole app — portals included — follows. Default is green; the picker lives in the settings dialog's Appearance tab (`components/AppearanceSettings.tsx`; the dialog is vertical side tabs — API keys / Appearance — with the key form in `components/ApiKeysSettings.tsx`).
- **Typed IPC** — `src/shared/ipc.ts` defines the `IpcApi` interface. `src/main/ipc/router.ts` implements it; `src/preload/index.ts` exposes it as `window.api`. To add an IPC call, add a method to `IpcApi` and the compiler forces implementations on both sides. `src/shared/types.ts` is the single source of truth for data shapes.

### Analysis pipeline

Analysis is **explicitly user-triggered** (an "Analyse PR" button — never automatic, so API credits are only spent on purpose). `analysis/pipeline.ts` fetches the PR detail + file patches from GitHub, builds one prompt (mechanical files like lockfiles get name/stats only; per-file and total patch-size caps), and makes a single Claude Messages API call to `claude-opus-4-8` (plain `fetch`, forced tool use for validated structured output). The result is an `AnalysisResult`: a plain-English `summary`, `groups` (logical change groups in reading order, each with a story, risk level `attention`/`routine`/`mechanical`, and files — every changed file is guaranteed to land in some group), plus `risks`/`behaviorChanges` claims (each with a short nav `title` + full text) carrying `DiffAnchor`s (file + new-file line number, so every claim is verifiable against the diff) and `outOfScope`. Cached by repo + PR + head SHA in `~/.pr-reviewer/analyses.json` (disk-backed so paid analyses survive restarts; pruned to the 100 newest; SQLite later) — `getExistingAnalysis` checks the cache without ever calling the model. Later: streaming progress stages, a cheap model for mechanical classification, background pre-analysis of the review queue.

## Current status (as of 2026-07-14)

Scaffold complete and verified: `pnpm typecheck` and `pnpm build` pass, `pnpm dev` opens the app. The UI is built with Chakra UI v3. Three things are real: (1) repository management — add local git repos via the native folder dialog, the GitHub slug is read from the `origin` remote, list persists to `~/.pr-reviewer/repositories.json`; (2) API-key settings — a gear on the welcome screen opens a dialog to enter a Claude API key and a GitHub token. Keys are validated with a live API call before saving, encrypted with Electron `safeStorage` (macOS Keychain), and stored in `~/.pr-reviewer/secrets.json`. Raw keys never cross IPC to the renderer; only status (set/not-set) does. (3) live open PRs and diffs — `github/client.ts` uses the stored token to fetch a repo's open pull requests via the GitHub REST API (plain `fetch`, no Octokit), including per-PR line/file counts, and each PR's changed files with their patches (`/pulls/{n}/files`). The Review screen is split into three tabs: **Overview** (`components/PullRequestOverview.tsx`) shows the PR's description and live GitHub metadata — state/draft badge, base ← head branches, labels, reviewers, commit/file/line counts, dates — via a new `getPullRequest` detail call; **Changes** (`components/ChangesView.tsx`) is the real selectable file list + unified diff (`components/DiffView.tsx`), with an optional commit-by-commit mode — a collapsible (collapsed by default) compact scrollable commit list (`components/CommitList.tsx`, shown only when the PR has 2+ commits, fed by `/pulls/{n}/commits` via `listPullRequestCommits`) sits above the file list; picking a commit swaps the file list/diffs to just that commit's changes (`listCommitFiles`, `/commits/{sha}`), and an "All changes" row at the top reverts to the full changelist (the default); **Review** (`components/ReviewPanel.tsx`) holds the agent summary + Q&A chat. The PR description renders as real GitHub-flavored markdown (`components/Markdown.tsx`, react-markdown + remark-gfm); external links open in the system browser (main-process `setWindowOpenHandler`/`will-navigate` guard via `shell.openExternal`). (4) the analysis pipeline is real — the stored Claude key powers a single structured-output call (see "Analysis pipeline" above), exposed over IPC as `getAnalysis` (cache-only check, returns null if not analysed) and `analyzePullRequest` (runs the model). The Review tab is the guided review: an "Analyse PR" empty state (analysis is never automatic), then a three-panel layout — left, `components/AnalysisNav.tsx` (a Changes-style nav list: Summary, then each risk, behavior change, and reading-guide group as a clickable row; claims show their short `title`, groups get risk-colored dots); middle, `components/AnalysisDetail.tsx` renders the selected item — the summary pane (+ "Not in this PR" + analysed-commit footer), or a claim/group with its full text and the relevant files' diffs embedded as collapsible cards (`components/FileDiffCard.tsx`, mechanical groups start collapsed) plus clickable `file:line` anchor chips that scroll to the diff within the pane; right, `components/ChatPanel.tsx` is the full-height Q&A column. Selection state (`AnalysisSelection`, exported from AnalysisNav) lives in `ReviewPanel` and falls back to Summary if a selected item no longer exists. Risk badges: `components/RiskBadge.tsx`. The chat is a repo-aware agent (`agent/session.ts` + `agent/tools.ts`): the main process keeps one context per PR (rebuilt if the PR gets new commits) and disk-backed conversation histories in `~/.pr-reviewer/chats.json` (capped at 100 messages per PR; the newest 20 go to the model as context) — exposed as `getChatHistory` over IPC, which `ChatPanel` loads via `useQuery(["chatHistory", …])` with local overlay state for streaming/failed messages, so conversations survive restarts; context = the same capped diff the analysis uses (`buildPullRequestContext`, exported from pipeline.ts) + the cached analysis JSON; model `claude-sonnet-5` (fast for interactive use — Opus stays on the one-shot analysis); the context block is marked `cache_control: ephemeral` so follow-up questions hit Anthropic's prompt cache. Answers stream: the main process parses the SSE stream and pushes `text_delta`s to the renderer via `webContents.send` on the `chatChunk` channel (see `ChatChunk`/`RendererEvents` in `shared/ipc.ts`; preload exposes `onChatChunk` returning an unsubscribe); `askQuestion` still resolves with the full answer, which replaces the streamed text as the authoritative copy. On top of that runs a client-side tool loop (max 8 rounds; the final round is sent without tools to force a text answer): the model can call `read_file`, `list_files`, `grep_repo`, and `git_log` (defined + executed in `agent/tools.ts` against the workspace clone, pinned to the PR's head SHA). `grep_repo` triggers `ensureHeadBlobs` first — a targeted backfill that lists the blobs missing from the reviewed commit's tree (`rev-list --missing=print`, which counts donor/alternate objects as present) and batch-fetches just those by id; it also runs during PR warm-up, so the first grep rarely waits. Within a question's loop, the full tool conversation is kept and a moving `cache_control` breakpoint sits on the newest tool results so each round re-reads the prefix from Anthropic's prompt cache; stored history stays plain text (tool activity is not replayed across questions). Tool failures are returned to the model as `is_error` tool results — it's prompted to fall back to diff-only answers and say what it couldn't verify. Diff rendering is shared: `lib/diffParser.ts` (patch → lines + syntax highlighting) feeds `components/DiffLines.tsx`, used by both the full-pane `DiffView` (Changes tab) and `FileDiffCard` (Review tab); file status letters/colors live in `lib/fileStatus.ts`. Nothing is mock anymore, and the chat can see beyond the diff via its repo tools.

The repo workspace is real (`repo/workspace.ts` + `repo/git.ts`): opening a PR fires a best-effort background warm-up (from the `getPullRequest` IPC handler) that maintains a **bare, blobless** clone per repo at `~/.pr-reviewer/repos/owner__repo.git` — no checkout; everything is read from the object store pinned to a commit (`showFile`/`listFiles`/`logForPath`), so all PRs of a repo share one clone and blobs download lazily on first read. The PR's head commit comes from `refs/pull/<n>/head` (works for fork PRs). Clones use the user's registered local checkout as an object donor (`--reference-if-able`) when available — the alternates link persists, so donor objects count as present forever. Warm-up finishes by backfilling the head commit's tree (`ensureHeadBlobs`): batch-fetch only the blobs missing after the donor and previously-fetched PRs are counted, so grep never has to lazy-fetch file-by-file and each PR only downloads its own delta. Auth: the GitHub token is injected per-command via `GIT_CONFIG_*` env vars (never written to the clone's config); every git command gets it because lazy blob fetches can happen on any read. Syncs are deduped in-flight and rate-limited (5-min TTL).

## Development

- `pnpm dev` — run the app. `pnpm typecheck` — both tsconfig projects. `pnpm build` — production build.
- `pnpm format` — Biome formatter (write). `pnpm lint` — Biome linter (check only). `pnpm check` — Biome format + lint + import sorting (write). Config in `biome.json`: 2-space indent, double quotes, respects `.gitignore`.
- pnpm 10 blocks dependency install scripts; `electron` and `esbuild` are allowlisted in package.json (`pnpm.onlyBuiltDependencies`). If `node_modules/electron/dist` is missing after install, run `node node_modules/electron/install.js`.
- Branding: the app is "Reviewr" (`productName` in package.json). Icon source is `resources/icon.svg` → rendered to `resources/icon.png` (1024px, via `rsvg-convert`) → `build/icon.icns` (via `sips` + `iconutil`). The main process sets the dock icon at runtime (`setDockIcon` in `main/index.ts`). Because dev runs the stock Electron binary, `scripts/brand-dev-electron.sh` (postinstall) rewrites the bundled Electron.app's Info.plist name, swaps its icns, and re-signs it ad-hoc so the dock says "Reviewr" during `pnpm dev`.
- Pinned: vite 7 + @vitejs/plugin-react 5 (electron-vite 5 doesn't support vite 8 yet).

## Conventions

- UI is Chakra UI v3 (`@chakra-ui/react` + `@emotion/react`, icons from `react-icons/lu`). Use Chakra components and style props, not CSS files. A Chakra MCP server is available for component examples and props.
- Data fetching goes through TanStack Query (`@tanstack/react-query`). The client lives in `renderer/src/lib/queryClient.ts` and wraps the app in `main.tsx` via `PersistQueryClientProvider`: the query cache persists to localStorage (24h max age, `pullRequestFiles` and `commitFiles` excluded — patches are too big for the ~5MB quota and cheap to refetch), so screens paint instantly from the last session while refetching in the background. The renderer cache is NOT the source of truth for analyses — the main process's disk cache is; `getAnalysis` stays correct after restarts because of it. Query keys in use: `["repositories"]`, `["pullRequests", slug]`, `["pullRequest", repo, number]`, `["pullRequestFiles", repo, number]`, `["pullRequestCommits", repo, number]`, `["commitFiles", repo, sha]`, `["analysis", repo, number]`, `["secretsStatus"]`. Mutations (add/remove repo, save/clear key) update the cache via `setQueryData` or `invalidateQueries` so dependent views (setup banner, PR list) refresh automatically.
- React components and functions inside them use the `function` keyword, not arrow functions.
- Component props: `interface Props {}` (or a descriptive exported name if they must be exported).
- No unnecessary comments; TODOs mark unimplemented stubs.
- Formatting and linting are handled by Biome (2-space indent, double quotes). Run `pnpm check` before committing.
- Conventional commits (`feat:`, `fix:`, `chore:`).
